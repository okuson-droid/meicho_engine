# 並行作業の進め方のレビューと裁定（2026-09-20）

依頼: `engine/HANDOFF_20260920_PARALLEL_REVIEW.md`。書いたのはアプリのチャットのクロエ（マスターがこのチャットに引継ぎ書を渡し、「手順を確定させよう」と指示した）。
**運用の決まりそのものは、ルートの `LANES.md` にある。**この文書は、なぜそう決めたかと、叩き台への採否を残す。

## 1. 結論

**1 つのファイルには、書き手の持ち場を 1 つだけにする。**共有して書くファイルを無くす。

叩き台の 7 項目は、どれも「2 つのチャットが同じファイルに書く」ことを前提に、札・番号の範囲予約・末尾追記・楽観ロックで守る形だった。
事故の再発防止としては正しいが、事故の面を狭めてはいない。共有をやめれば、D-番号の衝突・同時書き込み・札の外し忘れは**構造的に起きなくなる**。

### マスターの裁定（2026-09-20）

1. 上の原則を採用する
2. **M1（エンジン本体に出来事列と観戦視点を足す）はエンジンのチャットが実装する。**アプリのチャットが仕様書を書いて送り箱で渡す
3. **切り替えのための共有ファイルへの書き込みは、エンジンのチャットに任せる。**アプリのチャットは 2026-09-20 のこの時点から共有ファイルに書かない

## 2. 根拠（2026-09-20 にアプリのチャットで実際に起きたこと）

- `engine/decisions.md`（約 700KB）への書き戻し 6 回のうち **3 回、`device_commit_files` が written を返したのに中身が載らなかった**。
  更新日時は進み、サイズは古いままだった。3 回とも、新しい `mtimeMs` でもう一度書き戻すと載った。
  うち 1 回（D-108 追記 1）は書いた直後に確かめなかったため、数時間後に再ステージして初めて消えていることに気づいた
- アプリのチャットが `TASKS.md` をステージした **約 1 分後に、エンジンのチャットが同じ `TASKS.md` を書いていた**（更新日時 13:38:14 JST）。
  楽観ロックは衝突を弾くが、弾かれた側は読み直し・当て直し・書き直しになり、その書き直しがまた上の罠を踏む
- 700KB のファイルに 3KB 追記するたびに、700KB 全体を送り直している。書く回数が多いほど罠を踏む回数も増える

原因が OneDrive かどうかは切り分けていない（引継ぎ書 §2.2 の既知の罠と症状は同じである）。

## 3. 叩き台 7 項目への採否

1. **持ち場をファイル単位で決める → 採用し、強めた。**重なり（`engine.py`・`state.py`）に札を置く案は不採用。
   重なりそのものを無くした——エンジン本体はどんな場合もエンジンの持ち場が触る（裁定 2）。札が無いので、外し忘れ・期限の問題も消える
2. **D-番号を範囲で予約する → 不採用。**範囲を分けても同じ 700KB のファイルに 2 者が書く点は変わらず、§2 の事故がそのまま残る。
   代わりにアプリの決定は別ファイル・別番号（`APP-001`〜、`engine/app/DECISIONS_APP.md`）にした。
   接頭辞は `D-A01` や `AD-1` も考えたが、`D-1` という部分文字列を含むと既存文書の検索（`D-10` など）に混ざるので、含まない `APP-` にした
3. **台帳を分ける → 採用。**`engine/app/TASKS_APP.md`。`TASKS.md` にはその指し先の 1 行だけを置く（置くのはエンジンの持ち場）
4. **共有ファイルの書き方（直前に再ステージ・楽観ロック・末尾に足すだけ・書いた後に確認）→ 作法として採用**（`LANES.md` §5）。
   ただし共有ファイルが無くなったので、これは「2 者の衝突を防ぐ決まり」ではなく「OneDrive の罠を防ぐ決まり」になった。
   「既存行は直さず末尾に足すだけ」は不要になったので外した（自分の台帳は自分で自由に直してよい）
5. **PC への依頼は 1 本の列 → 形を変えて採用。**依頼書は持ち場ごとに自分の場所へ書く（アプリは `engine/app/PC_REQUEST_<日付>_APP.md`）。
   列を 1 つのファイルで管理すると、それがまた共有ファイルになる。代わりに「30 分を超える依頼を 2 つ同時に出したままにしない・
   出す前に相手の未実施の依頼書を見る・順番はマスターが決める」とした。実行するのはマスターなので、順番はマスターが自然に見える
6. **引継ぎ書の語幹を分ける → 採用**し、置き場所も分けた（`engine/app/HANDOFF_<日付>_APP.md`）。
   加えて「引継ぎ書で閉じられるのは自分の持ち場の項目だけ。相手に関わる項目は送り箱に置く」を足した（J-1〜J-6 の取り残しへの対策）
7. **連絡帳を 1 枚置く → 2 つに分けて採用。**決まりと持ち場の表は `LANES.md`（裁定のときしか変わらない）。
   申し送りは**方向ごとの送り箱**（`engine/app/TO_ENGINE.md`・`engine/TO_APP.md`）。
   1 枚の連絡帳に両者が申し送りを書くと、それが最も頻繁に書かれる共有ファイルになってしまう

## 4. レビュアーへの問い 7 つへの答え

1. 採否は §3。足りなかった項目は「破れたことに気づく仕組み」（問い 6）と「M1 の担当」（問い 4）
2. **D-番号**: 単一書き手（エンジンだけが振る）＋アプリは別系列 `APP-`。既存の文書が参照する D-番号には一切触れない
3. **`TASKS.md` と `decisions.md`**: 分ける。どちらもエンジンの持ち場だけが書く
4. **M1**: エンジンのチャットに依頼として出す（裁定 2）。理由: 指紋 4 種と digest の確認・全検査の PC 依頼・`MAX_LIFE` の相乗りは
   エンジンの持ち場が慣れており、出来事の記録は `engine.py` の広い範囲（`_apply_op`・`_draw`・`_damage`・`_pump` など）に手が入るので、
   どのみちエンジン線の変更と直列にするしかない。アプリ側が持つべき知識（何の出来事が要るか・誰に何を伏せるか）は仕様書で渡せる
5. **git**: いまの制約のままでは、並行作業の道具としては使わない。マスターの手動プッシュ（控え）は従来どおり。
   device_bash か Claude Code が使えるようになったら、ブランチで分けるのではなく、`git status`／`git diff` を**越境の検出**に、
   便ごとのコミット（メッセージに `[APP]`／`[ENG]`）を**記録**に使う設計へ見直す。OneDrive 上での worktree は引き続き推さない（未検証）
6. **食い違いの検出**: `LANES.md` §0 と §9。(a) 各持ち場が台帳類の「最後に書いたときのサイズとハッシュ」を控えに残し、チャットの始めに実物と比べる
   ——相手の越境も OneDrive の巻き戻しも同じ検査で見つかる。(b) 始めに相手の送り箱を読み、自分の台帳から参照されていない項目を挙げる。
   (c) 書き戻すたびに再ステージして比べる
7. **PC の時間**: §3 の 5。アプリの検査は純 Python なのでクラウドの作業環境で回し、PC を使うのは Windows 固有のものだけにする。
   エンジンの全検査（約 3 時間）と重なる依頼をアプリが出すのは M5（実行ファイルを固める）と総合テストの時期だけになる見込み

### 「そもそも 2 つに分けるのが得か」（叩き台 §3.2 の自問）

得である。アプリの線がエンジンの持ち場に触れるのは M1 の 1 回と、測定の依頼（SD02 の強さ 3 段階）くらいで、
残りは `engine/app/` の中で閉じる。摩擦は共有の台帳に集中していたので、そこを分ければ並行の利点だけが残る。
単一書き手を「全ファイルについて片方だけが書く」形にする案（叩き台 §3.2）は、アプリ側の記録がすべてマスターの橋渡し待ちになるので採らなかった。
「ファイルごとに書き手を 1 つ」にすれば、橋渡しが要るのは送り箱を見てもらう一言だけになる。
