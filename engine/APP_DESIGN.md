## v3 での変更点（先に要約）

## 0. 全体像

### 0.1 何を作るか

マスターが CPU と対戦できるアプリ。**遊ぶための製品ではなく、AI とルール実装の
欠陥を見つけるための計測器**である。目的（v2 で順序を変更）:

1. **AI の挙動に変なところがないか（改善できるところはないか）** ← 主目的
2. **対戦システム（ルール実装）におかしなところがないか** ← 主目的
3. AI の強さが人間に比べてどれくらいか ← 従（1・2 の副産物として得る）

### 0.2 作業の流れ（v3 で明確化）

```
  ①対局する            ②振り返る（全情報）        ③裁定する（機械）
  ┌──────────┐        ┌────────────────┐      ┌──────────────┐
  │ 相手の手札 │        │ 相手の手札が    │      │ その局面から  │
  │ は見えない │  ──→  │ 全部見える      │ ──→ │ 2つの未来を   │
  │            │  記録  │ 山札の順序も    │ 指摘 │ 200回ずつ走らせ│
  │ 明らかに変 │        │ AIの思考も      │      │ 勝率を比べる  │
  │ な手だけ指摘│        │ **ここが指摘の主戦場** │ → 勝率差と区間│
  └──────────┘        └────────────────┘      └──────────────┘
     集中して打つ          腰を据えて調べる          放っておけば終わる
```

**①は軽く、②が本番、③は機械が勝手にやる。** この分担が v3 の骨格である。

### 0.3 どう動くか

```
  マスターのPC
  ┌─────────────────────────────────────────────┐
  │  python3 -m webapp.server  で起動           │
  │  ┌───────────────┐        ┌───────────────┐ │
  │  │ ブラウザ       │ ←HTTP→ │ Python サーバ  │ │
  │  │（表示と入力）  │  JSON  │  ┌──────────┐ │ │
  │  │ ルールを持たない│        │  │ meicho   │ │ │
  │  └───────────────┘        │  │ エンジン  │ │ │
  │                           │  └──────────┘ │ │
  └─────────────────────────────────────────────┘
```

起動後 `http://127.0.0.1:8765` を開く。外部には一切公開しない
（カードテキストを画面に出すため、非公開はプロジェクト制約でもある）。

### 0.4 この設計の一番の勘所

**ブラウザ側にルールを一行も書かない。**

「今どんな手が指せるか」はブラウザが判断せず、**実エンジンの `legal_actions()` が
返した一覧をそのまま並べる**。「その手を指すとどうなるか」も `apply()` が決める。

もしブラウザ側でルールを書き直したら、見つけた不具合が「アプリのバグ」なのか
「エンジンのバグ」なのか判別できない。**ルールの真実源が 2 つに割れてはならない。**

## 1. 主目的は「欠陥の発見」である

### 1.1 悪手の指摘は「標本」ではなく「存在証明」

- 「このAIは平均してどれくらい強いか」は分布についての問いなので、
  多数の対局と信頼区間が要る。
- 「このAIはこの局面でこの明らかな悪手を指した」は、**1回観測すれば確定する事実**。
  信頼区間は要らない。反例が1つ挙がれば、そこに直すべきものがある。

主目的の 1・2 は後者である。**少数の対局で十分に成果が出る。**

### 1.2 統計が高価になるのは「僅差のとき」だけ

| 実際の勝敗 | 95% 信頼区間 | 言えること |
|---|---|---|
| 8戦8勝 | 約 [0.63, 1.00] | **人間の方が強い、と言い切れる** |
| 15戦12勝 (0.80) | 約 [0.60, 1.00] | **人間の方が強い、と言い切れる** |
| 30戦17勝 (0.57) | 約 [0.39, 0.75] | 差があるとは言えない |
| 100戦57勝 (0.57) | 約 [0.47, 0.67] | まだ言い切れない |

差が大きいほど少ない対局数で決着する。100 局が要るのは拮抗している場合だけ。

### 1.3 事前予測を記録する

マスターは着手前に「おそらく今の AI はかなり弱いと思う」と述べた。
**これを対局前に記録として残す。** 結果を見てから「やはりそう思っていた」と言うのは
容易だが、それでは予測の当否が検証できない。先に書いておけば、
当たっても外れてもそれ自体が情報になる。

## 2. 設計の根幹

### 2.1 実エンジンをそのまま使う

サーバは `meicho` をそのまま `import` する。**アプリのためにエンジンを変更しない。**
唯一の例外候補は「AI の思考を取り出すフック」だが、**AI の選ぶ手を変えない**形で入れ、
`bench_agents.py` の fingerprint が変わらないことを確認する。変わったら設計をやり直す。

### 2.2 対局中の画面は `observe(s, 人間の席)` だけから作る

サーバがブラウザに送る盤面情報は **`engine.observe()` の出力そのもの**とする。
「その席のプレイヤーに見えてよい情報」の定義そのものである（D-026 / D-036）。

1. **人間も覗き見ができない。** 相手の手札も山札の順序も、ブラウザに送られない。
2. **人間と AI が同じ情報で戦う。**
3. **`observe()` の完全性検査になる。** プレイに必要な情報が無ければエンジンの穴である。

**この制限がかかるのは対局中だけである。** 対局が終われば全情報を開示する（§5）。

### 2.3 同時提出（対抗ステップ）の扱い

1. 人間の選択を受け取る（**まだ apply しない**）
2. **同じ局面 `s`** を AI に渡して手を聞く
3. 両方揃えて 1 回の `apply` で解決する

AI が見る `s` に人間の提出は入っていない。**構造的に覗けない。**（テストで固定・§7.2）

### 2.4 人間と AI の公平性 — v1 の記述の訂正

> **【訂正】** v1 で「人間だけ選べるようにすると人間と AI が別のゲームをすることになる」
> と書いたが、**これは事実誤認だった。**

D-004 の「自動化」は **A-1〜A-7 として 2026-08-21 に全件解消済み**
（D-022 / D-023、`SIMPLIFICATIONS.md`）。現在それらは `Phase.CHOICE` の正式な選択肢として
`legal_actions()` に現れ、AI も人間も同じ決定に直面する。残る簡略化は B-1
（コスト支払いで協奏エリアのどのカードを使うか）だけで、現行カードでは挙動差が出ない。

**したがって人間と AI は同じルール・同じ選択肢の上で戦う。**

ただし非対称が 1 つ残る。planner はこれらの選択を探索の枝にせず簡易な規則で即決している。
人間はそこをじっくり考えられる。**これは欠陥ではなく発見の機会**であり、
そこで人間が勝つなら「探索の枝を広げる価値がある」という根拠になる。

## 3. 悪手を捕まえて裁定する仕組み

### 3.1 なぜこれが中核か

人間の目には「今のは変だ」と分かる。しかし**「変だ」だけでは直せない**。
「本当に損だったのか」「どれだけ損だったのか」を測って初めて、どこを直すか決まる。

**このプロジェクトにはそれを測る道具がある。** D-039 の対照実験
（同じ局面を複製し、行動を変えた 2 つの未来を両方走らせて勝率を比べる仕組み、
`experiments/measure_action_value.py`）である。

### 3.2 裁定の3通りの結果

| 結果 | 意味 | 次にすること |
|---|---|---|
| マスターの手が有意に良い | **AI の悪手が確定** | 評価関数のどの項が原因かを調べて直す |
| 差が無い | AI の手も悪くなかった | 「変に見えたが等価」。人間の直感の較正になる |
| AI の手が有意に良い | 人間の見落とし | AI の読み筋を見て、マスター自身の指し手が改善する |

**3 番目も収穫である。** 目的は「マスター自身の対人勝率の向上」なので、
AI に教わることも成果に数える。

### 3.3 悪手の台帳

指摘は `results/blunders.jsonl` に貯まり、集計できる。

```
| 局面 | 対局 | AIの手 | マスターの代替手 | 裁定 | 勝率差 |
| T5 対抗 | g007 | pass | submit(T02) | 確定 | +0.18 [+0.06,+0.29] |
| T3 行動 | g011 | charge(T01) | levelup   | 差なし | +0.02 [−0.05,+0.09] |
```

**同じ種類の悪手が繰り返し出るなら、それは評価関数の系統的な欠陥である。**
台帳がその繰り返しを可視化する。

### 4.2 操作しやすさ

| 施策 | 中身 | なぜ |
|---|---|---|
| **数字キーで選ぶ** | 行動一覧に番号。キーを押すだけ | 1 局に 50〜100 回の入力。マウスだけだと疲れて集中が落ちる |
| **クリックでも選べる** | 同じ行動をボタンとしても置く | 慣れないうちはこちらが早い |
| **手札クリック → 行動を絞り込む** | T04 を選ぶ → T04 に関する行動だけ残る | カード起点で考えるのが自然 |
| **確認は取り返しのつかない行動だけ** | ターン終了・投了・対抗へ進む | 全部に出すと邪魔になる |
| **合法手が1つなら自動で進む** | 押させない（ログには残す） | 意味のない操作を減らす |
| **キーボードだけで1局打てる** | 上記の帰結 | 数十局打つときに効く |

### 4.3 分かりやすさ

| 施策 | 中身 | なぜ |
|---|---|---|
| **カードは常に全情報を表示** | 色・コスト・速度・ダメージ・スキルを常時表示 | 隠れていると判断に手数がかかる |
| **使えないカードは理由を出す** | 「コスト3 > 協奏2」「リーダーが漂泊者（男）でない」 | 操作の助けであり、**同時にルール実装の検証**。理由が違えばエンジンのバグ |
| **変化した数値を強調** | ライフ 17 ▼3、手札 5 ▲2 | 何が起きたか一目で分かる |
| **対抗の結果を判定根拠つきで** | 「青は赤に勝つ」「速度 3 > 2」「同値なのでターンプレイヤー」 | §6.4(2) のどの規則で決まったかが見える。**間違っていればルール実装のバグ** |
| **継続効果を常時表示** | 旋風のコスト+1、連撃禁止、切り替え禁止 | D-036 で観測に足した情報。見えないと不可解に見える |
| **1ターン1回の使用済みを表示** | チャージ☑ 切替□ Lv□ | 「なぜチャージできないか」が即分かる |
| **選択は理由つきで出す** | 「レベルアップ Lv2 のコストとして手札を2枚捨てる（1枚目）」 | 何のための選択か分からないと判断できない |

| **カードIDも併記** | `SD001-T07 旋風` | 記録と画面を突き合わせるとき ID がないと追えない |

### 4.4 対局中は「気になる」を押すだけでよい

対局中の指摘は**1クリック**で終わらせる。対局は止まらない。
**深く考えるのは §5 のレビューで行う。**

対局中に見えるのは表面的な挙動だけである。「明らかにおかしい」ものだけ拾い、
それ以外は見送ってよい。**レビューで拾い直せる。**

### 4.5 対局中に見せてはいけないもの

- 相手の手札の中身（枚数のみ）／両者の山札の順序と中身
- 対抗ステップで相手が提出したカード（**公開前**）
- AI の思考のうち、上記に触れる部分

§2.2 の設計により上 2 つはブラウザに送られない。AI の思考表示だけは注意が要る
（AI は決定化＝仮の相手手札を仮定して読む）。
**対局中の思考表示では候補の手と点数だけを出し、読み筋の局面は出さない。**

## 5. 対局後レビュー（全情報）— **v3 の中核**

### 5.1 なぜ全情報が要るか

マスターの指摘のとおり、**対局中に判断できる「変な挙動」は表面的なものに限られる**。

対局中には分かるもの:
- 使えるカードがあるのにパスした
- 明らかに得なチャージをしなかった
- ライフを削り切れる場面で削らなかった

**対局中には分からないもの（こちらの方が多い）:**
- 相手が強い札を持っていたのに、それを警戒しない手を選んだ
- 相手の手札が尽きていたのに、無駄に守りに入った
- 相手が出せる色が限られていたのに、それを読まずに不利な色を出した
- 「良い手に見えた手」が、実は相手の持ち札を考えると悪手だった

**後者を拾えなければ、検証としては浅いところで止まる。**

### 5.2 全情報はどこから来るか

**記録し直すのではなく、記録から再生して復元する。**

対局の記録は「シード＋全行動列」を持っている（§6.1）。エンジンは決定的なので、
同じシードから同じ行動を順に適用すれば、**すべての局面が完全に再現される**。
両者の手札も、山札の順序も、そこから読み取れる。

なぜ手札を直接保存しないか。保存すると**同じ事実が 2 か所に書かれ、食い違いうる**。
再生で導出すれば真実源は 1 つのままである。そして §7.1 の再生テストが、
その再生が正しいことを機械的に保証する。

**注意**: 記録には `rules_version` と `engine_version` を持たせる。
将来ルールやエンジンが変わったとき、古い記録は再生できなくなる可能性がある。
**版が食い違う記録をレビューしようとしたら警告を出す**（黙って違う盤面を見せない）。

### 5.3 レビューで見えるもの

| 見えるもの | なぜ要るか |
|---|---|
| **両者の手札**（全ターン） | 「相手の持ち札を考えるとこの手は変」を判断できる |
| **両者の山札の順序** | 「その賭けは正しかったが引きが悪かった」と「そもそも悪手」を切り分けられる |
| **AI の思考**（候補と点数、評価の内訳） | なぜその手を選んだかが分かる |
| **AI が仮定した相手の手札** ← 重要 | 下記 |
| **自分の手の再検討** | 「自分はここでこう指すべきだった」も記録できる |

**「AI が仮定した相手の手札」を見せることが、診断上とくに重要である。**

AI は相手の手札が見えないので、未公開のカードから**当てずっぽうで仮定を立てて**読む
（決定化。`GLOSSARY.md` 参照）。したがって AI の悪手には 2 種類ある。

| 種類 | 中身 | 直し方 |
|---|---|---|
| **仮定は妥当だったが、外れた** | 相手の手札の推測が現実と違っただけ。読み自体は正しい | **直すところは無い**（運。ただし推測の精度を上げる余地はある） |
| **仮定が当たっていても悪手** | 相手の手札を正しく知っていても、その手は損 | **評価関数か探索の欠陥。ここを直す** |

**この 2 つを混同すると、直す必要のないものを直そうとしてしまう。**
仮定と現実を並べて表示すれば、その場で切り分けられる。

### 5.4 後知恵の罠と、その扱い（重要）

全情報を見ると**あらゆる手が「読めたはず」に見える**。これは人間の認知の癖であり、
避けられない。相手の手札を知ってから見れば、不確実性の下では正しかった手も
愚かに見える。

**ただし、この罠はこの設計では実害にならない。理由は 2 つある。**

1. **人間は後知恵で気づいてよい。** レビューの役割は「怪しい局面を見つけること」で
   あって「有罪を宣告すること」ではない。見つける段階では見落としの方が有害である。
2. **裁定する側は後知恵にならない。** D-039 の対照実験は、その局面から
   **AI に決定化をやり直させて**両方の未来を走らせる。
   つまり**AI は再び相手の手札を知らない状態で指す**。
   したがって測っているのは「不確実性の下でのその手の価値」であり、
   後知恵は入らない。

**人間が後知恵で疑い、機械が後知恵抜きで裁く。** この分担が成立している。

なお、レビュー画面には**「対局中に見えていたもの」に戻すボタン**も置く。
「当時の情報だけならどう見えるか」を確かめられるようにするためである。

### 5.5 怪しい局面の自動抽出

1 局は 50〜100 手ある。**全部を人が見るのは現実的でない。**
機械が先に候補を拾い、印を付けて並べる。

| 拾う条件 | なぜ怪しいか |
|---|---|
| **AI の上位2候補の点数が僅差** | AI 自身が迷った局面。評価関数の粗が出やすい |
| **AI の評価が急に振れた** | 直前に想定外のことが起きた。読み抜けの疑い |
| **手札に「相手の提出に色で勝てる札」があったのに、負ける色を出した** | 全情報でのみ検出できる典型的な候補（後述） |
| **手札に使える札があったのにパスした** | 対局中にも見えるが、機械なら見落とさない |
| **ライフを削り切れたのに削らなかった** | 決着を逃した疑い |
| **人間の手の直後に AI の評価が大きく動いた** | マスター自身の好手・悪手の候補 |

**「色で勝てる札があったのに負ける色を出した」は、全情報があって初めて機械が
検出できる**。ただしこれは**候補であって判定ではない**——コストが払えなかったり、
その札を温存する価値があったりする。だから拾い上げるだけにして、
損得の判断は §3 の裁定に回す。

**自動抽出は「見るべき順番」を作るだけで、人の判断を置き換えない。**
拾われなかった局面も自由に見られる。

### 5.6 レビューの操作

```
┌────────────────────────────────────────────────────────────────┐
│ 対局 g007  マスター(先攻) vs 計画探索  結果: マスターの勝ち 14T   │
│ [◀◀最初] [◀1手] 手 27/86  ターン5 対抗ステップ [1手▶] [最後▶▶]│
│ [怪しい局面へ ▼ 6件]   表示: (●)全情報  ( )対局中に見えていたもの │
├────────────────────────────────────────────────────────────────┤
│ CPU の手札 ← **全情報表示**                                     │
│   T02 迅雷(赤/1/2)  T05 静寂(青/3/4)  T01 疾走(赤/1/2)          │
│ CPU の山札（上から）: T04, T06, T03, …                          │
│ あなたの手札: T07 旋風(赤/3/2)  T04 奏鳴(緑/2/1) …              │
├────────────────────────────────────────────────────────────────┤
│ この手: CPU が pass を選択                                       │
│                                                                │
│ AI の思考:  pass +1.20 ★選択 /  submit(T02) +1.14               │
│   → 上位2候補が僅差（0.06）。**自動抽出で拾われた局面**          │
│                                                                │
│ AI が仮定した相手（あなた）の手札:                               │
│   [仮定1] T01, T03, T06 …   [仮定2] T02, T05, T07 …             │
│   **実際のあなたの手札: T07, T04, T01, T05, T02**               │
│   → 4回の仮定のうち、T07 を含むものは 1 回だけだった            │
├────────────────────────────────────────────────────────────────┤
│ [この手を指摘する]  代替手: [submit(T02) ▼]  メモ: [__________] │
└────────────────────────────────────────────────────────────────┘
```

- **1手ずつ進む・戻る**、ターン単位で飛ぶ、怪しい局面だけを順に辿る
- **全情報 ⇄ 対局中の視点**を切り替えられる（§5.4）
- **どの局面でも指摘を追加できる**（対局中に見落としても後から拾える）
- 指摘には**代替手**（「本当はこう指すべきだった」）と**メモ**を付けられる
- 代替手を指定しなければ、裁定では「AI が 2 番目に高く評価した手」を対抗馬にする
- **自分の手にも指摘できる**（マスター自身の上達に使う）

### 5.7 安全装置 — 対局中に全情報が漏れないこと

**全情報を返す API は、対局が終了した記録に対してのみ応答する。**

- 進行中の対局を指す要求には、**理由を付けて拒否する**（黙って空を返さない）
- 対局中の画面が使う API と、レビューが使う API は**別の入口**にする
- 「終了した」の判定は記録側（結果が書かれているか）で行い、
  ブラウザからの申告では判定しない

**テストで固定する**（§7.2）: 進行中の対局に全情報を要求すると拒否されること。
ここが破れると人間が覗き見できてしまい、勝率の比較が無意味になる。

## 6. 記録の設計

### 6.1 何を記録するか

1 局につき 1 レコード。**再現に必要なものを漏れなく持つ。**

```json
{
  "app_version": "1", "rules_version": "v0.10", "engine_version": "v0.1",
  "played_at": "2026-08-24T21:30:00+09:00",
  "game_id": "g007",
  "seed": 130007, "deck": "SD001", "mode": "mirror",
  "human_seat": 0,
  "opponent": {"factory": "planner", "kwargs": {}, "seed": 260014},
  "show_ai_thinking": false,
  "actions": [{"ply": 0, "turn": 0, "phase": "setup_chara",
               "by": "human", "action": {...}, "ms": 4200}, ...],
  "ai_thinking": [{"ply": 14, "candidates": [...], "chosen": {...},
                   "assumed_opponent_hands": [[...], [...]]}],
  "flags": [{"ply": 27, "target": "ai", "when": "review",
             "note": "…", "alternative": {"type": "submit", "hand": 2}}],
  "result": {"winner": "human", "turns": 14, "life": [6, 0],
             "aborted": false, "draw": false}
}
```

- `flags` の `when` は `"live"`（対局中）か `"review"`（レビュー中）。
  **後知恵で付けた指摘かどうかを区別できるようにする**（§5.4）。
- `assumed_opponent_hands` は AI が決定化で仮定した相手の手札（§5.3）。
  これは AI 自身が作った仮定であって実際の手札ではないので、
  **対局中の画面には出さない**（§4.5）。

保存先は `results/human_games/YYYY-MM.jsonl`（月ごとに追記）。
指摘は `results/blunders.jsonl` にも集約する。

### 6.2 記録が正しいことをどう保証するか

**記録した対局を再生して、同じ結果にならなければ落ちるテストを置く。**

記録の `actions` を順に返すだけの「再生エージェント」を作り、同じシード・同じ設定で
`play_game` を回す。勝敗・ターン数・最終ライフが一致しなければ失敗。

これが通れば同時に保証されること:

- 記録に漏れがない（漏れていたら再生できない）
- エンジンが決定的である（作業規約6 / D-006）
- **アプリがエンジンを迂回していない**（迂回していたら食い違う）
- **§5 のレビューが正しい盤面を見せている**（レビューは同じ再生を使う）

## 7. 検査（テスト）

作業規約5（テスト先行・現在 141 件を下回らない）に従う。

### 7.1 記録と再生
- 記録した対局を再生すると勝敗・ターン数・ライフが一致する
- 記録が壊れている場合は明確に失敗する
- **再生した局面列が、レビューが表示する局面列と一致する**

### 7.2 公平性・情報の遮断
- **AI の手が人間の提出内容に依存しないこと**（同じ局面で人間の提出だけ変えて確認）
- **対局中にブラウザへ送る盤面に隠蔽情報が含まれないこと**
- **進行中の対局に全情報 API を要求すると拒否されること**（§5.7）
- **`assumed_opponent_hands` が対局中の応答に含まれないこと**

### 7.3 入力の健全性
- サーバは合法手一覧に無い手を拒否する
- どの局面でも人間側に必ず 1 つ以上の合法手がある（詰まらない）

### 7.4 「使えない理由」の表示が正しいこと
- 「使用不可」と表示したカードが本当に `legal_actions` に無いこと／その逆
- 表示した理由が実際の判定理由と一致すること（コスト不足／リーダー条件）

### 7.5 自動抽出が正しく拾うこと
- 仕込んだ局面（色で勝てる札を持ちながら負ける色を出す等）を確実に拾う
- 拾った件数が現実的な範囲に収まる（全手が「怪しい」になると使い物にならない）

### 7.6 エンジンを変えていないこと
- AI の思考フックを入れた状態で `bench_agents.py` の fingerprint 3 種が従来と一致

## 8. 強さの測定（従）

### 8.1 主目的ではない
勝率と信頼区間は常に表示するが、「何局打つべきか」をマスターに課さない。
**打った分だけ表示する。**

### 8.2 相手は最初から現 champion（計画探索）
マスターが「AI はかなり弱い」と予想している以上、最初から一番強い相手と戦うのが最短。
予想どおり圧勝するなら 10 局程度で決着し、以後は §3・§5 の悪手収集に全振りする。
相手は設定で切り替え可能（H_default / 貪欲 / 計画探索 / IS-MCTS）。**既定は計画探索。**

### 8.3 測定を歪めないための最小限の約束
- **強さを数える対局では AI の思考表示を隠す**（記録で区別し集計を分けられる）
- **対局中のやり直しは付けない**（振り返りは §5 で行う）
- **席（先攻・後攻）は自動で交互に入れ替える**
- シードは新しい帯（`next_free` は現在 **130000**）から取り、台帳に登録する

## 9. 作らないもの（スコープ外）

- **装飾**（カード画像・アニメーション・凝った配色）。
  ただし**分かりやすさのための表示は §4・§5 のとおり作り込む**。
- **人間 vs 人間**、オンライン対戦、公開サーバ。localhost のみ。
- **デッキ構築 UI**。SD001 同型戦を既定とし、SD02 は設定で切り替えるだけ。
- **スマートフォン対応**。PC のブラウザのみ。
- **エンジン・ルールの変更**。アプリは観測者である。
- **対局中のやり直し**（§5 のレビューで代替）。
- **レビューからの分岐対局**（「この局面から指し直して遊ぶ」）。
  裁定（§3）が同じ目的をより正確に果たすため。要望があれば後で検討する。

## 11. 実装の段取り

### 段階1: 対局が最後まで進む（骨格）
- サーバとセッション管理、`observe()` API、合法手 API、行動 API
- 最小限の画面（盤面・合法手のボタン・日本語ログ）
- **数字キー操作**と**カードの全情報表示**はここから（後付けだと作り直しになる）
- 記録の書き出し／**再生テスト**（§5 の土台でもある）
- **[気になる] ボタン**（記録するだけ）

→ **ここで 1 局打ってもらい、操作感と「弱いかどうか」の第一印象を聞く。**

### 段階2: 対局後レビュー（v3 で優先度を上げた）
- 記録の再生と、**全情報での局面表示**（両者の手札・山札の順序）
- 1手送り／戻し、ターン移動、全情報⇄対局中視点の切り替え
- **AI の思考と、AI が仮定した相手の手札**の表示
- **レビュー中の指摘追加**（代替手・メモ）
- 安全装置（進行中の対局には全情報を出さない）とそのテスト

→ **段階2 が終われば、マスターの指摘のとおりの検証ができるようになる。**

### 段階3: 分かりやすさの作り込みと自動抽出
- §4.3 の全項目（使えない理由・差分強調・判定根拠・継続効果・選択の説明）
- **怪しい局面の自動抽出**（§5.5）
- 対局中の AI 思考表示＋隠すボタン

### 段階4: 裁定と台帳
- 指摘 → 対照実験（D-039）の起動と結果の記録
- 悪手の台帳と集計
- 勝率・信頼区間・推定 Elo の表示

**v2 からの順序変更**: レビューを段階3 → **段階2** に繰り上げ、
分かりやすさの作り込みを段階2 → 段階3 に下げた。
**指摘の主戦場がレビューである以上、そちらを先に通すべきだからである。**
