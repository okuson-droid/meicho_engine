   **以後「書き戻す前に PC の末尾を見る」決まりを `CLAUDE.md` に置いたが、人の注意に頼る形のままである。**
2. **書き戻したファイルが PC に載っていない（OneDrive）。**更新日時だけ進んで中身が古い。
   D-084 で 2 回、D-091 で 1 回（再ビルドの結果が 1 ビットも変わらず発覚）、2026-09-19 にも `TASKS.md` で 1 回。
   `device_commit_files` が「written」を返しても信じられない。**書き戻したら再ステージしてサイズか中身で確かめる**のが現行の対策
3. **台帳の取り残し。**D-090 の判断が要る点 J-1〜J-6 は「次の引継ぎ書 §0.3 で閉じる」とされたが、
   次の引継ぎ書が別系統（公式ルール線）だったので閉じられず、台帳から落ちかけた（`TASKS.md` の J-1〜J-6 の項の注記）。
   **系統が並ぶと「次の引継ぎ書」がどれかが曖昧になる。**
4. **検査の共有状態。**全検査が緑でも、名指しで回すと落ちる検査があった（検査どうしが import の副作用で支え合っていた・D-105）。

5. **指紋は打ち方を変えなくても動く**（決定列に選択が増えるだけ・ルールが変わるだけで動く・D-091 §3／D-104）。
   アプリの M1 が `engine.py` に出来事の記録を足すとき、**既定で切っていても指紋が動かないとは限らない**。
   確かめるには PC で `check_champion_fingerprint.py` と pytest の 14 節点を回す必要がある

### 3.1 クロエが採らなかった案と理由

- **git のブランチ／worktree で分ける案 → 推さなかった。**理由: (a) チャットから git を叩けない（§1.2）、
  (b) OneDrive の上で worktree を使うと同期で壊れやすい。**(b) はクロエの判断であり、この PC で試したわけではない。**
  ただし **PC で Claude Code（コマンドラインで動く版）を使う、または device_bash が使えるようになるなら前提が変わる**ので、
  そのときは再検討の余地がある。この比較もレビューしてほしい

### 3.2 クロエ自身が疑っている点

- 叩き台は**事故の再発防止を積み上げただけ**で、「そもそも 2 チャットに分けるのが得か」「分けるならどこで切るのが最小の摩擦か」を
  考えていない。たとえば「共有ファイルは片方のチャットしか書かない（もう片方は連絡帳に書いて、書く側が転記する）」という
  **単一書き手**の方式のほうが、ロックや範囲予約より単純かもしれない。比較してほしい
- 札（ロック）はチャットが途中で終わると外れないまま残る。**札の期限や、外し忘れの検出**を考えていない
- マスターの手数（モバイルでの橋渡し）を数えていない
