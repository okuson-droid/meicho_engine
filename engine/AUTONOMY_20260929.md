## 2. 採点役（reviewer）

### 2.1 何が効くか

参考資料まとめの言葉で「効くのは上位モデルであることより、まっさらな文脈で、編集権限を持たずに、diff と基準だけを見て採点すること」。D-142 の点検（1・2 回目とも重大な指摘なし）はこの形に近いが、**モデルの格が条件になっていて、編集権限の有無は決めていなかった**。ここで決める。

### 2.2 定義（`engine/autonomy/agents/reviewer.md` → `.claude/agents/reviewer.md`）

- 道具: **Read・Grep・Glob・Bash だけ**。Write・Edit は持たない（Bash で検査を回すことはできるが、ファイルを書く命令は禁じる）
- 入力: 区切りの diff（`git diff <前の区切り>..HEAD`）と、その便の設計書の「判定の規則」節・報告書
- 出力: **1 行目に `PASS` か `NEEDS_WORK`**、続けて指摘を番号つきで。指摘は**正しさと要件に効くものだけ**（設計書の規則と実装が食い違う・数字の写し間違い・帯の未登録・検査の無効化）。文体・抽象化・防御的な書き方の提案は出さない（参考資料まとめ「全指摘を拾うと過剰な抽象化や防御的コードが増える」）
- この計画に固有の基準（雛形に書き込んだ）:
  1. 判定の規則が、結果を見る前に固定されていたか（設計書の該当節が diff より前の commit にあるか）
  2. 使った帯が `seed_bands.json` に登録済みで、`kind` が用途（train／validate／diag）と合うか。学習に使った帯で評価していないか
  3. 数字は区間つきで写されているか（勝率だけの「勝った」は NEEDS_WORK）
  4. 報告書に「実行したコマンドと出力の在り処」があるか（宣言だけは NEEDS_WORK）
  5. 検査を skip・xfail・削除で黙らせていないか。`--run-slow` を回した便か
  6. 台帳（TASKS.md・decisions.md）の数字が報告書と一致するか。D-番号が末尾の続きか
  7. 脱線の兆候 4 つ（§5）のどれかが diff に見えないか
- モデル: 定義では指定しない（`inherit`）。上位モデルを当てるかは §9-1

### 2.3 使い方

- **いつ**: D-142 と同じ「区切りごと」。区切り＝設計書の段が 1 つ済んだとき・便の報告書を書いたとき・PR を `main` に入れる前
- **NEEDS_WORK** が出たら、作った側は指摘を直して**もう 1 回だけ**採点役を呼ぶ。2 回目も NEEDS_WORK なら止めて STEER.md か台帳に書き、マスターの裁定を待つ（同じ問題で 2 回直しても外れたら人に返す・参考資料まとめの `/clear` の話と同じ向き）
- **PASS** は「進んでよい」であって「正しい」ではない。台帳の照合（`verify_report.py`）は別に回す
- 採点役の出力は報告書の末尾に**そのまま**貼る（要約しない）。マスターは昼か夜にそこだけ読めばよい

## 4. セッション開始の定型（Claude Code・エンジンの持ち場）

毎回この順で。飛ばさない。**7 行目までは何も書かない・回さない**。

1. `git pull` → `STEER.md` を読む。`AGENT_STOP` が在れば §3.2 のとおり終える
2. `TASKS.md` の Active の先頭 1 件を読む（未着手はここが一元管理・`CLAUDE.md`）
3. `git log --oneline -5` で、前のセッションが何を commit したかを見る。台帳と食い違えば台帳に合わせて直す前に止めて書く
4. その作業の設計書を開き、**「判定の規則」と「判断が要る点」の節だけ**を読む。裁定済みでない判断があれば着手しない
5. 使う帯を `seed_bands.json` で確かめる（登録済みか・`kind` が用途と合うか・`next_free`）
6. 検査を回す（作業環境は既定の組・PC は `--pc`）。落ちていれば直す前に台帳に書く
7. **未完了のものを 1 つだけ**着手する。塊は 10 分以内・塊ごとに push（D-137）

## 5. 脱線の兆候（4 つ）

見つけたら**直さずに止める**。台帳の Waiting On に 1 行と、報告書に「兆候 n を見た」と書き、マスターの裁定を待つ。

1. **同じことの繰り返し** — 同じ検査を 3 回以上同じ直し方で通そうとしている
2. **頼んでいない機能** — 設計書に無い引数・口・欄を足している（「ついでに」は全部これ）
3. **検査の無効化・削除** — skip・xfail・`--run-slow` の省略・落ちる検査の書き換え（`CLAUDE.md` 罠「skip は通ったではない」）
4. **シード帯・測定条件の無断変更**（この計画に固有・参考資料まとめの提案） — 登録していない帯を使う・局数を減らす・対照を省く・判定の規則を結果を見てから変える・学習に使った帯で評価する（`measurement_discipline` の各ルール）

## 6. 完了判定の機械化（Stop hook・まず測定の便だけ）

### 6.1 なぜ測定の便から

「終わった」の判断が報告と目視に依存していて、無人ではここが最初に崩れる（参考資料まとめ）。測定の便は完了の条件が**すでに文書で決まっている**（帯の登録・判定の規則・報告書・照合）ので、機械に写しやすい。実装の便（コードを変える便）は完了条件が便ごとに違うので 2 回目。

### 6.2 検査の中身（`engine/scripts/check_done.py`・PC の Claude Code が実装）

引数なしで回し、**通らなければ非ゼロで終わり、理由を 1 行ずつ出す**。Stop hook はこれを呼ぶだけ。

- (a) `git status --porcelain` が空。`git rev-parse @{u}` と `HEAD` が一致（push 済み）
- (b) 直近の commit で増えた `results/**/manifest*.json`（と `*_report.json`）の `seed0`〜`seed0+n−1` が `seed_bands.json` のどの帯に入るかを見て、**登録済み**で、帯の `kind` が manifest の用途と合う。学習の帯（`train`）で評価の結果を出していない
- (c) 直近の commit で増えた `engine/*_2026*.md`（報告書）に、**区間つきの数字**（`[…, …]` か `±`）と、**実行したコマンドの行**（```` ``` ```` の中に `python` か `eval_` か `record_`）がある
- (d) 報告書の末尾に採点役の出力（`PASS` か `NEEDS_WORK` で始まる節）がある。`NEEDS_WORK` のままなら通さない
- (e) `pytest` の結果ファイル（`--junitxml` を毎便 `results/ci/last.xml` に出す運用にする）で、**skip の件数が既定の組の値（`scripts/make_test_sets.py` の組）を超えていない**（黙らせた検査を見つける）
- (f) `TASKS.md` の Active の先頭の項目に、今日の日付の追記がある（台帳を書き忘れていない）

何もしないとき（測定の便でない・`results/` に変更が無い）は (a)・(f) だけを見て通す。

### 6.3 配線（PC の Claude Code）

- `.claude/settings.json` の `hooks` の `Stop` に `python engine/scripts/check_done.py` を登録する。書き方は公式の hooks の説明（`code.claude.com/docs/ja/hooks`）を**その場で読んで**合わせる（クロエは正確な JSON の形を確かめていない・§10）
- hook が落ちたときのメッセージは check_done.py の出力そのまま。Claude Code はそれを見て直すか、直せなければ STEER.md を読み直して止まる
- 最初の 1 便は**hook を入れずに check_done.py を手で回して**、通ることを確かめてから hook にする（hook が間違っていると永遠に終われない）
