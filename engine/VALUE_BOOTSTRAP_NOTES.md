## 1. 何が動くようになったか

### 1.1 計画探索に 2 つのつまみが付いた（`meicho/planner.py`）

```python
PlannerAgent(seed, ..., extra_turns=0, value_net=None)
```

- `extra_turns=1` — 探索が「ここで採点する」と決める地点を、**自分のターンの終わり**から
  **次に自分の手番が始まるところ**まで延ばす（設計書の裁定 1）。相手のターンを 1 つ通してから
  採点するので、【ターン開始時】に働く効果が 1 回だけ見えるようになる。
  これは D-046 で「対策 A」と呼んでいたもので、実装は `measure_horizon.py` にあった
  `LongHorizonPlanner` をここへ移した。**同じ打ち切り条件が 2 か所にあると必ず食い違う**ので、
  `LongHorizonPlanner` は `PlannerAgent(extra_turns=1)` を呼ぶだけの別名に畳んだ。
- `value_net="..."` — 採点そのものを、学習した価値ネット（局面を入れると勝つ確率が出てくる
  ニューラルネット）に差し替える。**この輪の主役**である。

どちらも既定は「無効」であり、指定しなければ一手も変わらない（§0 のフィンガープリント）。

### 1.2 反復 k のエージェントの定義が 1 か所になった（`experiments/vb.py`・新設）

`champion.py` と同じ役割分担である。「反復 k のループのエージェントとは何か」を
1 か所に閉じ込め、記録・学習・評価・登録簿がすべてここを読む。定義が散らばると
「名前は同じで中身が違う」事故が起きるからである。

```
反復 k のエージェント = planner(extra_turns=1, value_net=V_{k-1}, opp_policy_net=π₀, 根だけ)
```

`k=1` では V_0 が存在しないので価値ネットを積まない（設計書 §3.5 の「反復 1 では判定しない」の理由）。

**π₀（相手の手を読むためのネット）はここに直接書いてある**。`champion.py` を読んで動的に
決めると、将来 champion が交代したときにこの輪の相手モデルが黙って変わってしまい、
設計書 §3.6 の「π₀ は据え置き」が破れるためである。`champion.py` には触れていない（設計書 §10）。

### 1.3 記録の口が 3 通りになった（`experiments/drl_record.py`）

設計書 §6 の教材レシピ（自己対戦 約 70%／対 H・貪欲 約 20%／δ 介入 約 10%）を、
同じ `--vb` に 3 通りの付け方をして作る。

```bat
rem 自己対戦（ミラー・両席を記録）— 主食
python experiments\drl_record.py --deck SD001 --vb 1 --record both --seed0 341300 --n 6000 --out results\drl\vb1_train.bin --tau 0.5 --workers 2
rem リーグ局（相手を H に変える・A 席だけ記録）
python experiments\drl_record.py --deck SD001 --vb 1 --spec-b heuristic --record a --seed0 ... --n 1000 --out ...
rem δ 介入局（A 席に「強いる」型を重ねる・A 席だけ記録）
python experiments\drl_record.py --deck SD001 --vb 1 --delta-gens A --record a --seed0 ... --n 750 --out ...
```

**記録する席は必ずループのエージェント側に固定される**（設計書 §6.3）。リーグ局や δ 局で
`--record a` を書き忘れると引数の検査で止まるようにした。これは D-046 証拠 B の
「弱い AI が作った局面から学ぶと符号を逆に覚える」（シンプソンの罠。全体で見た傾向と
グループごとに見た傾向が逆になる現象）を、席を固定することで防ぐためである。

### 1.4 教師の作り方が変わった（`experiments/drl_train.py`）

`--vtarget max`（**新しい既定**）で、V の学習目標に使う探索値を「実際に選んだ手の値」から
**「その決定で探索が付けた値の最大値」**に変えた。局面の価値とは「そこから最善を尽くした
ときの価値」だからであり、また記録時は温度（わざと最善以外も選ばせる仕掛け）を入れるので、
選んだ手の値だと**わざと選んだ悪手の値が教師に混ざる**。最大値なら温度に汚されない。

### 1.5 反復の検証が 1 コマンドになった（`experiments/eval_vb.py`・新設）

門番（新旧の直接対決）・錨 3 種（素の計画探索・H・貪欲に対する勝率を新旧**同じシード**で対にする）・
カナリア（漂泊者 Lv2 到達率・200 局）をまとめて回し、`results/vb/iter<k>.json` に落とす。

`--null` を付けると**同じ版どうしを当てる空回し**になる。0.5 付近に出れば配管は正しい。
実際に回して確認した（下は 60 局の短縮版。本番は 1,200 局）。

```
1. 門番: 新 vs 前の版            0.517 ±0.126 (n=60)  下端 0.390 / 上端 0.643  → 越えない
  vs 素planner   新 0.467 / 前 0.467  差 +0.000 ±0.252
  vs H          新 0.900 / 前 0.900  差 +0.000 ±0.152
  vs 貪欲         新 0.867 / 前 0.867  差 +0.000 ±0.172
```

± の意味は「同じ条件で測り直したら、だいたいこの幅に収まる」である。同じ版どうしなので
本当の値は 0.5 のはずで、0.517 はその幅の内側に収まっている＝配管は正しい。
錨の差がぴったり 0 なのは、同じシードで同じ中身を当てているからである。

## 3. 判断が要る点（7 件）

設計書は「本書に書いていない設計判断が必要になったら、推測で補完せず、判断が要る点として
報告すること」と定めている（設計書の冒頭・作業規約 1）。以下がその 7 件である。
**1 と 2 は裁定が要った。3〜7 は「こう決めて進めた」の報告である。
2026-09-01、マスターが 7 件すべてを承認した**（`decisions.md`「D-064 実装の第 1 便への裁定」）。

### 判断 1【要裁定】終端の点数を ±10000 ではなく 1.0 / 0.0 / 0.5 にした

**何が問題か**: 探索は「もう勝ちが決まっている局面」に出会ったら、それを他のどの局面よりも
高く（負けならどの局面よりも低く）採点しなければならない。そうしないと**勝ちを勝ちと
認識できなくなる**。手作りの評価関数はこれを ±10000 という桁違いの数（番兵）でやっている。

設計書 §3.2 は「終端は必ず ±WIN（10000）の番兵を返す」と書いている。ところが**Rust 側は
すでに 1.0 / 0.0 / 0.5 で実装されていた**（`agents.rs::Greedy::net_value`・段階 0-4 で導入済み）。

**Python をどちらに合わせるかで、次のことが起きる。**

| 選択 | 起きること |
|---|---|
| Rust に合わせる（1.0 / 0.0 / 0.5）**← 採った方** | 価値ネットの出力は 0〜1 の勝率なので、1.0 と 0.0 がそのまま「どの非終端よりも上／下」の役割を果たす。引き分けは 0.5＝「五分」で自然。Python と Rust が一致し、再ビルド以外の追加作業は不要 |
| 設計書どおり ±10000 にする | 引き分けの扱いが Python（0.0＝負けと同じ）と Rust（0.5＝五分）で食い違い、**Python/Rust 一致検査は原理的に通らない**。通すには Rust も直して再ビルドが要る |

**採った理由**は 3 つある。(1) 設計書 §3.2 が本当に求めているのは「終端が支配すること」で、
0〜1 の尺度ではそれを 1.0 / 0.0 が満たす。(2) ±10000 にすると引き分けが「負けと同じ」に
なってしまい、これは実害のある間違いである。(3) Rust 側の既存実装を尊重すれば追加の
再ビルドが要らない。

**マスターの裁定を仰ぐ点**: この解釈でよいか。よければ設計書 §3.2 の文言を
「価値ネットを積んだ葉の終端は 1.0 / 0.0 / 0.5（[0,1] の尺度における番兵）」に直す。

### 判断 2【要裁定】Rust に引数を 1 つ足した（再ビルドが要る）

設計書 §4.2 は「`value_net` の葉差し替えは実装済み」と書いており、実際そのとおりだった——
ただし**対局列をまとめて回す経路（spec 経由）だけ**である。1 手ずつ Python と突き合わせる
検査は `meicho_rs.PlannerAgent` クラスを直接使うので、そちらに `value_net` の口が無かった。

設計書 §8-4 が要求する「`extra_turns=1`＋`value_net` で Python/Rust が同じ手を選ぶ」検査を
成立させるため、`lib.rs` のそのクラスに `value_net=None` を足した。既定値なので挙動は不変。

**マスターの裁定を仰ぐ点**: 再ビルド（§2）をお願いしてよいか。
断る選択肢もあるが、その場合は設計書 §8-4 の検査を落とすことになる——つまり
「Rust で回した記録が Python と同じ AI のものである」という保証が 1 つ無くなる。**勧めない。**

### 判断 3 δ を「1 局につき 1 つ・無作為」ではなく「δ ごとの連なったシード帯」に割った

設計書 §6.1 は「δ は 1 局につき 1 つ・無作為」と書いている。しかし記録を回す Rust の関数は
**1 回の呼び出しにつき 1 つのエージェント定義しか取らない**ので、局ごとに δ を変えるには
呼び出しを分けるしかない。

そこで δ の種類ごとに連なったシード帯へ等分し、1 種類につき 1 本ずつ回すことにした。
SD001 なら δ は 8 種類なので、750 局は 1 種類あたり 93〜94 局になる。

**無作為抽出との違いは、実質的には無い**（どの δ も同じ回数だけ現れる）。むしろ利点があり、
あとから「この局はどの δ だったか」をシードだけで引ける。割り当ては manifest（記録の
お品書きファイル）に全部書いてある。

### 判断 4 δ の選び方を「カード名を書かない判定」で実装した

設計書 §6.1 は「持続効果（【ターン開始時】【常在】系のスキルを持つキャラ・カード）に
関わるものを中心に無作為」と書いている。これを `measure_persistent_feature.py` と**同じ判定**
（タイミングが【ターン開始時】か【常在】／条件が無いか実質いつでも真／任意でない）で実装した。
カード名を 1 つも書いていないので、発売後にカードが増えても書き足す必要が無い（D-047 の考え方）。

SD001 では該当が 2 キャラ（漂泊者（女）Lv2 と 熾霞 Lv2）になり、
「1・4・7 ターン目から急いで Lv2 に」×3 と「リーダーに固定」×1 の**計 8 種**が δ になる。
「禁じる」型（`forbid_levelup`）は入れていない——ここでの目的は
「今の方策が行かない場所へ**行かせる**」ことであって、行き先を減らすことではないからである。

### 判断 5 `--select best_v` の強制範囲を「λ > 0 のとき」にした

設計書 §4.4 は「この輪では `--select best_v` を必須とする」と書いている。しかし
「この輪かどうか」を機械が判定する手がかりが引数に無い。

そこで **`--lam > 0` のとき**（＝探索値を教師に混ぜる＝V をブートストラップする構成のとき）に
`--select best_v` を強制した。λ を使わない従来の学習（方策 π の線）は今までどおり動く。

（`--select best_v` は「学習の途中で検証成績がいちばん良かった回の重みを保存する」指定である。
段階 1 で「価値 V は 1 回目が最良で以降悪化する」と分かっているため、
既定の「最後の回を保存」は V にとって誤りである。）

### 判断 6 シード帯の台帳を 2 本に分け、評価帯での記録を機械が拒むようにした

台帳（`seed_bands.json`）には 340000..409999 が 1 本の帯として登録されていたが、
設計書 §7.6 は中で「記録用（34〜38 万台）」と「評価用（39〜40 万台）」を分けている。
**この区別を人の注意力に任せない**ため、台帳を 2 本に分けた。

| 帯 | 種別 | 用途 |
|---|---|---|
| 340000..389999 | `search` | 記録（反復 1〜5、各 10,000 幅） |
| 390000..409999 | `validate` | 評価・カナリア・検算（反復ごと 4,000 幅） |

あわせて `drl_record.py` が、評価専用の帯（`validate` と `ladder`）や未登録の帯での記録を
**拒む**ようにした。D-058 の SD02 で「記録に使った帯で評価してしまい、0.515 という数字が
約 +0.02 汚染されていた」事故が実際に起きているためである（台帳の 270000.. の注記）。

| 1.0 | **0.292** ±0.036 | 40/200・9.2 ターン |

## 9. 原因の特定 — 較正の目盛りが番兵に食われている

### 9.1 較正とは何をしているか

探索が付ける点数は `greedy.evaluate` の重み付き和であって確率ではない。勝敗が確定している
局面には **±10000 という桁違いの数（番兵）**が入る。この点数をそのまま勝敗 z と混ぜると
教師がでたらめになるので（D-059）、**1 変数のロジスティック変換で勝率 [0,1] に直してから**混ぜる。

その変換は `p = sigmoid(a · clip(v, ±c) / c + b)` という形で、**c は「|v| の 90% 点」**である。
c は「番兵をここで潰す」ために置かれた（D-059 の設計意図）。

### 9.2 何が起きたか

**この輪では番兵が 10% よりずっと多く出る。** 地平を 1 往復延ばしたので、探索の中で
勝敗が決まる筋が頻繁に見えるようになったためである。加えて教師を「探索値の最大値」に
した（`--vtarget max`）ので、なおさら番兵を拾いやすい。

実測（反復 1 の記録・検証側 66,794 決定）:

- `|v| ≥ 9999`（完全な番兵）が **6.6%**
- ±5000・±7502 のような**部分的な番兵**（決定化 4 通りのうち一部で勝敗が決まった平均値）も多く、
  **`|v|` の 90% 点は 5007** になった
- 一方、番兵を除いた探索値の**本体は中央値 3.65・四分位 0.40〜7.26** ——目盛り c の **約 1/1000**

つまり `clip(v, ±5007)/5007` は、**探索値の本体をまとめて 0 の近くに潰している**。
その結果、較正後の教師 p は次のようになった（学習データ 207,188 決定で測定）。

| 目盛り c | 較正後の対数損失 | 「常に平均勝率」との差＝情報量 | 教師 p の分位（5/25/50/75/95%） |
|---|---|---|---|
| **現行 c=5007（\|v\| の 90% 点）** | 0.6705 | **0.0209** | 0.498 / 0.498 / 0.499 / 0.499 / 0.772 |
| c=9.4（本体の 90% 点） | **0.6409** | **0.0506** | 0.212 / 0.426 / 0.543 / 0.685 / 0.711 |
| tanh(v/10) | 0.6411 | 0.0503 | 0.231 / 0.430 / 0.544 / 0.648 / 0.739 |
| 順位（分位）変換 | 0.6417 | 0.0498 | 0.288 / 0.391 / 0.532 / 0.669 / 0.762 |

対数損失は「予測の外し具合」で、低いほど良い。「常に平均勝率と答える」の値からどれだけ
下げられたかが、その変換が持っている情報量である。

**現行の目盛りでは、決定の半分以上（25%〜75% 分位）で教師 p が 0.498〜0.499 の定数になっている。**
つまり教師は事実上こうなっていた。

```
target = (1 − λ)·z + λ·0.499        ← 局面によらない定数
```

これは z を縮めただけの目標であり、**「探索が 1 往復先まで見た知識」は 1 ビットも入っていない**
（入っているのは「探索の中で勝敗が決まったか」という粗い情報だけ）。
設計書 §3.4 の機構——探索値が V_{k-1} の知識の 1 往復先を含み、それを V_k が覚える——は、
**この目盛りでは働きようがない。** λ を上げるほど弱くなった（§8.2）のは、これで説明がつく。
λ を上げるほど「定数の教師」の割合が増え、z の情報が薄まるだけだからである。

目盛りを本体に合わせると、情報量は **0.0209 → 0.0506（2.4 倍）**、教師 p の広がりは
**0.03 → 0.50** になる。ここが直れば設計の機構が初めて動く見込みがある。

### 9.3 これは設計書の想定外である

設計書 §3.3 は「較正は**実装済み**（`drl_train.py::calibrate_vsearch`・D-059）」として、
中身を検討の対象にしていない。D-059 のときは葉が手作り評価・地平が 1 ターンだったので
番兵が 10% を超えず、目盛りは本体に合っていた。**地平を延ばしたこと（裁定 1）と
教師を最大値にしたこと（§3.3）が、揃って番兵の割合を押し上げた**——設計の 2 つの変更が
既存の道具の前提を壊した形である。

## 10. 判断が要る点【要裁定】較正の目盛りをどう直すか

`calibrate_vsearch` は D-059 で作った道具で、方策 π の線でも使う。**勝手に変えない。**
選択肢は次の 3 つで、いずれも記録は取り直さずに済む（学習 10 分＋評価 25 分でやり直せる）。

| 案 | 中身 | 良い点 | 気になる点 |
|---|---|---|---|
| **A（推し）** | 目盛り c を「**番兵を除いた本体の 90% 点**」にする。番兵は clip で潰れる | 測定でいちばん情報量が大きい（0.0506）。変更が 1 行で、意味も説明しやすい | 「番兵」の判定に閾値が要る（`\|v\| ≥ 100` など）。新しい既定値が 1 つ増える |
| B | `tanh(v / s)` に変える（s は本体の尺度） | 閾値が要らず、番兵が滑らかに飽和する。情報量は A とほぼ同じ（0.0503） | 変換の形が変わるので、D-059 の記録と直接は比べられない |

## 14. 較正を直したら何が変わったか

直した中身は 1 つだけ——**目盛り c の決め方**である（`--calib-scale bulk`）。

| | 従来 `p90` | 直した `bulk` |
|---|---|---|
| 目盛り c | 6668.2 | **9.757** |

**副作用は無い。** 葉が価値ネットになる反復 2 以降は探索値が [0,1] に収まるので、
`bulk` と `p90` は同じ目盛りになる（検査 `test_calibration_recomputed_per_iteration` で固定）。
既定は `p90` のままなので、方策 π の線（D-059）の再現性も壊れていない。

## 15. 判断が要る点【要裁定】「対 H」だけの小さな悪化を、採用の拒否理由とするか

§7.1 は「錨のどれかで明確に負ける（差の区間が 0 をまたがず悪化）なら、門番を通っても
採用しない」と定める。今回それに当たるのは**対 H のみ**（−0.035 ±0.029）である。

**この規則が防ごうとしていた失敗（D-059）の形と、今回の形は違う。**

| | D-059（規則ができた理由） | 今回 |
|---|---|---|
| 門番 | 通る（境界 0.526） | **通る（0.593・下端 0.566）** |
| 対 素の計画探索 | 下がる | **変わらない（+0.007）** |
| 対 H | 下がる | 下がる（−0.035） |
| 対 貪欲 | 下がる | **変わらない（+0.008）** |

A-3 で **相手プール {H_default, X1, X2} に対して CEM で最適化した値**である
（`meicho/planner.py` の `TUNED_WEIGHTS` の由来）。つまり**対 H は、前の版にとって
「調整に使った相手」＝ホームでの試合**である。そこで 0.923 という高い値が出ているのは自然で、
学習した V がそこだけ 3.5 ポイント届かないことは、設計の失敗の証拠としては弱い。

一方で、規則を都合よく緩めるのは D-043 以来この計画がいちばん警戒してきたことでもある。
**だから勝手に判断せず、マスターの裁定を仰ぐ。** 選べる道は 3 つある。

| 案 | 中身 | 費用 |
|---|---|---|
| **1（推し）** | 採用して**反復 2 へ進む**。対 H の −0.035 は台帳に残し、反復 2・3 でも同じ方向に悪化し続けたら停止する（悪化の累積を停止条件に足す） | 反復 2 が約 35 分 |

| 3 | 字義どおり**採用しない**。停止して §9 の診断に進む | 反復は止まる |

**2 は 1 の前に挟める**（ラダーで 1 位相当なら 1 へ、順位が落ちるなら 3 へ）。
判断材料を増やす順序としてはこれがいちばん堅い。

## 37. 結論（先に）— **V_3 が頂点。反復 4 は採用しない。**

## 39. 何が「上限」を作っているのか（仮説と、確かめ方）

断定はできないが、**確かめられる仮説が 1 つある**——それは、まさに保留していた判断である。

第 5 便 §24 で「学習データは**その反復の記録だけ**」と決めた。理由は 2 つあって、
(1) 一度に 2 つ変えない (2) 古い版の探索値が混ざると §3.4 の機構を薄める、だった。
**その判断は反復 2・3 では正しく働いた。** しかし単独の窓には別の弱点がある。

- 1 反復ぶん（約 79 万決定）で学習し直すたびに、**前の反復で覚えたことの一部を忘れる**
  （`--init` で重みは引き継ぐが、教師は毎回入れ替わる）。
- 反復が進むほど方策が尖り、記録に出てくる局面の**種類が狭くなる**。狭い教材で学ぶと、
  「今の自分が行く場所」だけが正確になり、他が痩せる——錨（H・貪欲）で先に悪化が出たのは
  その形と整合する。

設計書 §9 の「データ窓＝直近 3 反復ぶんを使う」は、まさにこれへの備えだった。
**反復 2・3・4 の記録はすべて残っており、探索値の尺度も揃っている**（葉が価値ネットなので [0,1]）。
つまり**記録を取り直さずに、学習と評価だけで試せる**。

| やること | 費用 |
|---|---|
| 反復 2＋3＋4 の記録（約 237 万決定）で V_4 を学習し直す | 学習 約 30〜40 分 |
| 同じ帯（402000..）で門番・錨・カナリアを取り直す | 評価 約 40 分 |

**合計 1 時間 20 分ほどで、「上限は窓のせいか、設計の限界か」が分かる。**
これは第 5 便 §24 で「反復 3 の結果を見てから改めて判断する」と書いた点そのものであり、
いま判断すべき時である。**マスターの裁定を仰ぐ。**

なお同じ帯で測り直すことになるので、**もし門番が境界に出たら別帯（414800..417199・登録済み）で
2,400 局の追試をする**。窓を変えた版と変えない版のどちらを採るかを、同じシードの上で比べられる利点もある。

# 第 10 便 — データ窓を広げて試した（2026-09-02）

## 41. 結論（先に）— **窓は「悪化」の原因だった。しかし「頭打ち」の原因ではなかった。**

反復 4 を、**直近 2 反復ぶんの記録**（反復 3＋4・156 万決定）で学習し直し、
まったく同じ帯・同じシードで測り直した。結果は 2 つに分かれた。

| 測定 | 窓 1 反復（第 9 便） | **窓 2 反復（今回）** | 読み方 |
|---|---|---|---|
| 門番（n=1200・帯 402000..） | 0.480 ±0.028 | **0.483 ±0.028**（下端 0.455） | **変わらない。どちらも越えない** |
| 錨 vs 素の計画探索 | −0.002 ±0.050 | **+0.020 ±0.054** | 差なし → 差なし |
| 錨 vs H | **−0.037 ±0.031（悪化）** | **+0.005 ±0.029** | **悪化が消えた** |
| 錨 vs 貪欲 | **−0.050 ±0.039（悪化）** | **−0.013 ±0.036** | **悪化が消えた** |
| カナリア（対 H・n=200） | 175/200（4.3 ターン） | 175/200（4.3 ターン） | 同じ |

**§39 の仮説は半分当たっていた。**

- 当たっていた側: 「単独の窓だと**教材が痩せて他の相手に弱くなる**」。窓を広げたら
  H・貪欲への悪化が**両方とも消えた**。第 9 便で錨に先に出た傷は、確かに窓のせいだった。
- 外れていた側: 「窓を広げれば**また伸び始める**」。門番は 0.480 → 0.483 でびくとも動かない。
  **伸びが止まっているのは窓のせいではない。**

したがって **V_3 が頂点である**という第 9 便の結論は変わらない。窓を広げた版（`drl_sd001_vb4w.json`）も
門番を越えていないので採用しない。**champion は `planner_vb3` のまま**である。

## 42. これは「この構成の上限」だと読む

反復ごとの伸びは **0.593 → 0.534 → 0.547 → 0.480 / 0.483** と、3 反復で使い切った形である。
設計書 §3.4 の機構（反復ごとに実効地平が 1 往復ずつ延びる）は反復 3 まで働き、
そこで**別の要因が上限を作っている**。心当たりは 2 つあるが、どちらも**この輪の外側**にある。

1. **符号化の限界**（D-061 の指摘）。V の入力は `encode.py` の 596 次元で、カードは ID の
   one-hot である。「同じ機構を持つ別のカード」を別物として覚えるので、教材が増えても
   一般化しにくい。D-061 の「第一手は埋め込みではなく**符号化の分解**」がここに効く見込みがある。
2. **相手モデル π₀ の据え置き**（設計書 §3.6）。V は「π₀ が相手をするときの勝率」を学ぶので、
   V が強くなるほど「π₀ を相手にした世界」に最適化されていく。D-059/060 で π の反復は
   頭打ちと分かっているが、**V が伸びなくなった今なら、π を 1 回だけ更新して V の輪を回し直す**
   のは筋が違う実験になる（`DRL_POLICY_ITERATION_NOTES.md` の線）。

**どちらも設計書 §10 の「やらないこと」の外にある新しい設計判断なので、ここでは踏み込まない。**
マスターの裁定を仰ぐべき候補として置いておく。

## 43. 途中で直した 2 つ（どちらもメモリの問題）

データ窓を試すために `drl_train.py` へ `--train` のカンマ区切り（複数接頭辞）を足したところ、
**2 か所で作業環境のメモリ（7 GB）を使い切って落ちた**。どちらも計算結果は変えずに直した。

| どこ | 何が起きたか | 直し方 |
|---|---|---|
| `meicho/drl_data.py::read_records` | `np.frombuffer` は元のバイト列への**参照**を残すので、全ファイルの生バイト（約 1.8 GB）と積み上げた配列の**両方**がメモリに乗っていた | 読んだ直後に `.copy()` して自前の領域へ移し、ファイルのバイト列を手放す |
| `experiments/drl_train.py` の入力スケール | `np.abs(tr.obs.astype(np.float32))` が **156 万 × 596 × 4 バイト ＝ 3.7 GB** を一度に確保していた | 20 万決定ずつに分けて同じ最大値を求める（**結果は 1 回で求めたものと厳密に同じ**） |

**3 反復ぶんの窓（234 万決定）は、この 2 つを直してもまだ入らなかった**ので、
今回は 2 反復ぶんで試している。3 反復ぶんを試すなら、記録を間引くか、
メモリの多い環境（Kaggle 等）で回すことになる。

検査は **473 passed, 2 skipped**（データ窓の検査 `test_files_of_accepts_a_data_window` を 1 件追加）。
`bench_agents.py` のフィンガープリント 3 種は着手前と完全一致のまま。
