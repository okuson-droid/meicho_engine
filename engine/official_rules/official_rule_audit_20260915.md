# 鳴潮：対決 公式ルール照合報告（2026-09-15）

対象:

- 正本: 『鳴潮：対決 総合ルール』Ver.1.0.0（2026-09-12）および FAQ（2026-09-12）
- 実装: `meicho_engine` の作業ブランチ `stage1b-encoding-v5` の Python 実装と Rust ソース

この文書では、公式条文・FAQで決まる挙動と、現行ソースを読み取りで照合した。変更・コミットは行っていない。Rust はこの環境にコンパイラがないため、ソース照合までとした。

## 結論

公式ルールと異なる、または公式ルールの必須処理を欠く点を **6件確認** した。最優先は「デッキとトラッシュが空なら敗北」の扱いで、現実装は意図的に逆の挙動をする。

|優先度|判定|公式根拠|現行実装の挙動|
|---|---|---|---|
|高|確定|701.1.1.1|アクションデッキとトラッシュが空でも敗北しない|
|高|確定|FAQ 33、FAQ 46、701.1.2|特定のデッキ操作後に必要なリフレッシュを行わない|
|高|確定|700.1.2–700.1.3、800.5.3|一部の同時誘発スキルをプレイヤーが順番選択できない|
|中|確定|800.4、800.5.1–800.5.3|いったん誘発済みのスキルを、解決時に条件を再評価して取り消し得る|
|中|確定|101.1.1.1、FAQ 1|各キャラの Lv.0 を「ちょうど1枚」にする構築検査がない|
|中|確定|ユーザー確認（正式ルール）|回復量をライフ20で上限にしている|

なお、投了（102.4）はエンジンAPIの合法手としては未提供である。対戦アプリ側のUIで処理する設計なら問題にならないが、エンジン単体を完全なルール実装とみなす場合は未実装である。

## 確定した差異

### 1. デッキ切れ敗北を実装していない

公式ルール 701.1.1.1 は、プレイヤーの「アクションデッキエリアおよびトラッシュ」にカードが1枚もない場合、そのプレイヤーは直ちに敗北すると定める。

しかし Python の `meicho/engine.py` は `_draw()` でデッキ・トラッシュがともに空なら単に戻り、ゲームを続行する。さらに `tests/test_engine.py::test_deck_out_does_not_lose_the_game` は、この非敗北挙動を明示的に期待している。Rust の `draw()`／`is_deadlocked()` も同じ旧仕様に沿っている。

影響: 一方だけが尽きた局面で、本来は即敗北なのに、ライフが0になるまで対戦が継続する。両者が尽きた場合も、公式は同時敗北による引き分け（102.2）だが、現実装は別の「進行不能」規則を用いている。

### 2. FAQ指定のデッキリフレッシュが欠ける

- FAQ 33: BP01-028 の「上から2枚を公開し、該当カードを手札、残りをトラッシュ」の解決後、デッキが0枚ならリフレッシュする。
  - 現行 `reveal_n_take_matching` はカードをデッキから取り出すだけで、解決後のリフレッシュを行わない。
- FAQ 46: BP01-073 のデッキ検索で対象「龍憑の天舞」が存在しない場合、存在しないことを宣言してデッキリフレッシュを行う。
  - 現行 `search_deck` は空のデッキをそのままシャッフルするだけで、トラッシュをデッキに戻さない。

これらは共通のルールチェック（701.1.2）を、カード操作の後に実施していないことによる。

### 3. 同時に誘発したスキルの解決順を選べない経路がある

公式ルール 700.1.2–700.1.3 は、処理待ちのスキルをターンプレイヤー、次に非ターンプレイヤーが1つずつ選んで解決すると定める。603.1.2.2.1–2 でも、レベルアップ時に【登場】と【レベルアップ】がともに誘発し得る。

通常の処理待ち列では順序選択を実装している一方、`_queue_fire_nested()` が作る `pending_triggers` は `_start_next_trigger()` で先頭から固定順に解決する。コードコメントにも「順番の選択を挟まない」と明記されている。Python と Rust の両方に同じ構造がある。

影響: レベルアップ、切り替え、回復、ダメージなどで同一プレイヤーの複数スキルが同時に誘発する局面では、公式に認められた解決順を選べず、結果が変わり得る。

### 4. 誘発済みスキルを後から失効させ得る

公式ルール 800.4 は、処理待ち状態に入った誘発型スキルを発生源から独立して扱い、発生源が元の領域を離れても通常どおり解決すると定める。

現行 `_start_next_skill()` と `_start_next_trigger()` は、待ち行列に積んだ後に `_skill_condition_met()` を再実行し、条件を満たさなくなったスキルを解決せず捨てる。先に解決したスキルによるリーダー交代、カード移動、状態変更で、既に誘発した後続スキルが消える可能性がある。

FAQ 47・48は「その時点で有効だったか」で誘発を判定することを補強している。FAQ 47のように誘発時点で無効なスキルを積まないのは正しいが、逆に誘発済みのものを後から取り消すのは公式 800.4 と整合しない。

### 5. デッキ構築時の Lv.0 枚数を厳密に検査していない

公式 101.1.1.1 と FAQ 1 は、3種類の各キャラについて Lv.0 のキャラカードを「ちょうど1枚」入れることを要求する。

`GameConfig.validate()` は各キャラ名について Lv.0 が「少なくとも1枚ある」ことしか検査しない。将来、同名の別カード番号の Lv.0 が登録された場合、2枚入れた不正なデッキを受理する。また、初期配置コードは同名Lv.0を辞書にするため、どちらを置くかが暗黙的に決まる。

現登録プールには同名Lv.0が複数ないため、現時点の公式デッキリストでは直ちに発火しないが、構築ルールの実装としては不足している。

### 6. 回復量をライフ20で上限にしている

正式ルールではライフ回復に上限はない。公式本文の 101.6 は開始ライフを20に設定する規定であり、最大値を定めるものではない。

一方、Python `_heal()` と Rust `heal()` は `min(20, life + amount)` として回復を20で止める。したがって、ライフ20のプレイヤーが回復する場合や、回復後に20を超える場合に、現実装は正式ルールより少ないライフになる。

## 照合済みで公式と一致した主要項目

- キャラデッキは3種類、合計3～15枚／アクションデッキは40枚、同一番号上限（101.1、FAQ 1–3）。ただしLv.0の枚数検査は上記の差異あり。
- 初手5枚、任意枚数の引き直し、先攻1ターン目は1枚ドロー（101.5、602.1.3）。
- 切り替えはリーダーとバックのみ（603.1.2.1、FAQ 16・23）。
- ルールによるレベルアップの対象・手札コスト（603.1.2.2、FAQ 4・5）。
- 対抗でのターンプレイヤーの提出必須、非ターンプレイヤーの任意提出、色・速度による勝敗、引き分けで【判定】を誘発しない（604.1、FAQ 9–12）。
- コストの任意選択支払い、【リーダースキル】の使用条件、追撃の加算（FAQ 6・7・21・32・35）。
- FAQ 42–43の「このカード自身がダメージを与えた時」だけを対象にする扱い、FAQ 47–48の誘発時点のリーダー判定は、カードを待ち行列へ積む段階の処理として実装されている。
