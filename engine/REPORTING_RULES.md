# 報告の作法（マスター指示・2026-08-24 制定）

このプロジェクトの成果物・報告は、**機械学習や統計の専門知識を前提としない**読者が
読んで理解できる形で書く。以下は守るべき規則であり、好みではない。

## 0. 規則の本文

> **マスターは機械学習の専門知識を持たない前提で報告すること。
> ただし内容は一切省略せず、必要に応じて解説を挟むこと。
> その結果として報告の分量が増えるのは構わない。**

## 1. なぜこの規則があるか

このプロジェクトの目的は「ユーザー自身の対人勝率の向上」であり、
**判断を下すのはマスターである**。判断の材料が専門用語の壁の向こうにあると、
マスターは中身を検討せずに結論だけを受け取ることになる。それは
「AI が言うからそうなのだろう」という状態であり、このプロジェクトが
避けるべきものである。数字と論拠が読めてこそ、異議も出せる。

短くまとめること自体は美徳だが、**理解できない短さは、長さより悪い**。

## 2. 具体的に守ること

### 2.1 専門用語は初出で必ず説明する

用語をそのまま使ってよいのは、直前か直後に一言の説明が付いているときだけである。

- 悪い例: 「valid logloss が 0.5601 から 0.5241 に改善した」
- 良い例: 「予測の外し具合を表す指標（対数損失。低いほど良い。当てずっぽうなら
  0.693）が 0.5601 から 0.5241 に下がった。つまり勝敗の予測が上手くなった」

繰り返し出る用語は `GLOSSARY.md` に登録し、文書の冒頭で参照を示す。
既に説明した用語を同じ文書の中で何度も説明し直す必要はない。

### 2.2 数字には「何と比べて」「どれくらい確かか」を添える

- 単独の数字を置かない。基準（現状値・当てずっぽうの値・理論的下限）を必ず並べる。
- 勝率や指標の差には、信頼区間（＝測り直したときに収まる範囲）を付ける。
  これは元々の作業規約6でもあるが、**区間の意味を毎回一言で説明する**こと。
- 「有意」「有意でない」は必ず言い換えを添える
  （例:「区間が 0 をまたぐので、差があるとは言い切れない」）。

### 2.3 結論を先に、機構を後に

各文書・各報告は「何が分かったか」を先頭に置き、
その後に「どう測ったか」「なぜそうなるか」を置く。
読み飛ばしても損をしない順序にする。

### 2.4 比喩と具体例を使う。ただし正確さを犠牲にしない

抽象的な仕組みは、このゲームの具体的な場面に翻訳して説明する。
分かりやすさのために嘘をつかない。比喩が破綻する境界は明示する。

### 2.5 「分量が増えるのは構わない」

説明を足した結果として文書が長くなることを、削る理由にしてはならない。
削ってよいのは重複と、判断に影響しない細部だけである。

### 2.6 マスターに作業を頼むときは、手順を省略せずに書く（2026-08-27 制定・D-058）

**マスターの手を動かしてもらう依頼は、それだけを読んで実行できる形で書く。**
「もう一度お願い」「同じ手順で」「前回と同様に」は**禁止**である。前に書いたから省いてよい、
という判断をしてはならない。会話は流れて、手順は埋もれる。

依頼には次の 5 つを必ず含める。

1. **どこで**（作業ディレクトリ。`engine\rust` のように具体的に）
2. **何を打つか**（コマンドをそのまま貼れる形で。1 行ずつ）
3. **成功したらどう見えるか**（最後に出る行・生成されるファイル名）
4. **確認のしかた**（検査コマンドと、期待される値）
5. **転びやすいところと、その症状**（何が起きたらどう読むか）

加えて、**なぜ今それが要るのか**を一行添える（例:「`agents.rs` を変えたので、
`.pyd` はソースと一緒に配られない」）。理由が分かれば、次に同じ状況になったとき
マスター自身で判断できる。

**この規則が生まれた経緯**: 2026-08-27、クロエが「`maturin build --release --out dist` を
もう一度お願い」とだけ書いた。その前に一度、手順書きが `target\wheels` を指していたのに
運用が `dist` だったせいで「ビルドしていないのに `pip install` して失敗」という往復も起こしている。
**手順の省略と、手順の不一致は、同じ失敗の別の顔である。**

### 2.7 n が小さい勝率は「点」で語らない（2026-09-07 制定・文献計画 便 D / D-1）

**対人局や n が小さい勝率は、点推定ではなく Wilson 区間と Clopper-Pearson 上端を併記する。**

- *点推定* とは「4 局で 0 勝だったから勝率 0%」のように、割り算の答えをそのまま書くことである。
  4 回コインを投げて 4 回とも裏が出ても、そのコインが「絶対に表が出ない」とは言えない。
  **少ない回数から言えるのは点ではなく範囲**である。
- *Wilson 区間* … ふだん使う 95% 区間。n が小さくても 0 や 1 をはみ出さない
- *Clopper-Pearson 区間*（正確区間）… 二項分布から直に解く区間。**必ず Wilson より広い**
- **0 勝・全勝など極端なときは判断に Clopper-Pearson を使う**（Wilson は端で狭すぎる）
- **相手の版が混在しているときはその旨を書く。** 版ごとに強さが違うものを 1 つの
  二項分布として扱うのは近似であり、区間は本当はもっと広い
- **対人局は判定ではなく診断に使う。** 「どの対抗で価値の見立てが崩れたか」を見るのが役目で、
  champion の採否を決めるのは自己対戦の門番である

道具は `experiments/human_games_ci.py`。書き方の例:

> AI の対マスター勝率は **0.602 を上回らない**（95%・n=4・AI 0 勝）。
> **どれくらい弱いかは言えない**（下端は 0.000 まで開いている）。

### 2.8 測定の前に V を凍結し、由来を残す（2026-09-07 制定・文献計画 便 D / D-2・D-3）

**門番・錨・ラダーを回す前に、その時点の価値関数 V と方策 π のファイルの sha256 を結果に記録する。**

- *sha256* とは「ファイルの中身から作る 64 桁の 16 進数」である。中身が 1 バイトでも違えば
  まったく違う値になる。**同じ名前で中身が違うファイル**を見分けるために使う
- **門番の対局データで V を再学習しない。門番の結果を見てから V を差し替えない。**
  答えを見てから問題を選び直すのと同じで、勝率が意味を失う
- 実装上は、由来（`provenance`）を測定の**開始時**に作って書き出す（終了時ではない）。
  終了時に作ると「測っている途中で差し替える」抜け道が残る
- 道具は `experiments/provenance.py`。`eval_vb.py` / `probe_d065.py` /
  `champion_challenge_vb.py` / `ladder.py` の結果 JSON に入る

**すべての勝率は条件つきである。** 「0.606」という数字は「どの探索器で・どの価値関数を積んで・
どの実装で・どのシード帯で」測ったかが決まってはじめて意味を持つ。由来はその条件を
**人の書いたラベルではなく機械可読な形で**残すためのものである。

## 3. 適用範囲

| 対象 | 適用 |
|---|---|
| `*_NOTES.md` などの報告文書 | **適用する。** 冒頭に「この文書の読み方」を置く |
| `decisions.md` の裁定記録 | **適用する。** 裁定の一行目は専門用語なしで書く |
| 引継ぎ書 `HANDOFF_*.md` | **適用する。** ただし読者は次セッションの Claude でもあるため、正確な用語も併記する |
| 会話での報告 | **適用する** |
| **マスターへの作業依頼**（会話・引継ぎ書の両方） | **適用する。** §2.6 の 5 点を必ず書く |
| コード中のコメント・docstring | 適用しない（読者は実装者である） |
| テスト名・変数名 | 適用しない |

文体そのものは従来どおり。**文書は「である調」の技術文書、会話は口語**
（プロジェクト設定の口調指定に従う）。この規則が変えるのは
**難易度であって文体ではない**。

## 4. 判断に迷ったときの基準

「この段落だけを読んだマスターが、次に何をすべきか自分で判断できるか」
を基準にする。できないなら説明が足りない。
