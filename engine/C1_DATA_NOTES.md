## 1. 保存単位は `observe()` にした（D-037 裁定1）

**記録するのは `engine.observe(s, pi)` であり、`GameState` ではない。**

`observe` はこのプロジェクトにおける「pi に見えてよい情報」の定義そのもの
（§4 / §10、スキャン効果の `hand_known` を含む）なので、これを保存単位にすると
**覗き見の禁止 (D-026) が保存形式のレベルで構造的に保証される**。
学習側がうっかり隠蔽情報を触ることが原理的にできない。
特徴設計を後から変えても、観測が残っていれば再抽出できる。

副産物として容量も小さい。1行の生 JSON は約 950 バイトだが、
観測は反復の多い構造なので gzip が効き、実効 **42 バイト/行**に収まった。
4万行で 1.8 MB なので、データセットごとリポジトリに置ける。

## 2. その過程で見つかった `observe()` の欠落（D-036）

保存単位を `observe` にしようとして、**`observe` が公開情報を取りこぼしている**
ことが分かった。観測だけからは現行の特徴すら再現できなかった。

欠けていたもの（すべて表向きのカードや公開の行動から生じる公開情報）:

| 欠けていた項目 | 影響 | 実対局での出現率 |
|---|---|---|
| `red_cost_up` / `pending_red_cost_up`（旋風 SD001-T07） | `_effective_cost` が参照するので、**使用可能な赤の枚数 `live_reds` を数え違える** | 3.1% |
| `used_charge` / `used_switch` / `used_levelup`（§6.3 1ターン1回） | このターンにまだチャージできるかが分からない。合法手そのものを決める量 | 64.1% |
| `rush_forbidden` / `pending_rush_forbidden`（赤瞳凍土 SD02-T08） | 連撃可否が分からない | 現プールでは 0% |
| `leader_switch_forbidden` | 切り替え可否が分からない | 現プールでは 0% |
| `clash_winner` / `last_clash_winner` / `last_clash_cards` | 直近の対抗の結果が分からない（提出は公開される §6.4(1)-3） | — |

`live_reds` は A-3 で調整済みの6項の1つ（重み 0.533）である。これを取りこぼしたまま
4万局面を生成していたら、学習データは静かに壊れていた。

**引継ぎ書 §4.3 は「C-1 でエンジン本体を変更しない」としているので、マスターに諮って
`observe` を拡張した**（D-036）。追加は純粋に read-only で、`observe` を読む
エージェントは現状ゼロなので挙動には影響しない。`bench_agents.py` の
fingerprint 3種すべてが拡張前と一致することで確認済み
（`905073e2e202bd39` / `7cfceac12f2c070f` / `1f5e2e218cc54acc`）。

視点は pi 基準に写して `{me, opp}` で返す（`clash_winner` は 0=自分 / 1=相手 / None）。
`test_observation_orients_continuous_effects_to_the_viewer` が写し違えを検出する。

## 3. 特徴抽出を正式化した（`meicho/features.py`）

`bench_evaluate.py` の叩き台を、入口を2つ持つモジュールに昇格した。

- `from_obs(ob)` — 保存済み観測から。**学習時**に使う（D-026 が構造的に守られる）
- `from_state(s, pi)` — `GameState` から直接。**探索の葉**から呼ぶ速い経路

1本にまとめて `from_obs(observe(s, pi))` にすれば実装は1つで済むが、
`observe` は毎回大きな dict を組むので探索のホットループには置けない
（D-035 の予算に収まらない）。逆に学習側に `GameState` を触らせると
覗き見の禁止が構造的に守れない。**だから実装は2本にし、
「両者が完全一致すること」をテストで担保する**
（`test_from_obs_matches_from_state_on_real_games`。特徴を足すときは必ず両方に足す）。

`red_cost_up` は実対局の 3% でしか立たないので、通常の局面比較では踏み抜けない。
強制的に立てた局面で一致を確かめる専用テストを別に置いた
（`test_from_obs_matches_from_state_when_red_cost_up_is_active`）。

特徴は 22 項。現行 `evaluate` の6項（差分）に、それが潰している情報を足した:
素の値（ライフ差5の意味は 18-13 と 6-1 で違う）、協奏目標からの乖離、
対抗の色の累積回数（`clash_counts`, D-031）。

## 4. 配管の健全性チェック（**§4.1-2 の本番ではない**）

データが学習可能かどうかだけを確かめた。標準化＋ロジスティック回帰、
手書きの勾配降下 600 step、正則化の掃引なし、信頼区間なし。
**この数字は次セッションの出発点であって結論ではない。**

| | logloss | 正解率 |
|---|---|---|
| 基準（常に 0.5） | 0.6931 | 0.500 |
| train | 0.5250 | 0.721 |
| valid | 0.5238 | 0.724 |

train と valid がほぼ同じなので、この容量では過適合していない。
ターン帯別の valid 正解率は 1-4 で 0.650、5-8 で 0.744、9-12 で 0.781、13以降で 0.750。
序盤ほど当たらないのは当然で、**序盤の局面価値こそ探索が必要な部分**である。

標準化後の係数が大きい特徴（参考）:
`life_diff` +0.83 / `hand_diff` +0.51 / `hand_me` +0.44 / `life_opp` −0.42 /
`life_me` +0.41 / **`clash_pass_diff` +0.39** / `concerto_diff` +0.38。

**`clash_pass_diff` が効いているのは注目に値する。** これは D-031 で追加し、
B-3 が「相手モデルとしては効かない」と結論した対抗履歴の特徴である
（色は当てられるが当てても手が変わらなかった）。
**相手の行動予測としては無価値でも、局面価値の特徴としては情報を持つ**
可能性がある。次セッションで正面から検証する価値がある。

## 5. 限界と注意（次セッションへ）

1. **valid は「別の対局」であって「別の相手」ではない。** train と valid は
   同じ相手構成から生成している。測れているのは対局とシードをまたぐ汎化であって、
   未知の相手への転移ではない。転移を測るなら、プールに入れなかった相手
   （例: mcts160、π_det、π_mix）で第三の split を作ること。
   A-3 が同じ罠を踏みかけている（PLANNER_NOTES.md / D-028）。
2. **ラベルは最終勝敗のみ。** TD 系の目標値に替えたくなったら、同じ観測列から
   後で作れるように `turn_no` と `turns_total` を全行に併記してある。
3. **採取地点はターン開始時（アクションフェイズに入った瞬間）の両者ぶん**。
   対抗の途中は同一ターン内で強く相関するので採っていない。
   対抗ステップの価値を学ばせたくなったら採取地点を足すことになるが、
   そのときは対局単位の相関が増えることに注意する。
4. **同一ターンの2行は互いにほぼ鏡像で、ラベルは足して 1.0 になる。**
   train/valid を対局単位で分けているので漏洩はないが、
   **1つの対局の中で train と valid を分けてはならない**。
5. 現プールでは `rush_forbidden` / `leader_switch_forbidden` が一度も立たない
   （SD02-T08 が SD001 に入っていない）。SD02 を混ぜた生成では分布が変わる。
