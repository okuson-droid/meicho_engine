> **状態: 設計のみ。実装・測定は行っていない。** 実装は別チャット（エンジンの持ち場）が行う。
> 準拠: rules v0.18／符号化 v6／champion `planner_vc4cps_kheb_b75`（本書はどれも動かさない）。
> 出どころ: 監査（2026-09-22）でマスターが「環境デッキ群の策定には類似度の指標が要る。類似性の高いデッキを複数入れないため」と指示した。
> 関係する裁定: D-121（環境デッキ群はマスターがデッキメーカーで作り、割り振りはクロエが規則で案を作る）／計画書 `GENERALIST_AI_REVIEW_D086.md` §5.2（学習 12・調整 4・最終評価 4）・§5.4（構築系統と抽出配分の記録）。

## 0. 結論

1. **類似度は 1 つの数字に潰さず、3 つの層で別々に測る。**構成（カード番号）・キャラ（3 人組）・動き（機構と属性のプロファイル）。「札はほぼ同じで 1 枚違い」と「札は違うのに同じ動きをする」は別の種類の近さで、汎用 AI の評価では後者のほうが厄介だからである。
2. **数字を出したあとの規則（同じグループにする条件・並べ方・割り振り）は、候補デッキを見る前に固定する。**閾値は錨（SD001・SD02・`K_smoke` 3 種・SD001 の 1 枚替え）で尺度の感触を確かめてから決め、候補を見たあとには動かさない（`measurement_discipline` の「閾値は測る前に決める」と同じ）。
3. **対局は回さない。**3 層ともカードデータとデッキリストから決定的に計算でき、数秒で終わる。対局を使う 4 層目（打ち方の近さ）は「選ぶ道具」ではなく「選んだあとの診断」に留める（§7）。
4. 道具は `experiments/deck_similarity.py`。出力は対行列・系統のグループ・最遠点の並び・割り振りの案・`record_mix.py` の組み合わせ表にそのまま貼れる `decks` ブロック。

## 1. 何のための類似度か（用途を先に決める）

用途は 2 つで、どちらも「学習したことが評価デッキで通用するか」を正しく測るためである。

- **分割の保護**: 学習デッキと評価デッキに近縁のデッキがまたがると、「未知構築（A）」の評価が「既知構築の変種」の評価に化ける。計画書 §5.2 の「1 枚違いの姉妹デッキを割らない」を数値化する。
- **群の多様性**: 約 20 構築しか置けないので、同じ系統を複数入れると被覆が減る。候補を「既にある系統からの距離」で並べ、入れ替え候補を示す。

構築の近さは打ち方の近さそのものではない（§8）。本書の数字は「候補を並べ、割り振りを決める」ための物差しであって、汎用化の度合いの証明には使わない。

## 2. 入力と前提

- デッキは `engine/decklists/` と同じ JSON（`{name, description, chara_deck, action_deck}`）。デッキメーカーの書き出しには `id`・`description`・`art` などの余分な欄が付くが、**読み飛ばす**（欄が増えても落ちない）。
- `chara_deck` は 9 枚（キャラ 3 種 × Lv.0〜2）、`action_deck` は 40 枚（同番号 3 枚まで）。合法性は `GameConfig.validate` と同じ条件で先に検査し、通らないデッキは類似度を出さずに理由を返す。
- キャラの同一性は `CHARA_CARDS[c].name`（`record_mix.py` の `chara_trio` と同じ取り方）。Lv.0 に BP01 の別番号を使う構築（SD001 の `BP01-018` など）があるので、**キャラ名の一致と、キャラデッキの番号の一致は別に数える**。
- カードの機構の素性は `experiments/analyse_card_space.py::profile()` を**そのまま呼ぶ**（写さない）。この関数はカード番号・名前・専用キャラ名を伏せる（`tests/test_card_space.py` が番人）ので、層 3 が「誰のカードか」に引きずられない。
- 候補集合 = マスターから渡された全デッキ ＋ 錨（SD001・SD02・`K_smoke_ANKO`・`K_smoke_SANGE`・`K_smoke_TSUBAKI`）。錨は割り振りには入れない（SD001・SD02 は退化検査と既知構築の枠・計画書 §4、`K_smoke` は効果の実行検査用で環境デッキではない・§5.2）。

## 3. 層 1 — 構成の近さ（カード番号）

行動デッキ 40 枚を「番号 → 枚数」の多重集合 c_A(x) とし、**重みつき Jaccard** で測る。

    S1(A, B) = Σ_x w(x)·min(c_A(x), c_B(x)) / Σ_x w(x)·max(c_A(x), c_B(x))

- **S1_raw**: w(x) = 1。1 枚違いなら 39/41 = 0.951、2 枚違いなら 38/42 = 0.905、共通札が無ければ 0。
- **S1_idf**: w(x) = idf(x) = ln((N + 1) / (df(x) + 1)) + 1。N は候補集合のデッキ数、df(x) はその番号を 1 枚以上入れているデッキ数。誰でも入れる汎用札の共有を軽く、珍しい札の共有を重くする（計画書 §5.4 の抽出配分用 TF-IDF と同じ考え）。**idf は候補を全部集めてから 1 回だけ計算して保存し、分割を見てから直さない。**候補が増えたら再計算し、版を上げる。
- **S1_common**: 専用札（`dedicated_to` のあるカード）を除いた共通札だけで S1_raw を取る。層 2 の情報（3 人組が同じなら専用札も同じ）を層 1 から切り分けるための補助値。

3 つとも [0, 1]、対称、自分自身とは 1。

## 4. 層 2 — キャラの近さ（3 人組）

数字より先に**系統の鍵**として使う。

- **S2_trio** ∈ {0, 1, 2, 3}: キャラ名の一致数。3 なら同じ 3 人組（同じ系統の候補）、2 なら近縁、1 以下なら別系統。
- **S2_deck**: `chara_deck` 9 枚の番号での Jaccard（集合）。3 人組が同じでも Lv.0 の選び方で違いうる。
- 補助として記録するもの: 行動デッキに占める専用札の割合（`dedicated_to` の枚数 / 40）、色の主成分（赤・緑・青の枚数）。リーダーはデッキリストに無い（準備で選ぶ）ので扱わない。

## 5. 層 3 — 動きの近さ（機構と属性のプロファイル）

デッキを、カードデータから機械的に出せる集約ベクトル v_A にし、コサイン類似度で比べる。

    S3(A, B) = v_A · v_B / (|v_A| |v_B|)

v_A の作り方:

1. `action_deck` の 40 枚（枚数ぶん重ねる）と `chara_deck` の 9 枚それぞれについて `profile()` を取り、Counter を合算する。
2. 素性を**族**に分ける: `color=`／`cost=`（`meicho/buckets.py::cost_band` で 4 帯に畳んだもの）／`speed=`／`damage=`／`level=`／`tag=`／`timing=`／`cond=`／`op=`（パラメータ無しの名前）／`op=…/k=v`（パラメータつき）／その他（`dedicated`・`leader_skill`・`leader_only`・`optional`）。
3. **族ごとに合計 1 に正規化してから連結する**（族の中の素性数が多いほど重くならないように）。族の重みは全部 1（判断が要る点 §10-4）。
4. 語彙は候補集合 ＋ 錨に現れる素性の和集合で固定し、保存する。

S3 は [0, 1]（成分が非負なので）。「札は 1 枚も共通しないが、色・コスト帯・タイミング・オペコードの分布がほぼ同じ」デッキで高くなる。これが「未知構築 A」の評価で最も避けたい近さである。

## 6. 錨（尺度の感触を取る。閾値を決める前に必ず出す）

- **SD001 対 SD001** = 全層 1（自明の検査）。
- **SD001 対 SD02**: S1_raw = 0（D-061「ID で共通 0」）。S3 は中くらいの値（D-061「機構では 7/17 共通」）——**ここが「札が違っても動きが似ている」の基準点**。実測して記録する。
- **SD001 対 SD001 の 1 枚替え**（共通札 1 枚を別の共通札に替えたもの）: S1_raw = 0.951。S1_idf は替えた札の idf に依る。S2_trio = 3。S3 ≈ 1。**これが「姉妹デッキ」の基準点**。
- **`K_smoke` 3 種どうし・対 SD001/SD02**: 系統がばらけているはず。値を記録する。
- 錨の値は `results/decksim/anchors.json` に保存し、検査で固定する（数値そのものではなく「SD001 対 SD02 の S1_raw = 0」「1 枚替えの S1_raw = 39/41」など、理屈で決まるものだけ厳密に。S3 の値は回帰の番人として rel=1e-9 で固定）。

## 7. 規則（候補を見る前に固定する。閾値は仮置き）

### 7.1 同じグループにする条件（分割の保護）

次のどれかを満たす 2 デッキは同じグループとし、**学習と評価にまたがらせない**。

- S2_trio = 3（同じ 3 人組）
- S1_idf ≥ 0.5
- S3 ≥ 0.9

グループは上の関係の**連結成分**で閉じる（A〜B、B〜C なら A・B・C は同じグループ）。連結で膨らみすぎたグループは、どの組がつないだかを報告に出す（閾値を直す材料であって、その場で外さない）。閾値 0.5・0.9 は仮で、§6 の錨を見てから決め、**候補デッキを見たあとには動かさない**。

### 7.2 群の多様性（並べ方）

並べる用途にだけ、3 層を合わせた距離を使う。

    d(A, B) = ( (1 − S1_idf) + (1 − S2_trio / 3) + (1 − S3) ) / 3

**最遠点の貪欲選択**: 最初の 1 つは候補の中で他との平均距離が最大のもの、以後は「既に選んだ集合への最小距離」が最大の候補を順に取る。並びの後ろほど「既にある系統の変種」であり、入れ替え候補になる。d は並べるためだけの便宜で、採否の基準には使わない。

### 7.3 割り振り（学習 12・調整 4・最終評価 4）

1. グループ単位で割り振る（グループを割らない）。
2. 最終評価 4 のうち **3 つは学習・調整のどのグループとも別系統**（7.1 のどの条件も満たさない）、**1 つは学習した系統の変種**（学習デッキのどれかと S1_idf が 0.5〜0.8・S2_trio = 3）とする。変種枠は 7.1 の例外で、`split: "final_variant"` の旗を付けて区別する。理由: 変種を締め出すと「学んだ系統の変種に対応できるか」という A の易しい側が測れない。汎用化の段階（変種 → 別系統）を読むための枠である。
3. 調整 4 は、学習に無い系統を優先して置く（最終評価の代わりに途中で見てよいデッキ）。
4. 最終評価の 4 デッキは、学習の**相手側**にも出さない（計画書 §5.2）。
5. 割り振りは候補デッキの中身をマスターが知っている状態で行われる。これは避けられないので、割り振りの規則と乱数（同点のときの並び）を先に固定し、手で入れ替えたときはその旨を manifest に残す。
   **手割りの口（decksim-3・D-128）**: `--split-override <JSON>`（`{"reason": …, "split": {名前: train|tune|final|final_variant}}`）。`check_override` が**理由が空でないこと・名前が候補にあること・値が 4 種か `None` であること・1 に反してグループを割っていないこと**（`final_variant` だけ例外）を検算する。規則そのものは変わらず、規則が出した案は出力の `assignment_auto` と Markdown の「規則が出した案（参考）」に残る。

## 8. 4 層目（打ち方の近さ）— 選んだあとの診断にだけ使う

同じネット無し教師（`record_mix.py` の `netfree`）で固定の相手群（H・貪欲・素 planner）と打たせ、対抗で出す色の分布・コスト帯ごとの使用率・最初のダメージまでのターン数・勝率のプロフィール（ラダーの「ロジット行列の行の差」と同じ見方）を比べる。対局が要り（1 デッキあたり数百局）、教師の打ち方に依存するので、**候補を選ぶ物差しにはしない**。選んだ群に対して 1 回回し、「構築は遠いのに打ち方が同じ」組があれば §7.1 の閾値を見直す材料にする（見直しは次の候補集合から）。

## 9. 道具の仕様 `experiments/deck_similarity.py`

- **起動**: `python experiments/deck_similarity.py <デッキの JSON か フォルダ …> [--anchors] [--thresholds thresholds.json] [--out results/decksim/<名前>.json] [--md results/decksim/<名前>.md]`
  - `--anchors`: SD001・SD02・`K_smoke` 3 種を候補に加える（割り振りには入れない）
  - `--thresholds`: §7.1 の閾値と §5 の族の重み。無ければ本書の仮置き値。**使った値は出力に写す**
- **出力 JSON**: 各デッキの sha256（ファイルのバイト列・`record_mix.py::load_deck` と同じ）・キャラ 3 人組・専用札の割合・色の枚数／5 つの対行列（S1_raw・S1_idf・S1_common・S2_trio・S2_deck・S3）／idf の表と語彙（版つき）／グループ（連結成分と、つないだ組）／最遠点の並び／割り振りの案／**`record_mix.py` の組み合わせ表の `decks` ブロック**（`{名前: {lineage, group, split}}`。`lineage` はグループの代表デッキ名、`group` はグループ番号、`split` は `train`／`tune`／`final`／`final_variant`）
- **出力 Markdown**: マスターが読む要約。錨との比較、グループごとの一覧、並び、入れ替え候補（「このデッキは X の変種（S1_idf 0.7・S3 0.96）」の形）。表は使わず 1 デッキ 1 行。
- **決定性**: 乱数を使わない。同点の並びはデッキ名の辞書順。同じ入力なら出力のバイト列が一致する。
- **関数の口**: `load_decks(paths) → dict`／`layer1(a, b, idf=None) → (raw, idf, common)`／`layer2(a, b) → (trio, deck)`／`layer3(a, b, vocab) → float`／`groups(decks, thresholds) → list[set]`／`farthest_order(decks, groups) → list`／`assign(decks, groups, sizes=(12, 4, 4)) → dict`。段階 2 の manifest 作成（`record_mix.py`）から import できる形にする。写しを持たない。
- 対局を回さない。帯を使わない。エンジン本体・Rust・符号化・champion に触れない。

## 10. 判断が要る点（推しを先に書く）

1. **層 1 に idf を掛けるか** → 推し: 掛ける（S1_idf を主・S1_raw を併記）。
2. **最終評価に「変種」枠を 1 つ置くか** → 推し: 置く（§7.3 の 2）。

4. **層 3 の族の重み** → 推し: 全部 1（族ごとに合計 1 に正規化するだけ）。重みを変えるなら錨で理由を示してから。
5. **閾値（7.1 の 0.5・0.9、7.3 の 0.5〜0.8）** → 仮置き。錨を見て決め、候補を見たあとに動かさない。

## 11. 検査（実装より先に書く）

- 自分自身との類似度は全層 1・対称・[0, 1] に収まる
- SD001 対 SD02 の S1_raw = 0（D-061）／SD001 の 1 枚替えの S1_raw = 39/41・2 枚替え = 38/42（厳密）
- idf: 全デッキに入っている札の重みが最小・1 デッキにしか無い札の重みが最大／候補の並び順を変えても idf と全対行列が変わらない
- 層 3 が名前に依らない: 専用キャラだけが違う同じカードを差し替えた 2 デッキで S3 = 1（`analyse_card_space.py` §3 の「専用キャラだけが違う組」を使う）
- 族の正規化: 1 つの族の素性を全部 2 倍しても S3 が変わらない
- グループ: 閾値ちょうどの組の扱い（≥ で入る）／連結で 3 つがつながる例／つないだ組が報告される
- 最遠点の並び: 同じデッキを 2 つ入れたら 2 つ目が最後に来る／同点は辞書順
- 割り振り: グループを割らない／最終評価の 3 つが学習・調整のどれとも 7.1 を満たさない／変種枠が条件を満たす／`decks` ブロックが `record_mix.py` に読ませて落ちない
- 決定性: 同じ入力で 2 回回して出力がバイト一致
- 余分な欄（`id`・`art`）のあるデッキメーカーの書き出しを読める／合法でないデッキは理由つきで弾く
- **わざと壊す**: `profile()` の代わりにカード名を使う版に差し替えたら「専用キャラだけが違う」検査が落ちること／idf の平滑化を外したら 1 デッキにしか無い札で 0 除算になること

## 12. 言えないこと・使ってはいけない読み方

- 構築の近さは打ち方の近さではない。S3 が低くても対局では同じように回るデッキはありうるし、逆もある。
- 20 デッキで構築空間を代表することはできない（計画書 §5.2）。本書の規則は「置いた 20 の中で系統が重ならない」ことまでしか保証しない。
- 閾値は仮であり、錨 5 つで決めた尺度である。候補が増えて分布が変わったら、次の候補集合から見直す（その回の分割は変えない）。
- S3 の語彙は `profile()` の表現に依る。G0 報告 §2.3 のとおり `profile()` は条件の値・順序・対象の関係を落とすので、「動きが同じ」は「この表現上で同じ」と読む。
- 類似度が低いことは、そのデッキが環境で実際にありうる構築であることを意味しない。「実際にありそうか」はマスターの目で見る（D-121 の裁定どおりマスターが組む）。
