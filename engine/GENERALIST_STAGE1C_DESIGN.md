## 0. 何をするか（要約）

段階2（凍結した教師で約 1 万局の横断教材を作り、V の表現を比べる）に入る前に、次の 3 便を行う。**1 便で変える要素は 1 つ**の原則に合わせて割った。

## 2. 1C-b 異種デッキの記録入口

### 変えるもの

1. `drl_record.py` に**組み合わせ表**を渡す口（例 `--schedule plan.json`）。表には「デッキ A・デッキ B・局数・席の決め方・教師」を並べる。
   計画書 §5.3 の配分（ミラー 40%・学習デッキ同士 40%・H／貪欲／固定版 20%）を表で書けるようにする
2. manifest に §5.4 の項目: デッキの sha256・キャラ 3 人組・機構の系統・近似重複のグループ・予定の抽出確率・**実際の席別の局数と決定数**・教師の定義（ネットの指紋を含む）・「相手デッキ表を知っている」前提の旗
3. 教師は計画書 §3.3-5・G0 §5 の推しどおり**ネット無しの計画探索**（`extra_turns=1`・`choice_phases`・`solo_samples=4`・`known_hand`・`draw_buckets=1`）。
   探索の多様性は **`bundle_p=0`・小さい `tau`**（G0 §5.2 の推し。`tau` は学習デッキだけで下見して事前に固定する）。
   D-120 の実測でネット無しは 1 局 0.1 秒（2 コア・SD001）なので、1 万局は数分〜数十分の見込み

### ★落とし穴: いまの対局列は、違うデッキ同士だと相手デッキ表を半分取り違える

- `rs.series` / `series_record` は、シードが奇数の局で **A と B の席を入れ替える**。**デッキは席に付いたまま**である（`lib.rs::run_series`）
- 一方、探索器の相手デッキ表（`opp_decklist`）は**エージェントの定義（spec）に固定**で入っている
- ミラーでは両方同じデッキなので問題にならない。**違うデッキ同士では、奇数の局で A が自分のデッキを相手のデッキと思い込む**（決定化の母集団が違うデッキになる）
- 直し方: 対局ごとに「相手の席のデッキ」から `opp_decklist` を作る（Rust の `build_agent` に席のデッキを渡す）。spec の固定値は使わない
- **過去の測定への影響は未確認**: `experiments/ablation.py` の異型戦（SD001 対 SD02・2026-08-23）は planner の相手デッキ表を SD001 に固定していた。
  相手が SD02 の局では母集団が違っていた可能性がある。結論は「規則の寄与はどれも 0 に近い」で、この取り違えで結論が変わるかは測っていない。ラダーの `matchup` モードはいまの実装では `deck` が 1 つである前提のコードがあり、使われていない見込み

### 挙動不変の確かめ方

- ミラーの記録は、表を使っても従来の CLI と**バイトまで同じ記録**になる（同じ教師・同じシード）
- 違うデッキ同士で、A が両方の席で正しい相手デッキ表を持つことを検査で固定する（直す前の実装で落ちることを先に確かめる）

### 費用

実装 1〜2 日。Rust の対局列の口を変えるので PC の再ビルドが要る。

## 3. 1C-c 符号化 v6

### 変えるもの

- 観測の符号化に次を足す（Python `encode.py`・Rust `encode.rs`）:
  - 相手の手札について知っていること: `hand_known ∪ hand_public`（多重集合の max）のカード枚数ベクトル（v5 の `hand_known` の列を置き換える形にするかは実装時に決める）
  - PT-3 信念の要約: 相手の手札としてありうる区別できる手札の数 W の対数・既知の枚数・確定した色／コスト帯の上下限・山札の残りが確定しているかの旗
- `ENCODING_VERSION` 5 → 6。学習済みネット 12 本は新しい列の重みを 0 にして移行する（`scripts/migrate_nets_*.py` の形・移行前後の出力を float64 で検算）
- PT-4（先読みの結果を入力に）は**入れない**。段階2 の表現比較の第 3 候補として別に扱う（D-119）

### 挙動不変の確かめ方

- 移行したネットは出力が移行前と一致する（新しい列が 0 のあいだ）→ champion の指紋が変わらない
- Python↔Rust の符号化の一致（ランダムな局面）

### 費用

実装 1〜2 日＋ネット移行。**PC の再ビルド・移行・全検査が要る**（全検査は約 3 時間）。

## 4. 環境デッキ群（便の外の前提）

計画書 §5.2 と G0 §4 のとおり、段階2 には**学習・調整・最終評価に分けた約 20 構築**が要る。SD001・SD02 は退化検査と既知の別構築に残し、未知構築の評価に数えない。

- 条件: `GameConfig.validate` と同じ合法性（キャラ 3 種類ちょうど・アクション 40 枚・同番号 3 枚まで・専用カードは対応キャラ）
- 分け方: カード単位ではなく**構築単位**。キャラ 3 人組と中核の機構の組をまとまりとして学習と評価に分ける。1 枚違いの姉妹デッキを割らない
- 最終評価のデッキは作ったら封印する（学習・較正・候補選びに使わない。相手側としても教材に出さない）
- デッキ JSON の sha256 を分割の定義に保存し、あとから中身を変えない

作り方の案（§5 判断 3）:
- (a) マスターがデッキ構築ツール（アーティファクト）で作る
- (b) クロエが規則つきで合法な候補を生成し（キャラ 3 人組・色・コスト帯・機構の系統を層にして）、マスターが見て選ぶ
- (c) (b) の候補から、マスターが「実際にありそうな構築」だけを残す（(b) と同じ手間で質が上がる）

## 5. 判断が要る点（推しを先に書く）

1. **便の割り方と順序** → 推し: 1C-a → 1C-b → デッキ群 → 1C-c。1 便で変える要素は 1 つ
2. **`hand_public` を別の欄にするか** → 推し: 別の欄（champion の打ち方を変えない・D-118 裁定と整合）。汎用 AI の符号化で和を取る
3. **環境デッキ群の作り方**（★マスターの手間がかかる）→ 推し: (b)。クロエが 30〜40 候補を生成して、系統・色・コスト帯の散らばりを一覧にする。マスターは一覧を見て 20 を選ぶ（または差し替える）。
   マスターの手間の見込みは 1〜2 時間
4. **相手デッキ表を知っている前提で始めるか** → 推し: 知っている前提で始め、manifest に旗を立てる。計画書 §3.3-4 のとおり「未知リストへの対応」とは混ぜない。
   なお実際の対戦では相手のデッキ表は公開されないので、**この前提はいつか外す必要がある**（汎用 AI の後の段階の課題として残す）
5. **過去の異型戦の取り違え（§2 の落とし穴）を調べ直すか** → 推し: 調べ直さない。結論が「寄与 0 に近い」の古い測定で、いまの判断に使っていない。記録に「未確認」と残す
6. **PC への依頼の回数** → 推し: 1C-a と 1C-b の再ビルドを 1 回にまとめる（どちらも 1 日前後で、依頼は名指しの検査だけ）。1C-c は全検査が要るので別に 1 回
