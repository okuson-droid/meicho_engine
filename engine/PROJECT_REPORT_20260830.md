## この文書の読み方

これは「いままで何をやったか」と「これから何をやるか」を 1 本にまとめた文書である。
**この文書だけを読んで、環境を作り直し、すべての実験を再現できること**を目標に書いた。

構成は次のとおり。

| 章 | 中身 | こういうときに読む |
|---|---|---|
| §0 | 要約 | 全体を 3 分で把握したい |
| §1 | プロジェクトの定義（目的・制約・真実源・作業規約） | 何を守るべきかを確認したい |
| §2 | 全体像（何が何に依存しているか） | どこから手を付けるか決めたい |
| §3 | **第 1 部: 基盤** — エンジン・カードデータ・Rust・測定インフラ・対人アプリ | 仕組みを理解したい／直したい |
| §4 | **第 2 部: AI の系譜** — 作った AI 全部と、その結果 | 何が強くて何が失敗したか知りたい |
| §5 | **第 3 部: 分かったこと** — 横断する教訓 | 次の判断の材料がほしい |
| §6 | **第 4 部: これから** — 裁定待ち・候補・ロードマップ | 次に何をやるか決めたい |
| §7〜§10 | 付録: 再現手順・ファイル地図・用語・決定記録の索引 | 手を動かすとき |

**数字の読み方の約束**（この文書全体で共通）。

- 勝率のうしろの **±** は **95% 信頼区間**。「同じ条件で測り直したら、だいたいこの幅に収まる」という幅である。
  計算式は ±1.96√(p(1−p)/n)。**n（対局数）を必ず併記する。**
- 2 つの勝率を比べるとき、**区間が重なっていたら「差があるとは言い切れない」**と読む。
- 「差」と書いてあるものは、**同じシード（＝同じ初期局面・同じ山札順）で取った 2 本を、局ごとに対にして**
  測った値である。別々に測った区間を並べるより細かく差が見える。
- **採用の物差しは対局の勝率だけ**である。「予測の精度が上がった」を進捗とは呼ばない（理由は §5.1）。

**専門用語は初出で説明する。** 用語集は `GLOSSARY.md`。

### 0.2 いちばん大事な発見 5 つ

1. **予測が良くなっても強くならない**（D-038）。勝敗を当てる精度を上げる学習を 4 回やって、
   4 回とも対局では弱くなった。原因は特徴でも規模でもなく**目的関数**である。
2. **探索を強くするほど、評価の盲点が増幅される**（D-046）。
   「毎ターン 1 枚引く」キャラを作るのは、先読みしない規則ベース AI（28/40 局）の方が
   計画探索（5/40 局）よりずっと上手い。評価が表現できない便益を、強い探索ほど正確に捨てるからである。
3. **相手モデルは相手に依存する**（D-057〜060）。「相手は強い」と想定するネットは強い相手に効き、
   弱い相手に対しては前より外れる。自己対戦で反復すると「自分と同じ強さの相手」に特化していく。
4. **champion はカードプールごとに選ぶもの**（D-047・D-058）。
   SD001 で効いた手当てが SD02 で効かない例が複数出た。
5. **「カード ID が違う」と「カードが違う」は同じではない**（D-061）。
   SD001 と SD02 はカード ID の共通が 0 種だが、**機構の仕様で数えるとアクション 17 種中 7 種が共通**である。
   いまの符号化はそれを別物として扱っていて、学習の転移が失敗する理由の説明になっている。

## §1. プロジェクトの定義

### 1.1 目的と優先順位

対象は TCG『鳴潮：対決』（UCP・2026-09-12 発売）。目的は
**このゲームをデジタル化・シミュレーションし、マスター自身の対人勝率を上げること**である。
優先順位は次のとおり（プロジェクト設定）。

1. **マスターより強いプレイング AI の育成**
2. マッチアップ勝率行列とデッキリスト最適化
3. 環境（メタ）予測

**バランス調整の提案は目的外**である。既製品の解析であり、ルールの改変はしない。

この優先順位は判断のたびに効いてくる。たとえば §5.3 の「相手モデルが champion 専用に尖る」問題は、
**マスターは champion ではない**という一点で「目標から遠ざかる方向」と判定できる。

### 1.2 制約

- **カード画像・公式テキストの複製をそのまま含む成果物を公開しない**（個人研究用途に留める）。
  この制約は §4.8 の「カードの埋め込みを Word2Vec で作るか」の判断にも効いた（§5 参照）。
- ローカル PC は低スペック前提。学習・大規模シミュレーションは Kaggle / Colab 等の外部資源で行い、
  Hugging Face は学習済みモデルと結果の置き場として使う。
- 速度不足時はホットループを Rust に移植し、リファレンス実装と同シード同結果の一致テストで検証する（D-001）。

### 1.3 真実源（ここが食い違ったら全部が崩れる）

| 対象 | 真実源 | 補足 |
|---|---|---|
| ルール | `rules_draft.md`（現行 **v0.10**） | 作業の冒頭に準拠バージョンを明示する |
| 設計判断 | `decisions.md`（D-001〜**D-061**） | 新しい判断は必ず追記。**D-055 は欠番**（案のまま未裁定） |
| カードデータ | `meicho/cards.py` | Rust は `cards_export.cards_json()` 経由で受け取るだけ |
| ゲームロジック | `meicho/engine.py`（**Python が真実源**） | Rust は追従。同一性テストが両者を結ぶ |
| champion の定義 | `experiments/champion.py` | ラダー・アプリ・発見ループがここを見る。**3 か所が食い違うと検査が落ちる** |
| シード帯 | `experiments/seed_bands.json` | 未登録帯での実行はツールが拒否する |
| 報告の作法 | `REPORTING_RULES.md` | 機械学習の専門知識を前提としない |

### 1.4 作業規約（8 か条）

1. **ルールと実装の対応**: コードとテストに `rules_draft.md` の条項番号をコメントで示す。
   ルールの未定義箇所に遭遇したら推測で補完せず、未定義事項として列挙して報告する。
   ルール変更は `rules_draft.md` の版を上げてから実装に反映する。
2. **決定性**: 状態は非破壊更新。乱数は `(seed, rng_calls)` 由来のみでグローバル乱数は禁止。
   `GameState` の JSON 直列化可能性を維持する。
3. **同時手番**: 対抗ステップは「`decision_players` が決定要求者を返し、全員分の行動が揃ってから
   `apply` が解決する」構造。**この構造を壊す変更をしない。**
4. **カードデータ**: 未確認テキストは `unverified` フラグ付きプレースホルダとし、確認済みデータと明確に区別する。
5. **テスト**: ルール裁定の変更・カード追加時は対応テストを**先に**書く。
   全テスト通過を作業の完了条件とし、テストが落ちた状態で完了扱いにしない。
6. **統計**: 勝率等の比較には対戦数と 95% 信頼区間を併記し、それを下回る差で優劣を断定しない。
   シードを記録し全実験を再現可能にする。
7. **簡略化**: D-004 の自動選択（コスト支払い・捨て札等）は暫定。戦略的に意味を持つと判明した時点で選択肢化を提案する。
8. **報告**: マスターは機械学習の専門知識を持たない前提で報告する。ただし内容は一切省略せず、
   必要に応じて解説を挟む。分量が増えるのは構わない（`REPORTING_RULES.md`）。
   **マスターに手を動かしてもらう依頼は手順を省略しない**（同 §2.6・D-058）。

## §3. 第 1 部: 基盤 — 何を作ったか

### 3.1 ゲームの構造（AI 設計に効く部分だけ）

このゲームの、AI の設計を決めた 4 つの性質。

1. **同時手番がある**（対抗ステップ・§6.4）。両者が伏せて出し、同時に公開する。
   → **相手が何を出すかの信念（相手モデル）が構造的に必要**になる。囲碁・将棋には無い要素で、
   AlphaZero 型の手法がそのままでは使えない理由の 1 つ（§5.3）。
2. **不完全情報がある**（相手の手札が見えない）。
   → 先読みは「ありうる手札を抽選して埋める」**決定化**で行う（D-026）。
3. **3 すくみ**（赤 > 緑 > 青 > 赤・§2.2）。ただし後述のとおり、
   「相手の色を踏む」は実ゲームでは逆効果だった（§4.2）。
4. **Lv0【対抗】スキルは勝敗を問わず発動する**（§6.4(1)-4）。
   → 対抗で負けてもリソースが残るので、自分の担当色を出し続けるのが得になる。これが 3 の理由。

1 局はおよそ **12.8 ターン・95〜97 決定**（SD001 同型・実測）。SD02 は 10.3 ターンと短い。

### 3.2 エンジン（`meicho/engine.py`）

**純粋関数 API**。状態は非破壊更新で、JSON に直列化できる。

| 関数 | 役割 |
|---|---|
| `initial_state(config, seed)` | 初期局面 |
| `decision_players(s)` | **いま誰の決定が必要か**（複数返れば同時手番） |
| `legal_actions(s, pi)` | 合法手の列挙 |
| `apply(s, actions)` | 全員分の行動が揃ってから解決（非破壊） |
| `outcome(s)` | 勝敗（`None`／0／1／`DRAW`=−1） |
| `observe(s, pi)` | **pi から見える情報だけ**を返す |

`observe()` が要になっている。**AI は `observe()` の出力しか受け取れない**ので、
覗き見（隠蔽情報の利用）が構造的に起きない。学習データの保存単位も `observe()` である（D-037）。

#### 効果解決は中断・再開できる（D-022）

「1 枚引き、手札 1 枚を捨てる」のような効果は、ドローが終わってからでないと捨て札を選べない。
そこでプレイヤーの選択が必要な地点で `Phase.CHOICE` に移り、選択が揃ったら中断地点から再開する。
待ち行列は 3 層あり、すべて `GameState` に JSON で持つ。

| 層 | フィールド | 内容 |
|---|---|---|
| スキル | `pending_skills` | `[player, "chara"/"action", card_id, skill_index]` の列 |
| オペコード | `pending_effect` | `{"owner", "ops"}` 解決中スキルの残りオペコード |
| 一時情報 | `pending_ctx` / `pending_shared_ctx` | `switched_leader_to` / `bonus_damage` |
| 再開地点 | `choice_resume` | `judge` / `after_judge` / `turn_start` / `turn_end` / `rush_damage` / `action` |
| 復帰先 | `phase_before_choice` | 選択待ち直前のフェイズ |

**新しい選択肢を足すときは 4 箇所**: `_step_effect`（積む）→ `legal_actions` の CHOICE 分岐 →
`_apply_choice`（処理）→ テスト。新しい再開地点は `_dispatch_resume` に追加する。

`_queue_fire` / `_do_rush` / `_begin_turn` は**積むだけ**で、実際に進めるのは `_pump`。
`apply` が最後に必ず `_pump` を呼ぶ。エンジン内部関数を直接呼ぶテストは `_pump` も呼ぶこと。

### 3.3 カードデータ（`meicho/cards.py`）

現在の登録簿は **53 種**（キャラ 18・アクション 35）。スターターデッキ 2 種ぶん。

- SD001: 漂泊者（女）・秧秧・熾霞
- SD02: 漂泊者（男）・散華・今汐

各デッキ キャラ 9 枚・アクション 17 種・計 40 枚。

カードは**データではなく仕様**として書かれている。効果は **20 種のオペコード列**で、
エンジンがそれを実行して対局が成立する。

```
damage_opponent / dedicated_leader_card_damage_buff / discard_self / draw /
draw_if_switched / forbid_leader_switch_this_turn / forbid_rush_next_turn /
heal_self / opponent_pay_or_damage / peek_opponent_hand / pursuit /
raise_opponent_red_cost_next_turn / return_clash_card_to_hand /
reveal_top_to_hand / rush_damage_buff / self_damage_buff /
self_damage_buff_if_switched / switch_leader / top_to_concerto /
top_to_concerto_if_switched
```

**カード 5 枚につきオペコード 1 個**という増え方をしている。100 枚のブースターが入れば語彙は倍増する見当。

**新オペコードを 1 個足すときに触る場所は 3 箇所**:
`engine.py::_apply_op`（未知は `ValueError` で落ちる＝安全）／`rust/src/cards.rs`（`Op`）／
`rust/src/engine.rs::apply_op`。加えて `view._op_text`（画面表示・全カード検査あり）。
**`state`/`features`/重みは黙って古いまま動くので危険**である。

#### カード入力の運用ルール（次回以降も踏襲）

- 入力はチャット直書きのコピペ用テンプレート（キャラ用／アクション用）。MD ファイル添付は不評。
- カード番号未確定は仮 ID `<セット名>-T##`（アクション）／`-C##`（キャラ）。
- **同名カードでも専用キャラが異なれば別カード**。
- 「専用キャラ」欄と「リーダースキルの有無」欄は別概念（D-009）。
- キャラは Lv0/1/2 を揃えてから **Lv0 と Lv2 が入れ替わっていないか**確認する。
  標準形: Lv0=【対抗】色条件／Lv1=【判定】敗北時（全キャラ同一構造）／Lv2=キャラ固有。
- **入力欄の空欄・記入漏れは埋めずに確認する。**
- **デッキの枚数配分を早めに聞く**（受領済み種類数の検算になる）。
- 反映は「1 枚ずつ受領 → まとめて反映」。pytest 全通過と実デッキ自己対戦スモークまでが完了条件。
- **疑問点は指摘してよいが、返答を待たず受領どおり確定する**（作業を止めない）。

**教訓**: SD001 の入力中に、発売前に写真から起こした SD02 データの誤り 2 件と実装バグ 1 件（D-016）が見つかった。

### 4.2 ヒューリスティック（H・規則ベース）

### 4.3 貪欲（greedy）

`meicho/greedy.py`。1 手先読み＋評価関数。対 H 0.673。

**評価関数は 6 項の重み付き和**（`greedy.evaluate`）:

```
v = w_life     × (自ライフ − 相手ライフ)
  + w_concerto × (自協奏 − 相手協奏)
  + w_hand     × (自手札 − 相手手札)
  + w_live_red × 使える赤の枚数
  + w_level    × (自レベル合計 − 相手レベル合計)
  + w_resource × (自デッキ+トラッシュ − 相手デッキ+トラッシュ)
勝敗確定時は ±10000（WIN 番兵）
```

**この値は勝率ではない**——後述の D-059 で重要になる（§4.8）。

貪欲が担当するのは既定で**対抗ステップと連撃だけ**である。アクションフェイズでは弱い（0.338）ため
ヒューリスティックに委ねる（`GREEDY_NOTES.md`）。

### 4.4 計画探索（planner）— 現 champion の土台

`meicho/planner.py`。**アクションフェイズを「1 手」ではなく「ターン内の行動列」を単位に探索する**（D-027）。

- 1 ターンぶんの行動列の候補を作り、それぞれを固定方策で自分のターン末まで進めて葉を採点する
- **決定化**（相手の手札とデッキ順を抽選）を `plan_samples` 回行い平均する
- **共通乱数（CRN）**: 候補どうしを同じ乱数列で比較する（分散を抑える）
- 対 H 0.880〜0.923。**強さの半分は分散抑制から出ている**

#### 重みの調整は CEM（D-028）

**単軸掃引はしない。** `hand`/`concerto`/`live_red` はそれぞれ単独では改善して見えたが、
組み合わせると勝率 0.063 まで落ちた。`experiments/optimize_cem.py` が重み × Params を同時に探索する。

- 探索: シード 0..29 / 相手 {H_default, X1, X2}
- 検証: シード **10000..** / 相手に **X3・貪欲・調整前の自分**を追加（探索中は一切見ない）
- 結果: 対 H 0.773 → 0.887（n=300）。未使用シード帯・未使用の相手でも同等に改善

**派生した重要な知見: 重みは探索器と切り離せない。**
`w_level` の最適値が探索の構造で反転した（1 手貪欲では 0.0・1.0 にすると勝率 0.250 まで落ちる。
ターン計画では 0.498 が選ばれた）。**探索の構造を変えたら重みは必ず測り直す。**

`_value_after_turn` は `if u.turn_no != turn0 and u.phase != Phase.CHOICE: break` で打ち切る。
見ているのは「このターンの終わりの局面」までである。

**次のターン以降に効く持続効果は、費用だけが見えて便益が見えない。**
詳しくは §5.2。

### 4.5 IS-MCTS（B-1・D-033）— 届かなかった

### 4.6 相手モデル — 3 回の物語

#### (1) B-3: 色の履歴モデルは効かなかった（D-031/D-032）

**不採用（既定オフ）**: その履歴を使う相手モデル。差分は全て CI 内。

**なぜ効かないか（診断で特定）**:

→ **対抗の最適手が相手の色にほとんど依存しない。**

### 4.7 学習価値関数（C-1・D-038）— 1 度目の敗北

**「勝敗を当てる回帰」で評価関数を学習する**試み。

| | 検証の対数損失（低いほど良い） | 対 H（n=300・帯 110000..） |
|---|---|---|
| 現行 `evaluate`（CEM の 6 重み） | 0.5601 | **0.920 ±0.031** |
| logit6（同じ 6 特徴を予測で当て直す） | 0.5352（**有意に良い**） | 0.830 ±0.043 |
| logit22（22 特徴） | 0.5241（**有意に良い**） | 0.817 ±0.044 |

**予測では勝ち、強さでは負けた。**
引継ぎ書に書いてあった「超えないなら特徴が足りない証拠」は**外れ**で、足りないのは**目的関数**だった。
同じ 6 特徴で重みだけ当て直した logit6 が予測で勝ち強さで負けた（特徴を固定した対照実験）。

**機構**: 回帰は「その局面にいる者が勝つ確率」＝**観察的相関**を当てる。
探索が要るのは「そこへ動かしたときの良さ」＝**反実仮想の順序**である。

決定的な証拠が重みの符号反転にある。`level`（レベル差）の重みが **+0.498 → −0.197** になった。
レベルアップは手札を払う行動なので、データ上は「手札を減らした直後」と相関し、回帰は負の重みを付ける。

**潰した仮説**（すべて否定）: 飽和・凍結特徴（重みの 7.3% のみ）・共線性（共線性の無い logit6 も同じく弱い）。

**裁定**: 「予測が良くなった」を強さの代理指標にしない。価値関数の受け入れはラダー（D-034）のみ。

#### 段階 2 で見つけた 2 つの実装上の落とし穴

引継ぎ書に書いてあった段階 2 のコマンドは、**2 か所ともそのままでは意図どおり動かなかった**。

1. **`--policy-net` は champion の口ではない。** planner には学習した方策を差し込む口が 2 つある。

   | 口 | 何を覆うか |
   |---|---|
   | `policy_net` | 自分の**代打ち**（探索の中で非担当フェイズを埋める部分）と相手の手一般 |
   | `opp_policy_net` | **相手が対抗ステップで提出する手**だけ |

   現 champion は `opp_policy_net` ＋ `opp_policy_root_only`（根の対抗だけ）である。
   → `drl_record.py --champion` を新設し、`champion.py` の定義をそのまま両席に置くようにした。

2. **`--lam 0.5` は教師をでたらめにする。** `--lam` は V の教師を勝敗 z と探索値の混合にするつまみだが、
   **混ぜる探索値は `greedy.evaluate` の重み付き和であって勝率ではない**（§4.3）。
   実測（SD001・下見 200 局・19,074 決定）:

   | | 値 |
   |---|---|
   | 範囲 | **−10000 〜 +10000** |
   | 中央値 | 0.33 |
   | 5% 点 / 95% 点 | −10.4 / +2499 |
   | **[0,1] に収まる割合** | **10.0%** |

   旧実装は `[0,1]` に落ちた 10% だけを混ぜていた。つまり
   **「たまたま 0〜1 に落ちた決定だけが別の目標を持つ」**という教師で、エラーも警告も出ない。
   → 1 変数のロジスティック較正 `calibrate_vsearch`（探索値 → 勝率）を実装し、
   **較正なしの `--lam > 0` は拒む**ようにした。較正は自分の質を申告し、
   基準（「常に平均勝率と答える」）を下回らなければ学習を止める。反復 1 は λ=0 で回した。

**温度も 0 にした**（引継ぎ書の τ=0.05 を採らない）。学習する π の用途は相手モデル、すなわち
「champion は次に何を出すか」の予測である。champion は温度 0 で打つのだから、
教師も温度 0 で打たせないと π は**実在しない打ち方**を学ぶ。
なお τ=0.05 は探索値の目盛り（1 決定内の最大−最小が中央値 2.97）に対して小さすぎ、混ぜる効果もほぼ無い。

### 4.9 自動発見ループ（D-051〜D-054）

**champion の方策を機械的に少し変えた挑戦者 δ を語彙から生成し、勝てるものを探す仕組み。**
人間が仮説を出さなくても改善が見つかるかを試した。

```

 → 挙動確認（対 champion・30 局・同一シード・digest 比較。一手も変わらなければ測らない）

 → 境界（0.50〜0.52）なら再確認して合算
```

### 4.10 対抗ステップの CFR（2026-08-22）— 主結果は実ゲームで逆転した

対抗ステップだけを 1 手番の同時手番ゲームとして切り出し、CFR（後悔最小化）で均衡混合戦略を求めた。

**均衡の主結果**: 「相手のリーダーが得意な色を 3 すくみで踏む」。

**しかし実ゲームで逆転した。** 1 手番モデルは手札の枯渇を無視している（毎反復まっさらな手札を引き直す
＝手札が i.i.d. という仮定）。実測すると:

- 均衡戦略に従うと **青 −5.2pt / 緑 −3.9pt** 想定より出せない（赤だけ想定どおり +1.4pt）
- パスが想定 1.1% に対し実測 8.8%
- **自分の方策が自分の選択肢を狭める**: 青の可用性 70.2% → 66.1%、緑 70.8% → 65.2%
- 実ゲームの対抗の 43% は学習分布の外側（学習は手札 4 枚固定、実測は平均 5.41 枚）

**「常に青が安全」は 1 手番モデルの錯覚。青は温存資源として扱う。**
実ゲームでの結論は `heuristic_agent`（自色を出し続ける）が優先する。

### 5.1 予測が良くなっても強くならない（4 連敗・同じ形）

このプロジェクトは**同じ形の失敗を 4 回している**。

| 回 | 何をしたか | 予測 | 強さ |
|---|---|---|---|
| D-038（C-1 線形） | 6/22 特徴で勝敗を回帰 | **有意に良くなった** | 対 H 0.920 → 0.830／0.817 |
| D-038（C-1 交互作用） | logit22x | 有意でない | 同上 |
| D-057（段階 1 の V） | 深層ネットで勝敗を回帰し、planner の葉に挿す | — | 対 champion **0.383** |
| D-059（段階 2 の π） | 教師を強くして π を学習し直す | 一致率 0.735 → 0.747 | ラダー 3 位（素の planner にも負ける） |

**4 回とも「予測を良くする目的関数」を使い、4 回とも対局で負けた。**

**機構**: 回帰は「その局面にいる者が勝つ確率」＝**観察的相関**を当てる。
探索が要るのは「そこへ動かしたときの良さ」＝**反実仮想の順序**である。この 2 つは違う。

**この 4 連敗のうち、原因（目的関数）の診断に基づく作り直しは一度も試していない。**
これが §6.2 の案 A（V の目的関数をペアワイズ順位づけに変える）を推す理由である。

**規約**: 「予測が良くなった」を進捗と呼ばない。採用の物差しは対局の勝率だけ（D-038 の裁定）。

### 5.2 探索を強くするほど、評価の盲点が増幅される（D-046）

漂泊者（女）Lv2 は【ターン開始時】無条件で 1 枚引く（`leader_only=False`・バックでも効く）。
これを最短で作ると当時の champion に **0.555 ±0.040（下端 0.515・n=600・別シード確認）**で勝ち越す。
**遅らせる（7 ターン目から）と 0.467 ＝ 優位消失。効いているのは早さである。**

ところが、そこへ行けるのは弱い AI の方だった。

| エージェント | 先読みの深さ | 漂泊者 Lv2 到達（対 H・40 局） | 到達ターン |
|---|---|---|---|
| 計画探索 | 実質 1 ターン | **3〜5 / 40** | 7.7 |
| IS-MCTS(160) | ロールアウト 2 ターン | 12 / 40 | 10.8 |
| 貪欲 | 1 手 | **28 / 40** | 4.9 |
| H | **先読み無し** | **28 / 40** | 4.4 |

**先読みが浅いほどよく到達している。**

原因は 3 つあり、分けないと直せない。

1. **地平**: `_value_after_turn` が自分のターンの終わりで打ち切る（§4.4）
2. **表現**: 22 特徴は全部集計値。`level_me` は 3 枠の合計で「誰の」レベルかを持たない。
   **漂泊者 Lv2（毎ターン 1 枚引く）と秧秧 Lv2（条件付き）が同一の入力になる。**
   同じ入力に違う出力を返す関数は無いので、**重みでも MLP でも埋まらない**
3. **学習の素材**: 自己対戦の観察データは因果でなく相関。しかも
   **Simpson のパラドックス**が起きている——漂泊者 Lv2 の有無と勝率は
   エージェント別ではどの群でも正（H 0.107→0.233 / 貪欲 0.222→0.379）なのに、
   まとめると負に見える。作るのが主に弱いエージェントだから。
   **これが D-038 の `level_diff = −0.197` の正体。モデルの失敗ではなくデータの性質である。**

**H が正解するのは賢いからではなく、評価していないからである。**
評価が表現できない便益は、探索が強いほど正確に捨てられる。

**対策 A（地平を 1 ターン延ばす）は実測済みで効いた**が、SD001 でしか効かなかった（§5.4）。

| | SD001 | SD02 |
|---|---|---|
| 対策 A: 地平の延長 | **0.567 ±0.028**（n=1200・下端 0.5386） | **0.483 ±0.040**（n=600） |
| 対策 B: 持続効果を特徴に | 0.490 | 0.463 |

到達率は 3/40 → **17/40**、到達ターン 13.7 → 7.4。代償は速度 2.53 → 1.52 局/秒（1.66 倍）。
**採否は未判断のまま**（bake-off の候補として残っている）。

### 5.3 相手モデルは相手に依存する（D-057〜060）

**同じネットが、使い道によって正反対の結果になる**（§4.8 の表）。理由は一言で言える。

- **方策**の良し悪しは「**勝てる手を選べるか**」で決まる。強い教師をまねれば、誰が相手でも良くなる
- **相手モデル**の良し悪しは「**その相手の手を当てられるか**」で決まる。強い教師をまねると、
  **弱い相手に対しては前より外れる**

**−0.166 の大崩れの正体**: π₀ は**素の計画探索の対局から作られたネット**である。
相手が素の計画探索なら、π₀ は「その相手そのもの」を学んだほぼ完璧なモデルであり、
π₁ はそれを捨てて別の相手を学んだ劣化版になる。
**反復のたびに、前の版が想定していた相手を忘れる。**

**H だけがどちらの用途でも損なのは**、学習データ（champion どうしの対局）に
H のような手が一度も現れないから。目的関数ではなく**データの偏り**の問題で、対策はリーグである。

#### AlphaZero がそのまま使えない 3 つの理由

1. **同時手番がある** → 自分の提出を採点するには相手の提出の信念が要る。
   **相手モデルは構造的に消せない。** AlphaZero は逐次手番の完全情報ゲームを前提にしていて、
   そこには相手モデルという部品がそもそも無い
2. **不完全情報がある** → 自己対戦で強くなる保証を与えるのは AlphaZero ではなく CFR 系である。
   **「特定の相手への最適応答は必ず別の相手への隙になる」**——反復 1 はそれを実演した
3. **探索が全列挙**（D-033: 分岐が小さいと全列挙が UCB に勝つ）→ 方策の事前確率で枝を絞る余地が小さい。
   **このゲームで AlphaZero 型が効くとすれば、π ではなく V（葉の採点）である**

### 5.4 champion はカードプールごとに選ぶもの（D-047・D-058）

**「カードを知らない改善は転移する」は誤りだった。**

| 改善 | SD001 | SD02 |
|---|---|---|
| 対策 A（地平の延長） | **0.567** | **0.483** |
| 対策 B（持続効果を特徴に） | 0.490 | 0.463 |
| 相手モデル = π | **0.540（採用）** | **0.493（門番を越えない・据え置き）** |
| SD001 産の π を SD02 に転移 | — | **0.449（悪化）** |

理由: 無条件の持続効果を持つキャラは SD001 が 2 枚、**SD02 は 1 枚だけ**（今汐 Lv2・リーダー限定・小さい）。
**A の勝ち越しは A が優れていたからではなく、SD001 に A が拾えるカードが入っていたから。**

> **改善が転移するかは「カードを知らないか」ではなく「その改善が拾う性質のカードが新プールにあるか」で決まる。事前には分からない。**

**運用**: `experiments/champion.py` がプール名 → 追加引数の表を持つ唯一の真実源。
SD001 は「相手モデル=π」版、SD02 は素の計画探索。

一方で**骨組みの転移は良好**（n=300・同型）: 計画探索 vs H は SD001 0.883 → SD02 0.837、
貪欲 vs H 0.707 → 0.610、計画探索 vs 貪欲 0.753 → 0.767。
22 特徴が集計値なので個々のカードを見ず、プールが変わっても意味が変わりにくい。
**D-046 で「悪い」と書いた性質の裏面。集計は転移するが鈍い、個別は鋭いが陳腐化する。**

#### D-061 の訂正: 「共通 0 種」は ID で数えた値だった

D-058 が転移失敗の理由として記録した「共通 0 種」は**カード ID で数えた値**である。
カード ID もカード名も専用キャラ名も使わない**機構の仕様**で数え直すと:

| | ID | 名前 | **機構の仕様** |
|---|---|---|---|
| アクション（各 17 種） | **0** | 7 | **7** |
| キャラ（各 9 種） | **0** | 0 | **2** |

機構が一致した 9 組は**すべて「専用キャラだけが違う同じカード」**。
うち 2 組は名前まで違う（羽の刃・回避／冷徹な光・回避、息継ぎ／凛然浄化）ので、名前を鍵にしても繋がらない。
**2 つのスターターデッキは、同じデッキのキャラを入れ替えたものである。**
素性（オペコード・タイミング・条件・タグ・数値）の共通率は SD001 側 **75%** / SD02 側 **82%**。

**転移が効かないのは「共有するものが無い」からではなく、
「共有しているものを符号化が見せていない」からかもしれない**——これが §6.2 の案 E の仮説である。
**ただし仮説である**（SD02 専用の π ですら門番を越えなかった 0.493 は符号化では説明できない）。

### 5.5 デッキ構造（赤 55% の正体）

SD001/SD02 とも種類数は 赤 11 / 青 3 / 緑 3。§3.2「同カード番号は 3 枚まで」により
非赤は最大 (3+3)×3 = 18 枚。よって**赤の下限 = 40 − 18 = 22 枚 = 55%**。
**赤 55% はデッキ構築の選択ではなく、カードプールに強制された下限である。**

そして**その大半は常に死に札**である。

- 赤 22 枚のうち **10 枚（45%）がリーダースキル条件**（共鳴スキル・共鳴解放）を持つ
- リーダースキルは自分がリーダーのときしか使えない。3 キャラ編成なので**約 2/3 が常に死に札**
- **実効的に使える赤は 22 枚中 13〜15 枚（デッキの 33〜37%）**で、青緑の合計 18 枚（45%）と大差ない

**決定的な実測**: 連撃したいのにできなかった 4,273 回の内訳は
リーダー条件不一致 61.5% / コスト不足＋リーダー条件 34.1% /
**手札に赤が 1 枚もない 2.7%** / コスト不足のみ 1.8%。
そのとき手札には平均 3.08 枚の赤があった（持っているのに撃てない）。
赤を 55% → 82.5% に増やしても赤切れ率は 71% → 70% とほぼ不変。**枚数はボトルネックではない。**

**この発見はカードの類似度からは絶対に出てこない。出したのはシミュレーションである。**
（§6.2 の案で「埋め込みはデッキ構築の主用途にしない」と判断した根拠。）

### 5.6 行動の価値は対照実験で直接測る（D-039・D-043）

シミュレータを所有しているので「やった世界／やらなかった世界」を両方走らせられる。
**両枝で同じシード（共通乱数）**を使うと対応のある比較になり、少ない対局数で差が見える。

レベルアップについて測った結果:

| 方向 | 結果 |
|---|---|
| **減らす**（禁じる） | 今やる vs 1 ターン待つ −0.013 [−0.050, +0.025]／一切やらない −0.030 [−0.077, +0.013] ＝**差なし** |
| **増やす**（必ずやる） | 直接対決 **0.375 ±0.067**／対 H 0.770 vs 通常 0.890 ＝**はっきり悪化** |

通常の計画探索は機会の **31.7%** でしか実行しない。
**応答は 0% ≒ 31.7% > 100%。現状は平らな部分にいる。**

> **方法論の教訓（最重要）: 禁じる版だけでは応答の形が分からない。強いる版も作れ。**

**負の結果もある**: 「捨て札の選び方が下手だから損」という筋の良い仮説を測ったら、
1 手先読みで捨て札を選ぶ版は対 H **0.695**（さらに −0.075 悪化）。
**壊れた評価関数で丁寧に選ぶと、大雑把な経験則より悪くなる。**

### 5.7 測定の作法（8 か条）

このプロジェクトが実際に踏んだ地雷から作った規則である。

1. **同型自己対戦だけで規則の寄与を判断しない。** 最低 3 条件（同型・異型・その部品が実際に使われる文脈）
2. **探索空間は「その探索器で実際に発火する軸」に絞る。** 基準値と完全一致したらその軸は no-op
3. **境界の結果は新しいシード帯で追試してから採用する。**
   26 件の摂動のうち 1 件が有意に見えたが追試で再現しなかった。
   **26 回比較すれば CI95% の境界付近は 1〜2 件出るのが当たり前**
4. **探索と検証はシード帯と相手プールの両方を分ける**
5. **学習に使ったシードで評価しない。** 帯の「番号」ではなく実際に使うシードの範囲で見る（汚染量 約 +0.02 の実測あり）
6. **新旧を比べるときは対照を同じシードで測り直す。** 別々の帯の勝率を引き算しない
7. **同じシードで取った 2 本の差は、局ごとに対にして測る。**
   対 H で 1,200 局中 1,007 局は結果が同じ。入れ替わった 193 局の内訳（72 対 121）から
   差 −0.041 ±0.023 が出る。別々の区間を見比べるより明確
8. **門番（対 champion）だけで採否を決めない。ラダーで総合の順位も見る。**
   「現 champion にだけ勝つ」は D-059 で実際に起きた

### 5.8 やり方そのものから学んだこと

- **decisions.md の一行目に測定の範囲を必ず含める**（2026-08-25 レビュー）。
  覆ったのは測定ではなく「見出しの範囲」だった
- **1 例から原則を測る前に書かない。** 仮説台帳を作り、数で答える
- **測る前の「推し」を報告に混ぜない**（`POOL_GROWTH_PLAN.md` は 2 回書き直した）
- **引継ぎ書に書くコマンドは、次のセッションでそのまま実行される。**
  口の名前が似ているだけの別物（`policy_net` と `opp_policy_net`）と、
  単位の違う数を混ぜる指定（`--lam` と探索値）は、どちらもエラーを出さずに進む。**書く前に一度自分で通すこと**
- **マスターに手を動かしてもらう依頼は手順を省略しない**（`REPORTING_RULES.md` §2.6・D-058）。
  「もう一度お願い」「同じ手順で」「前回と同様に」は**禁止**。必ず (1) どこで (2) 何を打つか
  (3) 成功したらどう見えるか (4) 確認のしかた (5) 転びやすいところ の 5 点を書く
- **「共通 0 種」のような決定的に見える数字も、何で数えたかを書いておく**（D-061 の教訓）

| 1 種あたりのデータが薄くなったら | 素性ベクトルを圧縮する（ここで初めて「数十次元」の話になる）。材料は素性ベクトルであってテキストではない |

**Word2Vec でテキストから作るのは不採用。** 理由:
(1) 効果オペコードという実行可能な正確な仕様がある（テキストは仕様の**説明**であって仕様ではない）、
(2) テキストの類似は機構の類似と食い違う（「1 枚引く」と「1 枚捨てる」は語が似て作用が逆、
「羽の刃・回避」と「冷徹な光・回避」は語が違って機構が同じ）、
(3) 公式テキストの複製はプロジェクトの制約に触れる。

**転びやすいところ**:

| 症状 | 意味 | 直し方 |
|---|---|---|
| `looks like a filename, but the file does not exist` → `OSError: [Errno 2]` | **ビルドしていない**（失敗ではない） | 2 に戻る |

| `アクセスが拒否されました` | `.pyd` を掴んでいるプロセスがある | 1 に戻る |
| `Couldn't find a virtualenv or conda environment` | `maturin develop` を使った | `maturin build` ＋ `pip install` に戻す（**`develop` は使わない**） |

**`--out dist` を省かないこと。** 省くと wheel は `target\wheels\` に出る。
`rust/dist/` はこのプロジェクトの wheel 置き場（Linux 版も同じ場所）で、行き先がずれると
「古い wheel を入れ直して入ったつもりになる」事故が起きる。
`CARGO_TARGET_DIR` も OneDrive の外に置くこと。

## §9. 付録 C: 用語

詳しくは `GLOSSARY.md`。この文書で使ったものだけ。

| 用語 | 意味 |
|---|---|
| **95% 信頼区間（±）** | 同じ条件で測り直したとき、だいたいこの幅に収まるという範囲。±1.96√(p(1−p)/n) |
| **共通乱数（CRN）** | 2 つの条件を同じ乱数列で比べること。差が見えやすくなる |
| **決定化** | 見えていない情報（相手の手札・デッキ順）を抽選で埋めて、完全情報のように扱うこと |
| **覗き見監査** | 隠蔽情報を差し替えても同じ手を選ぶかを再生して検査すること |
| **fingerprint** | 各局の結果を畳み込んだハッシュ。挙動を変えないはずの変更の受け入れテスト |
| **digest** | 1 局の全決定（誰が・どの手）を畳み込んだ 64 ビット。全局一致＝毎手同じ手 |
| **ガントレット** | ラダーで使う固定の相手プールの定義（JSON） |
| **Bradley-Terry / Elo** | 総当たりの勝敗から強さを 1 つの数に推定する方法。ここでは H を 1000 とする |
| **門番（D-034）** | 「現 champion との直接対決で 95% 区間の下端が 0.5 を超えたときだけ交代」という条件 |
| **非推移性** | じゃんけんの輪（A が B に、B が C に、C が A に勝つ） |
| **方策 π** | 局面を見て手を決める関数。ネットにすると「局面 → 各合法手の点数」 |
| **価値 V** | 局面を見て「ここから勝つ確率」を返す関数 |
| **模倣学習** | お手本が選んだ手を正解として、同じ手を選ぶようネットを学習させること |
| **専門家反復** | 探索の出力を教師にネットを学習し、そのネットを探索に戻して次のデータを作る、の繰り返し |
| **温度 τ** | 方策の確率分布を尖らせる／なだらかにするつまみ。τ→0 で最良手を必ず選ぶ |
| **リーグ** | 自己対戦の相手を「最新の自分」だけでなく過去の版や他の AI の集団にすること |
| **符号化** | 観測を、ネットが読める固定長の数値列に直すこと |
| **ワンホット** | カードの種類ぶん枠を用意し、そのカードの枠だけ 1 にする表し方。鋭いが初見に効かない |
| **埋め込み** | カード 1 枚を数値ベクトル 1 本で表すこと |
| **対数損失** | 予測の外し具合の指標。低いほど良い。当てずっぽうなら 0.693 |
| **Simpson のパラドックス** | 群ごとに見ると正の関係が、まとめると負に見える現象 |
| **カナリア** | 先に死ぬ鳥＝早期警報。ここでは漂泊者 Lv2 到達率 |
| **δ（デルタ）** | 発見ループで champion の方策を機械的に少し変える介入 |
| **in-sample 評価** | 学習に使ったのと同じデータ（ここでは同じシード）で性能を測ってしまうこと |
