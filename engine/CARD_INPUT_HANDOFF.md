## 1.1 SD001入力で得られた教訓（次回のカード入力で必ず使う）

- **既存データの誤りを2件発見した**。SD001のカードと突き合わせたことで、
  発売前に写真から起こしたSD02データの不備が露見した:
  (a) キャラカードのタグが「瑝瓏」のみで、属性・武器種が欠落していた（D-013）。
  (b) 「追撃N」が上書き実装になっていた（正しくは加算, D-012）。
  さらに実装バグも1件（「次のターン中〜」効果が1ターン多く持続, D-016）。
  **新デッキのカードが既存カードと食い違ったら、新デッキ側の誤記を疑う前に
  既存側が誤っている可能性も併せて検討すること。**
- **入力欄の空欄・記入漏れは埋めずに確認する**。実際に カード名の欠落・
  専用キャラの誤記（男/女）・タグの記入漏れ が発生し、いずれも確認して訂正できた。
- **マスターは「記載どおりで正しい」場合は返答しない**方針である（2026-08-21指示）。
  疑問点の指摘はしてよいが、返答を待たずに受領テキストどおり確定として控え、
  訂正が来たときだけ差し替える。ただし**ルールが未定義で実装が分岐する事項**
  （ライフ回復の上限など）は別枠で、必ず裁定を仰ぐ。
- **合計枚数による検算が有効**。「赤2枚ずつ・青緑3枚ずつで合計40枚」という
  マスターの申告と受領済みカード種類数が一致したことで、
  未受領カードがないことを確認できた。デッキ枚数は早めに聞くとよい。

## 2. カード入力の進め方（マスターとの合意事項）

### 2.1 入力フォーマット
コピペしやすいよう、**チャット本文に直接、コードブロックで**テンプレートを貼る。
MDファイルとして送るのは不評だったため使わない（ファイル添付だと編集しづらいとの
フィードバック）。テンプレートは以下の2種（キャラカード用／アクションカード用）。

```
カード番号:
カード名:
レベル: (0 / 1 / 2)
タグ:
スキル1:
  タイミング:
  条件: (無ければ「なし」)
  効果:
  リーダー限定: (はい / いいえ)
出典/備考:
```

```
カード番号:
カード名:
色: (赤 / 青 / 緑)
コスト:
スピード:
ダメージ:
タグ:
専用キャラ: (無ければ「なし」。デッキ構築の制約のみ、使用時にリーダーである必要はない)
リーダースキルあり: (はい / いいえ。「はい」なら必要リーダーは専用キャラと同一)
スキル1:
  タイミング:
  条件:
  効果:
出典/備考:
```

注意点（過去のやり取りで判明した仕様上の細部）:
- アクションカードのスキルに「リーダー限定」欄は**存在しない**。リーダー限定に
  相当する使用条件は、カード全体につく「リーダースキルあり」で表現する
  （§2.1の【リーダー】前置はキャラカード側のみの概念）。
- 「〜してもよい」（任意効果）かどうかは効果テキストの文面からこちらで判断する。
  マスターに入力してもらう項目には含めない。
- カード番号が本人にも分からない場合は空欄でよい。その場合は仮ID
  `SD001-T##`（T=Temporary、01始まり連番）を付与し、正式番号判明時に一括置換する
  想定で進める（decisions.md D-008参照）。

### 2.2 反映のタイミング
入力は1枚ずつ、こちらは受領のたびに作業ログへ控えるだけにとどめ、
**cards.py・テスト・デッキリストへの実反映はマスターが「まとめて反映して」と
言ったタイミングでまとめて行う**。毎回逐次コミットはしない。

### 2.3 データの疑問点は都度確認する
テキストの内容に既存登録との矛盾や、ルール上妙な点（色とタグの組み合わせが
通例と異なる等）を見つけたら、その場で率直に確認する。黙って合わせにいかない。
SD02では次の2件が実際にここで見つかった:
- 散華の回避カードの色を赤と聞いていたが、実は青の誤入力だった（マスターが後から訂正）。
- 漂泊者（男）・散華・今汐の3キャラすべてで、Lv0とLv2のスキルが登録時に
  丸ごと入れ替わっていた（cards.py上の既存データの誤り）。SD001でも同種の
  取り違えが無いか、Lv0/Lv2を両方受領した時点で一度疑ってみるとよい。

## 3. データモデル上の重要な仕様（D-009）

`ActionCard` の「専用キャラ」と「リーダースキル使用条件」は別概念。
- `dedicated_to: Optional[str]` … デッキ構築時、そのキャラがキャラデッキに
  含まれていないと採用できない、という構築時の制約のみ。使用時にリーダーで
  ある必要はない。
- `leader_skill: bool` … True の場合のみ、自分のリーダーが `dedicated_to` と
  同名でないと使用できない、という追加の使用条件（rules_draft.md 133行目）。
  リーダースキルの対象キャラは常に専用キャラと同一なので、専用キャラ名を
  二重に持たせる必要はない。

この分離はSD02反映時に、旧実装が両者を混同していたバグの発見とセットで行った
（`engine.py` の `_usable_in_clash` が、専用キャラを持つだけでリーダースキルの
無いカードにまでリーダー一致を誤って要求していた）。SD001でも「専用キャラ」欄と
「リーダースキルあり」欄を分けて聞く。

## 4. カード番号の仮ID運用（D-008）

- カード番号が未確認のカードには `SD001-T##` を付与する（SD02では `SD02-T##`
  を使った）。
- 既に登録済みでテストコード等から広く参照されているカード（SD02では
  `AC-001`〜`AC-007`）がある場合、無理に仮IDへ付け替えず、内容だけを確定
  テキストへ更新する方針を取った。SD001は真新しいカードセットのため、
  基本的にはすべて `SD001-T##` を新規付与することになる見込み。

## 5. 情報公開・継続効果など、エンジン未対応の効果への対応方針

SD02では以下のようなエンジン未対応の効果に遭遇し、それぞれ対応方針を決めた:
- 「相手の手札を確認する」等の一時的な情報公開効果: `observe()` が非対称情報の
  一時公開に未対応のため、暫定で no-op のオペコードとして実装する（D-010）。
  SD001でも同種の効果が出た場合は同じ方針で進めてよい。
- 「次のターン中、相手は連撃できない」のようなターンをまたぐ継続効果:
  `GameState` に予約フラグ（`pending_rush_forbidden`）と発動フラグ
  （`rush_forbidden`）を追加し、`_begin_turn` で予約→発動の切り替えを行う形で
  実装した。SD001で類似の継続効果（例: 「次のターン、〜できない」系）が
  出てきたら、この実装パターン（予約フラグ→対象プレイヤーのターン開始時に
  発動）を踏襲できる。

## 6. 反映作業のチェックリスト（まとめて反映する際に使う）

1. `cards.py` にカードを追加・更新する。ID・専用キャラ・リーダースキル・
   タグ・スキルのタイミング/条件/効果を、確認済みデータどおりに反映する。
   既存カードとの重複（同一カードの内容確定）が見つかった場合は、IDを
   維持したまま内容を差し替える（§4節参照）。
2. 新しい効果オペコードが必要なら `engine.py` の `_run_effects` /
   `_skill_condition_met` に追加する。既存の汎用オペコード
   （draw, top_to_concerto, damage_opponent, pursuit, discard_self,
   self_damage_buff, switch_leader系 等）で表現できないか先に検討する。
3. 対応するテストを `tests/test_engine.py` に追加する（ルール裁定変更・
   カード追加時はテスト先書きが原則）。
4. `python3 -m pytest tests/` で全テスト通過を確認する。
5. デッキリストが揃っていれば `decklists/SD001.json` / `.md` を作成し、
   `GameConfig.validate()` に通ることを確認するテストも追加する。
6. 実デッキでのランダム自己対戦スモークテスト
   （`scripts/sd02_selfplay_smoke.py` を複製・改修）を1000局程度回し、
   クラッシュ・異常な打ち切り率がないか確認する。
7. 新しい設計判断・意図的簡略化が発生した場合は `decisions.md` に
   D-011以降として追記する。
8. `README.md` の検証状況セクションを更新する。
9. すべての変更ファイルをユーザーのデバイス上の元フォルダへコミットする。
