# シミュレーション高速化方針

作成: 2026-08-23（レビューセッション） / 準拠: rules_draft.md v0.10 / 対象: engine v0.1
測定スクリプト: `experiments/bench_speed.py` / `bench_parallel.py` / `bench_fast_clone.py`
（シードは決定的。すべての施策で fingerprint＝勝者・ターン数・ライフ列のハッシュの
一致を確認済み）

測定環境: クラウド（2コア, CPython 3.11）。ローカルPCとは絶対値が異なるが、
**相対比較（何倍になるか）**は移植可能な情報として読む。

---

## 1. 必要な速度の見積り — 何倍足りないのか

現状（本環境実測）: ヒューリスティック 252局/秒、貪欲 25局/秒。
apply のスループットは約 24,000回/秒（1局 ≒ 95 apply）。

| 用途 | 必要規模 | 現状での所要 | 判定 |
|---|---|---|---|
| フェーズ3: 勝率行列・重み探索（CEM/TPE） | 300局×数百試行 ≒ 10^5局 | ヒューリスティックで数分〜1時間 | **足りる（並列化推奨）** |
| フェーズ4: IS-MCTS 対局生成 | 1決定に数百シミュレーション × 1局約100決定 ≒ 1局あたり10^4〜10^5 apply | 1局に数秒〜数十秒 | 桁不足 |
| フェーズ4: 強化学習（10^5〜10^6局） | 10^9〜10^11 apply | 単機Pythonで数週間〜年 | **2〜3桁不足** |

つまりフェーズ3は「並列化＋小さな積み上げ」で足り、フェーズ4は
**アルゴリズム的削減＋Rust移植（D-001）が本命**という二段構えになる。

## 2. プロファイル結果 — 単一の犯人はいない

cProfile（ヒューリスティック自己対戦30局）:

| 区分 | 割合 | 内訳 |
|---|---|---|
| apply 全体 | 54% | clone 約26% / 効果解決 _pump 約17% / その他 |
| エージェント側 | 39% | _action 13% / legal_actions 9% / _clash 7% / card_utility ほか |

**特定の関数がボトルネックなのではなく、インタプリタのオブジェクト操作コストが
全体に薄く乗っている。** したがってマイクロ最適化の上限は小さく（後述の実測どおり
1件あたり数%）、大きな倍率はアルゴリズム・並列・言語のレベルからしか出ない。

貪欲は事情が異なり、**時間の90%が対抗ステップの決定化サンプリング**
（標本×候補手×_settle の apply 連打）に集中している。こちらは
アルゴリズム的削減が直接効く。

## 3. 候補策の実測結果

| 施策 | 結果 | 決定性 | 判定 |
|---|---|---|---|
| **プロセス並列（対局をシードで分割）** | **1.91x／2コア**（コア数にほぼ線形） | fingerprint一致 | **採用** |
| **貪欲の標本数 6→3** | **1.95x**、勝率 0.653±0.054（6標本の 0.680±0.053 とCI内） | — | **採用** |
| **CPython 3.11→3.13** | **+15%**（252→291局/秒） | fingerprint一致 | **採用** |
| fast clone（dataclass `__init__` 迂回） | +6%（252→266局/秒） | fingerprint一致 | 余裕があれば |
| `python -O`（assert除去） | +7% | — | 測定運用のみ可（下記注意） |
| PyPy 7.3.15 (3.9) | **0.48x（半減・逆効果）** | fingerprint一致 | **不採用** |

注意:
- `-O` はエンジン内の不変条件チェック（assert）も消す。学習・大量測定の
  本番運転のみに限定し、開発・テストでは使わない。
- PyPy が遅い原因は確定していない（短命オブジェクト大量生成・旧版JITの相性と
  推測）。新しめの PyPy で再測する価値は残るが、優先度は低い。
  副産物として、**同シード同結果が処理系をまたいで成立する**ことが確認できた
  （`random.Random` のMT19937がCPython/PyPyで互換のため）。
- 貪欲は標本数2でも 0.637±0.054 でCI内（2.5x）。まず3で運用し、
  重み探索など大量に回す場面でだけ2に落とすのが安全。

## 4. 推奨する積み上げ（フェーズ別）

### 4.1 いますぐ（フェーズ3: 勝率行列・重み探索）

1. **実験ランナーの並列化**。`bench_parallel.py` の型
   （シードで分割 → `Pool.map` → 結果を並べ替えて集計）をそのまま
   実験スクリプトに移す。fingerprint一致で確認済み。コア数倍。
2. **貪欲の既定 samples を 6→3 に変更**（GREEDY_NOTES.md の数値を再測して更新）。
3. **CPython 3.13 へ移行**。コード変更ゼロで +15%。ローカル（Windows）でも
   `uv python install 3.13` で複数版を併用できる。
4. 余裕があれば fast clone（`bench_fast_clone.py` の実装を state.py に取り込み。
   フィールド追加時の更新漏れを防ぐテストを添えること）。

合算の目安: 4コアのローカルPCなら ヒューリスティック 250 → **約1,300局/秒**、
貪欲 25 → **約230局/秒**（3.13 ×1.15、samples3 ×1.95、並列 ×3.8）。
フェーズ3の重み結合探索（10^5局規模）が一晩から**数十分**の作業になる。

### 4.2 フェーズ4の入口（探索側のアルゴリズム的削減）

言語を変える前に、探索が呼ぶ apply の回数そのものを減らす。

- **ターン計画抽象**（REVIEW_2026-08-23.md §6 A-2）: アクションフェイズを
  1手ずつ木に展開せず「ターン内行動列」を1ノードに潰す。分岐9.1の数手分が
  1決定に縮み、MCTSの木が桁で小さくなる。
- **標本の適応化（racing）**: 決定化サンプリングで、数標本の途中経過で明らかに
  劣る候補手を打ち切る。標本数固定 6→3 の延長線で、統計的に安全な削減。
- **候補手のプルーニング**: 対抗の同色内は既に最大ダメージに絞られている。
  同様の支配関係（同効果でコスト高、等）を legal_actions の後段で刈る。
- **A-7（誘発順序）の枝刈り**: 結果が同じになる解決順序を列挙前に同一視する
  （SIMPLIFICATIONS.md A-7 の備考どおり）。

### 4.3 フェーズ4本格（Rust 移植, D-001）

強化学習の 10^9〜10^11 apply は Rust の領分。純Pythonのゲームエンジンの
移植では単コア **30〜100倍**（apply換算で毎秒10^6回級）が典型的な期待値で、
これで RL のセルフプレイが単機〜Kaggle規模に収まる。

移植の設計判断（decisions.md に起こすべき項目）:

1. **範囲**: apply / legal_actions / decision_players / observe のコアのみを
   Rust化し、PyO3 で Python から呼ぶ。エージェント開発・実験の柔軟性は
   Python 側に残す。全面移植は学習ループが Rust に移る段階で改めて判断する。
2. **乱数互換が一致テストの肝**: 現行は `random.Random(f"{seed}:{rng_calls}")`。
   文字列シードの初期化と shuffle/sample の消費列を CPython と厳密一致させる
   必要がある（MT19937 クレートに加え、CPythonのシード変換・Fisher-Yates の
   実装を揃える）。一致検証は fingerprint 方式（`bench_speed.py`）が
   そのまま受け入れテストになる。互換再現が高くつく場合の代替は、
  「シャッフル結果の列を Python 側で事前生成して渡す」方式
  （エンジンの乱数消費点は山札シャッフルに限られるため現実的）。
3. **clone戦略**: Rust側では毎手フルコピーをやめ、undo方式または
   アリーナ確保に置き換える（非破壊APIの見た目は境界で維持する）。

### 4.4 学習時（Kaggle / Colab / HF）

- 対局生成はシード分割の**恥ずかしい並列**なので、Kaggle/Colab の
  マルチコアCPUセッションにそのまま載る（`bench_parallel.py` の型）。
  シード範囲をジョブに割り当て、結果を結合すれば再現性も保たれる。
- 価値ネットワーク導入後は**葉の評価をバッチ化**（MCTSの仮想損失＋
  ミニバッチ推論）。GPUはここでだけ意味を持つ。ゲームロジック自体の
  GPU化・ベクトル化は、分岐とオブジェクト構造が支配的なため不適。

## 5. やらないこと（測って捨てた・構造的に不適)

- **PyPy**: 実測で半減（§3）。
- **numba / ベクトル化**: dict・list・Enum 中心のデータ構造で JIT/SIMD の
  対象にならない。
- **mypyc / Cython の部分コンパイル**: 期待値2〜5倍に対し、型注釈整備と
  ビルド複雑化のコストが Rust 移植と重複する。D-001 が既定路線である以上、
  中間投資はしない。

## 6. 決定性の担保（全施策共通の受け入れ条件）

高速化の変更は必ず fingerprint（勝者・ターン数・ライフ列のハッシュ、
seeds 0..49）の一致を確認してから取り込む。本方針の全施策で一致を確認済み。
`bench_speed.py` を回帰チェックとして流用できる（処理系・並列・コード変更の
いずれにも同じ物差しが使える）。

# B-2 実施記録（2026-08-23）

対象を**計画探索**に移して測り直した。以前の測定は貪欲が主役だった。
再現: `python3 experiments/bench_agents.py`（速度＋fingerprint）
/ `python3 experiments/bench_agents.py --profile`

## 結果（クラウド2コア・CPython 3.11・単プロセス）

| | 着手前 | B-2後 | 倍率 |
|---|---|---|---|
| ヒューリスティック同型 | 243.8 局/秒 | 287.0 局/秒 | 1.18x |
| 貪欲 vs H | 19.8 局/秒 | 28.8 局/秒 | **1.45x** |
| **計画探索 vs H** | 1.4 局/秒 | **2.1 局/秒** | **1.50x** |

**fingerprint は3つとも着手前と一致している。** 挙動は変わっていない。
勝率も 0.923 ±0.030（n=300）で B-2 前と同じ。

## 何が効いたか

### 1. `apply_owned` — ロールアウトの clone を省く（最大の効き）

`apply` は毎回 `state.clone()` してから書き換える（非破壊APIの規約）。
だが**ロールアウトの連鎖は自分で作った state を何十手も進めるだけ**で、
誰も元の state を参照していない。そこに clone は要らない。

`apply_owned(state, actions)` を追加し、`_settle` と `_value_after_turn` の
ループで使う。公開APIの `apply` は `apply_owned(state.clone(), actions)` に
なったので、外から見た非破壊性は変わらない
（`test_apply_is_non_destructive_and_apply_owned_is_not` で担保）。

clone の呼び出しは 97,894 → **37,181 回**（6局あたり）に減った。
計画探索で 1.77 → 2.1 局/秒（+19%）。

**前提条件に注意**: `apply_owned` は呼び出し側が state を専有しているときだけ
使える。`_search` が枝を展開するときの基準局面のように**共有される state には
使ってはいけない**。関数の docstring に前提を明記してある。

### 2. 高速 clone（`__new__` ＋属性直接代入）

`bench_fast_clone.py` の案を `state.py` に取り込んだ。dataclass の
`__init__`（既定値ファクトリの評価を含む）を迂回する。あわせて、
中断・再開用フィールド（`pending_*`）は空であることがほとんどなので、
空なら `_jcopy` を呼ばずに定数を置く。`_jcopy` 自体にもスカラの早期returnを追加。

**フィールドの足し忘れは静かに壊れる**ので、全フィールドに既定値と違う値を
入れてから複製し `dataclasses.asdict` で突き合わせる
`test_clone_copies_every_field` を置いた。実際に B-3 で足した `clash_counts` は
この形式でないと見落としていた（`bench_fast_clone.py` の案には入っていない）。

### 3. スキル索引のキャッシュ

`_active_skill_refs` が計画探索6局で約14万回呼ばれ、毎回スキル列を走査していた。
カードのスキル定義は不変なので `(card_id, timing) → 該当インデックス列` を
遅延キャッシュする。**カード定義を実行時に書き換えるとキャッシュが古くなる**が、
カードの追加（新しい card_id）は安全であり、書き換えは行わない運用である。

### 4. CPython 3.13

3.11 → 3.13 で +3%（H）/ +9%（貪欲）/ +6%（計画探索）。
以前の測定（+15%）より小さいのは、上の最適化でインタプリタ負荷の高い部分を
先に削ったためである。**fingerprint は処理系をまたいでも一致した**
（D-001 の乱数互換の前提を再確認できた）。

## 効かなかったもの: racing（1手目の絞り込み）

決定化を重ねながら、平均値の下位半分の1手目を次の標本から外す枝刈りを実装した
（`PlannerAgent(race_after=...)`）。

| race_after | 速度 | 対H勝率 (n=300) |
|---|---|---|
| 1（1標本で即絞る） | 2.44 局/秒 | 0.863 ±0.039 |
| 2 | 2.00 局/秒 | 0.903 ±0.033 |
| **99（無効・既定）** | 1.77 局/秒 | **0.923 ±0.030** |

（速度は `apply_owned` 取り込み前の測定。相対比較として読むこと。）

**速度と強さがきれいに交換されている。** plan_samples を増やしたのは
分散抑制のためだった（`PLANNER_NOTES.md`）ので、標本を早く打ち切る racing は
その効果を部分的に打ち消す。フェーズ3では速度は足りているので**既定は無効**。
大量実験で速度が要るときだけ `race_after=2` を使う。

## 現時点の見積り（ローカル4コア想定）

単プロセスの 1.5x（B-2）× 1.06（3.13）× 約3.8（4コア並列）≒ **6x**。
計画探索が約 8-9 局/秒 の見当になる。フェーズ3の実験（10^2〜10^3局規模）は
これで十分に回る。

## 残る手（B-1 の実測を見てから）

- `_active_skill_refs` はまだ全体の約13%。タイミング別の索引を
  スロット構成単位でキャッシュする余地がある
- `legal_actions` が約10%。アクションフェイズのレベルアップ候補列挙が重い
- **Rust移植（D-001）は依然として本命だが、着手はカードDB確定後**
  （マスターと合意, 2026-08-23）。PyO3 の境界をどこに引くかは
  IS-MCTS の実測プロファイルを見てから決める
