## 1. C-1 とは何か、なぜ次なのか

レビュー（`REVIEW_2026-08-23.md` §6 C-1）の定義:

> 自己対戦データで局面価値を学習し、手書き評価関数 `evaluate` を置き換える／補う。

### 動機

1. **B-1 の結論（D-033）**: IS-MCTS が計画探索に届かない弱点は
   **葉評価の質と分散**である。学習した価値関数はそこを直接改善し、
   木の構造はそのまま使える。
2. **計画探索（champion）も同じ `evaluate` を使っている**
   （`meicho/greedy.py` の `evaluate` + A-3 の `TUNED_WEIGHTS`）。
   葉の質が上がれば champion 自身も強くなりうる。
3. CEM（A-3）は線形の重み 6 個の調整で頭打ち。特徴の**非線形な組み合わせ**
   （例: ライフ差の価値は協奏の枚数に依存する）は現行の形では表現できない。

## 2. すでにある資産（作り直さないこと）

### 現行の評価関数（置き換え対象であり、特徴の出発点）

`meicho/greedy.py`:

```python
class Weights:  life / concerto / hand / live_red / level / resource
def evaluate(s, pi, w) -> float   # pi 視点。相手の手札の中身は参照しない
```

調整済みの重みは `meicho/planner.py` の `TUNED_WEIGHTS`
（life=1.0, concerto=1.034, hand=1.126, live_red=0.533, level=0.498, resource=0.061）。
MCTS は葉でこれを `tanh` で [0,1] に潰して使う（UCB の有界報酬前提）。

### 特徴の候補（レビュー時点の目星）

- 現行 `evaluate` の 6 項（差分特徴）
- `live_reds(s, pi)`（`meicho/heuristic.py`。使用可能な赤の枚数）
- 協奏目標からの乖離（`Params.concerto_target=4` との差）
- `state.clash_counts`（D-031 で追加済み。両者の対抗色の累積回数。公開情報）
- 追加するなら**公開情報＋自分の私有情報のみ**から計算できること（下の規約参照）

### 対局データの生成と計測

- `meicho/runner.py` の `play_game`（`initial` 引数で途中局面からの再開も可）
- `experiments/arena.py` の `series` / `gauntlet`（プロセス並列・CI付き）
- `experiments/ladder.py` / `rating.py` / `registry.py`（C-4。受け入れ試験に使う）
- 速度: H同型 287局/秒、計画探索 2.1局/秒、MCTS(160) 0.29局/秒（2コア）

### エージェント登録の作法（C-4 で決めた）

新しいエージェント（例: 学習価値関数を積んだ planner/MCTS）は
1. `experiments/registry.py` の `FACTORIES` に登録名を足す
2. `tests/test_ladder.py` の登録テストに足す
3. ガントレット JSON に factory 名で書けば ladder が測ってくれる

## 3. シード帯（重要）

**80000..89999 はラダー（評価）専用。C-1 の学習・調整に使ってはならない**
（`ladder.py` が台帳を検査して拒否する。D-028/D-034）。

C-1 用の帯は `experiments/seed_bands.json` の `next_free`（**90000**）から取り、
**bands に用途を追記し next_free を進めてから**使う。例:
学習データ生成 90000..、検証 100000..、のように学習と検証も帯を分ける。

### 4.2 最初に測るべき損益分岐 → **実施済み (2026-08-24, D-035)**

**結論: 速度は壁ではない。以下の当初の懸念は実測で否定された。**
詳細は `C1_SPEED_NOTES.md`、計測は `experiments/bench_evaluate.py`。

- `evaluate` は計画探索の1局の **1.6%**、IS-MCTS の **0.6%** しか占めない
  （呼び出しは 2373 / 6301 回/局と多いが、1回 3.1 µs）。
  遅いのはロールアウト（`apply` 系）であり、`evaluate` ではない。
- 実測の低下（挙動不変のコスト付加・fingerprint 一致で確認）:
  線形22項（純Python）は測定ノイズ内、MLP 22-32-32-1 は numpy で計画探索 −6.1% /
  IS-MCTS −1.3%、純Python でも −32.4% / −14.4%。**2.1 → 0.5 局/秒は起こらない。**
- **葉のバッチ評価のための探索構造の改造は不要**（32件バッチの節約は1局 2.8%）。
- **`leaf_budget=220` は上限として機能していない**（終端数 中央値12・最大112、
  予算到達 0.00%）。「予算を削って単価を払う」はできない。効くつまみは `plan_samples`。
- **本件は D-001（Rust 移植）の追加根拠にはならない。** 壁は `evaluate` ではなかった。

以下は当初の記述（背景として残す）:

> **推論速度が強さに直結する。** `evaluate` は探索のホットループから呼ばれる
> （planner は leaf_budget=220、貪欲は全候補×標本6）。純Python の MLP 推論で
> planner が 2.1 → 0.5 局/秒に落ちれば、質の向上が予算の減少に食われうる。

## 5. 守るべき規約（このプロジェクト固有）

- **覗き見の禁止が最重要（D-026）**: 特徴は「自分の視点で見えるもの」だけから
  計算すること。`observe(s, pi)` に含まれない情報（相手の手札の中身・山札の順序）
  を特徴に入れたら、それは学習でも反則である。新エージェントは必ず
  `meicho/audit.py` の覗き見監査にかける（`tests/test_engine.py` に雛形4件）。
- **作業規約5**: 裁定変更・カード追加時はテスト先行。**141件を下回らない**こと。
- **作業規約6**: 勝率には n と 95%CI。学習の乱数もシードを記録し再現可能に。
- **D-006**: グローバル乱数禁止。`(seed, rng_calls)` 由来のみ。
- **探索に乱数を引く部品を足したら CRN のスナップショット対象に入れる**
  （B-3 の教訓。入れ忘れると分散が増えて勝率が落ちる）。
- **決定化は `sorted()` で正規化してから混ぜる**（D-026。`random.shuffle` は
  入力の並びの関数）。
- 学習環境（Kaggle/Colab）とローカルの分業はプロジェクト指示どおり。
  カード画像・公式テキストの複製を含む成果物を公開しない。

## 6. 前セッションで踏んだ罠（C-1 にも効くもの）

1. **旧シード帯の数字は甘い可能性がある。** planner vs H が帯を替えたら
   0.923 → 0.880 に下がった（§0）。比較はすべて同じラダーで行うこと。
2. **境界の結果は必ず別シード帯で追試する**（多重比較の偽陽性。A-4 で 26 件中
   1 件が偽陽性だった実績がある）。
3. **挙動を変えない最適化は fingerprint（`bench_agents.py`）で受け入れ、
   挙動を変える変更はラダーで受け入れる。** 学習価値関数は後者である。
4. pickle 制約: ラダーに載せる生成器は lambda 不可（`registry.Mk` を使う）。
   学習済み重みは生成器の kwargs（ファイルパス等）として渡す設計にすると
   ガントレット JSON に書ける。
