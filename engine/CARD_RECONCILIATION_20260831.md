## 0. 結論（ここだけで判断できるように書く）

**(1) 数値データはほぼ完全に一致している。**
コスト・スピード・ダメージ・色・キャラのタグは、突き合わせできた52枚すべてで
`cards/` と engine が一致した。発売前に写真から起こしたデータの精度は高かった、
ということである。**過去のシミュレーション結果を数値の誤りで捨てる必要はない。**

**(2) ただし内容の誤りが2件ある。うち1件は勝率に影響する。**

| # | カード | 誤っている側 | 内容 |
|---|---|---|---|
| A | 秧秧 Lv2（SD01-003） | **engine** | 発動条件が逆。実カードは「**相手が**赤で対抗した場合」、engine は「**自分が**赤で対抗した場合」 |
| B | 躍動する炎（SD01-009） | **engine** | 特徴タグ「焦熱」が抜けている |

A は「相手の赤を咎める防御的な能力」が「自分の赤を後押しする攻撃的な能力」に
化けているということで、**SD001 デッキの強さの評価そのものが変わる**。
実カード画像で裏取り済み（§4-A に画像所見を記載）。

**(3) 逆に `cards/` 側（CSV・JSON）にも転記漏れが2件ある。**

| # | カード | 誤っている側 | 内容 |
|---|---|---|---|
| C | 散華 Lv0（BP01-033） | **CSV/JSON** | 実カードは「置いて**もよい**」。CSV は「置く。」で任意指定が落ちている |
| D | 今汐 Lv1（SD02-006） | **CSV/JSON** | 実カードは「手札に加えて**もよい**」。CSV は「加える。」で任意指定が落ちている |

engine 側はどちらも「〜してもよい（＝プレイヤーが選択できる）」で実装済みであり、
**engine のほうが正しい**。画像で裏取り済み。
`cards/` を正とするなら、統一の前に CSV/JSON を先に直す必要がある。

**(4) engine には13枚が未登録、1枚が余分にある。**
未登録は BP01 の新規キャラ（ツバキ4枚・アンコ4枚）、既存キャラの別Lv1（4枚）、
アクション「黒メェと白メェ」1枚。
余分は `AC-001`「音の形・空中攻撃」で、これは判読不能だったカードの仮登録
（`unverified` 付き）だが、**`cards/` のどの画像にも該当がない**。実在しない
可能性が高い（§4-E）。

**(5) ID 体系は全面的に食い違っている。** engine は仮ID（`SD001-T01` / `AC-003` 等）を
使っており、公式番号と一致しているのは `SD02-002`・`SD02-004` の2枚だけである。
さらに悪いことに、**同じ文字列が別のカードを指している箇所が3組ある**
（例: engine の `SD02-001` は Lv0 だが、実物の SD02-001 は Lv2）。
機械的な一括置換をすると壊れるため、置換は §5 の順序で行う必要がある。

## 1. 突き合わせの方法

4つの系統を、それぞれ別々に比較した。

1. **CSV ↔ JSON**: 全76行・全15列を文字列として直接比較。
2. **画像 ↔ CSV**: ファイル名から `セット-番号`・カード名・LV表記・レアリティ違い（`-R`）を
   取り出し、CSV の行と突き合わせ。
3. **engine ↔ CSV**: ID が食い違っているため、**ID では突き合わせられない**。
   キャラカードは「キャラ名 + レベル」、アクションカードは「セット + カード名」を
   鍵にして対応づけ、そのうえで色・コスト・スピード・ダメージ・タグ・
   【リーダースキル】指定を比較した。
4. **効果テキスト**: 機械比較ができない（CSV は日本語文、engine はオペコード列）ため、
   34枚のアクションカードと18枚のキャラカードを1枚ずつ目視で照合した。
   差異が疑われた4枚は実カード画像を開いて裏取りした。

照合スクリプトは `engine/scripts/reconcile_cards.py` として保存できる状態にしてあるが、
本報告時点では未配置（裁定後に配置する）。

## 2. 系統ごとの一致状況

| 比較 | 結果 |
|---|---|
| CSV ↔ JSON | **完全一致**。76行×15列すべて同一。JSON は CSV の機械変換とみてよい |
| 画像 ↔ CSV（カード番号） | **完全一致**。両者とも65種。片方だけにある番号はゼロ |
| 画像 ↔ CSV（レアリティ違い） | **完全一致**。`-R` 画像がある11種は CSV も2行ある |
| 画像 ↔ CSV（カード名・LV表記） | ファイル名の表記ゆれが4件（§4-F）。カードそのものの相違ではない |
| engine ↔ CSV（枚数） | engine 53枚 / CSV 65種。差の内訳は §4-D・§4-E |
| engine ↔ CSV（数値・タグ） | 突き合わせできた52枚のうち**51枚一致**、1枚のみタグ欠落（§4-B） |

**用語の補足**: ここでいう「レアリティ違い」とは、同じカード番号で絵柄や加工だけが
異なる版のことである。ゲーム上の性能は同一なので、engine は区別しなくてよい。
CSV が76行あるのに65種なのは、この11種が2行ずつあるためである。

## 4. 差分の詳細

### 4-A. 【要修正・engine】秧秧 Lv2 の発動条件が逆になっている

- 該当カード: `SD01-003`（engine 側の現ID は `SD001-C06`）
- 実カード画像の記載:
  > 【リーダー】【対抗】**相手が**赤色のカードで対抗した場合、相手はコスト1を
  > 支払ってもよい。支払わなかった場合、相手はダメージ3を受ける。
- CSV の記載: 実カードと一致（CSV は正しい）
- engine の実装: `condition={"self_color": Color.RED}`
  → 「**自分が**赤色のカードで対抗した場合」になっている

**何が起きているか。** このカードは本来、
「相手が赤（攻撃色）で殴りにきたときに、コストを払わせるか3ダメージを与えるかを
相手に選ばせる」**カウンター型の能力**である。それが engine では
「自分が赤で攻撃したときに、相手にコストか3ダメージを押しつける」
**追加打点の能力**になっている。

**影響範囲。** 秧秧を Lv2 リーダーに置いたときの価値が変わる。
現行の engine では「自分から赤で殴れば必ず得をする」ので、探索AIは秧秧Lv2を
攻撃的に使う方向に最適化されているはずである。実カードでは逆に
「自分は赤で殴らず、相手の赤を待つ」のが正しい使い方になる。
したがって、**SD001 を含むマッチアップ勝率・ラダーのレーティング・
発見ループが見つけた「強い型」は、修正後に測り直しが必要**になる可能性がある。
（数値がどれだけ動くかは、修正して同一シードで対照実験をするまで分からない。）

対応する既存テスト `test_opponent_choice_pay_option` /
`test_opponent_choice_decline_option`（`tests/test_engine.py` 582行〜）は、
現行の誤った条件を前提に書かれているため、修正時に一緒に書き換える必要がある。

### 4-B. 【要修正・engine】躍動する炎のタグ「焦熱」が欠けている

- 該当カード: `SD01-009`（engine 側の現ID は `SD001-T09`）
- 実カード画像の特徴欄: 「変奏スキル」「焦熱」の2つ
- CSV: `変奏スキル、焦熱`（正しい）
- engine: `tags=("変奏スキル",)` のみ

**影響範囲。** 現時点では小さい。属性タグ「焦熱」を参照する効果は、いま登録済みの
カードには無いためである。ただし未登録のアンコ（BP01-012〜015）は【アンコ】名や
＜基本攻撃＞タグを参照する能力を持っており、今後タグ参照型のカードが増えると
効いてくる。また、カードを特徴ベクトルで表す仕組み（D-061 のカード符号化）では
タグが入力になるため、そこにも影響する。
なお SD02 側の対応カード「蟠龍の輝き」（SD02-009）は CSV も engine も
`変奏スキル、回折` で一致しており、欠落しているのは SD01-009 の1枚だけである。

### 4-C. 【要修正・CSV/JSON】「〜してもよい」の欠落2件

| カード | 実カード画像 | CSV/JSON | engine |
|---|---|---|---|
| `BP01-033` 散華 Lv0 | 「協奏エリアに置いて**もよい**。」 | 「置く。」 | `optional=True`（正） |
| `SD02-006` 今汐 Lv1 | 「手札に加えて**もよい**。」 | 「加える。」 | `optional=True`（正） |

**なぜ重要か。** 「〜してもよい」は、engine では `optional=True` として
**プレイヤーの選択肢**になる。強制なら常に実行される。
たとえば散華Lv0の「デッキの上から1枚を協奏エリアに置く」は、
デッキを削る行為でもあるので、終盤に強制されると自滅しうる。
つまりこの1語の有無で合法手の集合が変わり、AIの探索結果も変わる。

engine の実装が正しく、CSV/JSON 側が転記漏れである。
`cards/` を正とする方針を採るなら、**統一作業の前にこの2行を直す**必要がある。
そうしないと、正しい実装を誤ったデータに合わせて壊すことになる。

### 4-G. `cards/` 側に無い情報（統一の障害）

`cards_structured.csv` の列は
`code, rarity, name, cost, type, color, level, speed, affiliation, damage, attribute, weapon, trait, effect, set`
の15列である。ここに **「専用キャラ」の列が無い**。

必要、という構築上の制約）は、カード画像の左上に表示されているが、
CSV には落ちていない。**この列が無いままだと CSV からデッキ構築規則を再現できない。**

同様に、engine が持っていて CSV に無い情報:

- `dedicated_to`（専用キャラ）… **必須。CSV に列の追加が必要**

  **engine 側に持ち続けるのが妥当**

- `rarity`（レアリティ）… ゲーム性能に無関係。持たなくてよい
- `set`（収録セット）… プール定義（D-047）に使えるので**持つ価値がある**
- `affiliation / attribute / weapon` の**区別** … engine は3つを混ぜて
  1つの `tags` タプルにしている。現状は困っていないが、
  「所属が瑝瓏のキャラ」のような参照が今後出ると区別が要る

## 5. 「`cards/` を正として統一する」ための手順案

ID の付け替えは影響が広い。確認した参照箇所は次のとおり。

| ファイル | 仮IDの出現数 | 備考 |
|---|---|---|
| `meicho/cards.py` | 53件（定義そのもの） | 起点 |
| `decklists/SD001.json` | 49件 | デッキ40枚＋キャラ9枚 |
| `decklists/SD02.json` | 49件 | 同上 |
| `tests/test_engine.py` | 254件 | 最大の修正対象 |
| `tests/test_card_space.py` | 8件 | |
| `meicho/engine.py` | 7件 | すべてコメント内の言及 |
| `rust/src/cards.rs` | **0件** | Rust 側はIDを持たず添字で扱っている。**再ビルド不要** |
| `webapp/` | 未確認 | 要確認 |
| `experiments/`・`results/` | 未確認 | 過去の実験結果ファイルに仮IDが埋まっている可能性 |

**危険な点。** 単純な文字列置換をしてはいけない。次の3組は、
**同じ文字列が現行と正解で別のカードを指している**ためである。

| 文字列 | engine での意味 | `cards/` での意味 |
|---|---|---|
| `SD02-001` | 漂泊者（男）**Lv0** | 漂泊者（男）**Lv2** |
| `SD02-003` | 散華 **Lv0** | 散華 **Lv2** |
| `SD02-005` | 今汐 **Lv0** | 今汐 **Lv2** |
| `BP01-021` / `BP01-033` / `BP01-030` | それぞれ **Lv2** | それぞれ **Lv0** |

`SD02-001` を素朴に置換すると、Lv0のつもりで書いた箇所が Lv2 を指すようになる。

**推奨手順**（裁定後に実施）:

1. まず §4-C の CSV/JSON の転記漏れ2件を直す（正本を正しくする）。
2. §4-A・§4-B の engine 側の誤りを直し、対応テストを書き換えて全テスト通過を確認する。
   **この時点で、SD001 を含む勝率をすべて測り直す**（同一シードで修正前後を対照）。
3. ID の一斉置換は、**一度すべて衝突しない一時IDに退避してから正IDへ移す**
   2段階で行う（例: `SD02-001` → `TMP-001` → `BP01-021`）。
   置換後、`cards.py` の全IDが CSV の `code` 列に存在することを検査する
   スクリプトを回して、取りこぼしゼロを機械的に確認する。
4. `cards.py` を手書きの定義から **CSV を読み込む形に変える**かどうかは別の判断。
   効果のオペコードは CSV に書けないので、完全な自動化はできない。
   現実的なのは「数値・色・タグ・セットは CSV から読み、効果だけコードで持つ」
   ハイブリッドで、**CSV と食い違ったらテストが落ちる**ようにすることである。
5. 未登録13枚の追加は、新オペコード・新タイミング（【登場】【レベルアップ】）の
   設計を伴うので、**ID統一とは別の作業**として切り出す。

**作業量の見立て**: 2 が半日、3 が半日、5 が数日（新機構の設計・実装・Rust移植・
三者一致テストを含む）。1 は数分。
