### 5.1 （取り下げ）汎用 AI の線

- 初版の「届ける線（V_0 で対戦行列 第 1 版）」は取り下げた（冒頭の追記）。弱い AI 同士の相性表は、デッキの相性ではなく AI の打ちこなし方の差を映し、デッキ選びを誤らせうる
- 汎用 AI を強くする線は、壁の読みと 3 本の腕（TD 目標・代打ち π・補助の目標）を `engine/GENERALIST_WALL_DESIGN_20261006.md` に書いた。待ち時間の測定（W 系）の扱いもそちらの §0-6・§8-4

### 5.2 分岐の事前登録（推しは既定で進む）

- 設計書に「判定の規則」と並べて **「結果 → 次の一手」の表**を書く（例: 判定 1 が通る → 段 2 へ／区別できない → 腕 X を 1 本だけ／下端 < 0 → 止めて相談）。表は結果を見る前に commit される（採点役の基準 1 と同じ扱い）
- 表の中の分岐に当たったら、Claude Code は**推しのまま次へ進む**。マスターには定期報告で知らせる（止めて待たない）
- **必ず止まる種類**（表に書いても自動では進まない）: champion の交代／最終評価の 4 デッキを開ける／rules の版を上げる（ルールの解釈）／判定の規則・帯・局数・対照の変更／クレジットや有料の資源を足す／公開・配布・知人に渡すもの／履歴の書き換えと削除
- **止め方**: マスターは `STEER.md` に 1 行（スマホの GitHub から）、または `AGENT_STOP` を置く。Claude Code は塊の切れ目ごとに読むので、遅くとも 10 分で止まる（AUTONOMY §3）
- 効果の見込み: 10 月の 4 回の往復の待ち（合計 約 48 時間）のうち、表の中に収まるものはそのまま進む。マスターが読むのは「止まった理由」と定期報告だけになる
- 設計の頼み先: 段（段階・線）の切れ目の設計は今までどおり Cowork。段の中の次の一手は、設計書の表で済ませる

### 5.3 CI を物差しに戻す

1 便で済む（PC かクラウドの Claude Code・付録に雛形）:

1. `test_stage3_item4.py` の 6 件を資材の一覧に足す（理由「`s2v_id_ens3.json` は `.gitignore`・約 39 MB」）。これで `main` は緑に戻るはず
2. `concurrency`（同じ PR の古い実行は取り消す）を入れる
3. 途中経過の commit の件名に `[skip ci]` を付ける（GitHub は push と PR の先頭の commit の件名にこの文字があれば走らせない）。報告・道具・台帳の commit には付けない
4. 実行機を `ubuntu-24.04` に固定する（10/19 の切り替えを、測定の途中ではなく自分で選んだ日に行う）
5. torch（CPU 版）を入れた組を足す。PR と手動のときだけ回す（約 50 件の skip が回るようになる）
6. 2 便目: 大きいネット（`s2v_id_ens3.json` など）を GitHub の Release に置き、CI とクラウドが sha を確かめて取ってくる形にする。そうすれば 6 件は一覧から外せる
7. セッションの開始の定型（AUTONOMY §4 の 6）に「`main` の最新の CI が赤なら、着手の前に理由を台帳に 1 行」を足す。進行盤にも CI の色を出す

### 5.4 マスターの手を「見て OK」に変える

- **アプリの確認**: クラウドの Claude Code が Playwright（作業機に入っている）でアプリを立て、確認項目ごとに画面を撮って PR に貼る（動きは GIF）。マスターはスマホで見て OK かコメントを付ける。実機でしか分からないもの（スマホの長押し・bat の起動・知人との通話対戦）だけ手で行う
- **PC の再ビルド**: PC の Claude Code に「TE-13 と PR #16 の分を再ビルドして、指紋と `--pc` の組を確かめて」と頼むだけにする。5 点セットの依頼書は Claude Code 向けに残す
- **4-D のデッキ表**: マスターの 5 分の作業。汎用 AI がマスターに通じるかを測る唯一の線なので、ここだけは手で動かす価値がある
- **`check_done.py`**: 実装は PC の Claude Code（D-147 のまま）。分岐の事前登録と組にすると、自動で進む便の「終わり」を機械が確かめられる

### 5.5 台帳の減量

- `TASKS.md`: Active には未着手と進行中だけを置き、1 件 1〜3 行にする。済んだ 36 件は Done へ、Done は月ごとに `TASKS_DONE_2026-09.md` などへ移す。詳しい経緯は decisions.md と報告書にあるので、TASKS には書かない（TASKS の冒頭の原則「engine/ の文書は記録、TASKS は状態」に戻す）
- `decisions.md`: 10 月の分から月ごとのファイル（`decisions/2026-10.md`）に分け、`decisions.md` を 9 月までの記録と、全 D 番号の 1 行索引にする。**先に Claude Code が、`decisions.md` を読む道具（`verify_report.py`・進行盤の切り出しなど）が無いか確かめる**
- 新しい文書は `engine/docs/` の下に種類別（design・report・request）で置く。既存の 140 本は動かさない（参照が切れるため）
- 書くのは今までどおりエンジンの持ち場の Claude Code（`LANES.md` §3）

### 5.6 公開の扱い

- いまのファイルの本名のパス 29 本を `<ユーザー名>` に置き換える（PR #3 と同じやり方）。ルートに短い README（非公式のファン研究であること・公式素材は含めないこと・入口の文書）と About を足す。取り込み済みのブランチ 10 本を消し、設定の「Automatically delete head branches」を入れる（PR の中身は PR に残るので、報告書の commit の参照は切れない）
- 履歴に残る分は、気になるかどうかでマスターが決める。気になるなら、CI の回し方を直した**あとで**非公開にする（直す前に非公開にすると月 2,000 分の枠がすぐ尽きる）。履歴の書き換えは、報告書と decisions.md が引いている commit 番号が全部変わるので推さない

## 8. 言えないこと

- 裁定までの待ちは commit の時刻で測った近似で、マスターが実際に返事をした時刻ではない
- Actions の使用量（分）と、クラウドセッションのクレジットの残りは見ていない
- `decisions.md` を読み込んでいる道具があるかは確かめていない（§5.5 の分割の前に Claude Code が確かめる）
- アプリの持ち場と相場分析の線は、台帳の見出しと Active を見ただけで、中身までは点検していない
- 秘密の値の探し方は文字の型による検索で、漏れが無いことの証明ではない

## 付録 CI の直し方の雛形（`.github/workflows/tests.yml`・入れる前に Claude Code が公式の説明で確かめる）

```yaml
on:
  push:
    branches: [main]
    paths-ignore:
      - "**.md"
      - "Claude outputs/**"
  pull_request:
    branches: [main]
    # PR の paths の絞り込みは「PR 全体の差分」で判定されるので、道具の変更を含む PR では
    # 途中経過の push を止められない。途中経過は件名の [skip ci] と下の concurrency で止める
  workflow_dispatch:

concurrency:
  group: tests-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true       # 同じ PR の古い実行は取り消す

jobs:
  pytest:
    runs-on: ubuntu-24.04        # 10/19 の Ubuntu 26 への切り替えを自分で選ぶ
    # 以下は今のまま
```
