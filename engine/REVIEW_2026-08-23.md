## 3. §7「特に疑ってほしい箇所」への判定

### 3.1 §7.1 貪欲の重み調整の過適合 → 懸念は概ね晴れた

貪欲の非担当フェイズは既定ヒューリスティックに委譲しているため、
「貪欲 vs X」の勝率単体では貪欲の寄与が分からない。対照として
「既定ヒューリスティック vs X」を測り、その差分を貪欲の寄与とした
（`review_check.py`）。

| 相手 X | 貪欲 vs X | 対照（既定H vs X） | 貪欲の寄与 |
|---|---|---|---|
| 既定H（in-sample） | 0.680 ±0.053 | 0.500（同型対称） | +0.180 |
| X1: concerto_target=3, levelup_min_hand=4 | 0.673 ±0.053 | 0.520 ±0.031 | **+0.153** |
| X2: own_color=3, scarce=0.7, switch=1 | 0.703 ±0.052 | 0.558 ±0.031 | **+0.145** |
| X3: counter=6, own_color=1.5（踏み型） | 0.723 ±0.051 | 0.593 ±0.030 | **+0.130** |

寄与は in-sample の +0.180 からわずかに縮むが、3種の第三の相手すべてに
明確に転移した。**0.655 という数字を大きく割り引く必要はない。**

残る限界: 第三の相手がいずれもヒューリスティック族（パラメータ違い）である。
構造的に異なる相手（IS-MCTS、人間）への転移は未検証のままであり、
これはフェーズ4で自然に解消される。

### 3.2 §7.2 「自分の色を出し続ける」の頑健性 → 保留は妥当

指摘のとおり、対戦相手がすべて固定方策である以上、ここで結論は出ない。
own_color_weight=12.0 に留めた判断（実測上の損失なし・搾取への保険）は
合理的であり、IS-MCTS実装まで保留してよい。

なお、安価な中間検証として「凍結した H(own_color=1000) への最適応答探索」
を提案する（§6 A-5）。貪欲は既にヒューリスティックへの近似最適応答なので、
その勝率が被搾取性の下界になるという読み方ができる。

### 3.3 §7.3 CFR実験の価値 → 実験は残す価値がある。ただし記載の事実誤認と読者誤導の修正が必要

まず事実関係の訂正。引継ぎ書は「現状はレポート内に追補として『結論が逆転した』
ことを明記している」とするが、**CLASH_CFR_REPORT.md に逆転の記載はない。**
grep で確認した範囲で、逆転・counter_weight・自色確定 0.657 のいずれも
レポートに現れない。既存の追補2つは「手札の枯渇」「赤の枚数の理由」であり、
逆転はHEURISTIC_NOTES.md と引継ぎ書にしか記録されていない。しかもレポート
§9 の実戦Tips（「迷ったら青」等）は旧結論のまま生きている。

同種の矛盾が `meicho/heuristic.py` の冒頭docstringにもある。「対抗の色は
相手のリーダーの担当色を3すくみで踏むのが基本（CLASH_CFR_REPORT.md 主結果）」
と書かれているが、直下の `Params` の既定は counter_weight=0.0（踏まない）である。

実験自体の価値についての判断: **残すべきである。** 理由は、
「部分ゲームの均衡解は、切り出し方（手札i.i.d.仮定）が実ゲームと違えば
実ゲームで逆転しうる」というこのプロジェクトで最も教訓的な失敗例であり、
フェーズ4で同種の切り出し（部分観測の決定化、報酬の較正）を行う際の
警告として機能するからである。誤導リスクは構成の問題であり、内容の問題ではない。

処置の提案（30分以内の作業）:

1. CLASH_CFR_REPORT.md の**冒頭**に「結論の現在の状態」節を置き、
   主結果が実ゲーム検証で逆転したこと（counter_weight=0 が最強・
   自色確定 vs カウンター確定 0.657）と、HEURISTIC_NOTES.md への参照を明記する。
2. §9 実戦Tipsに取り消しの注記を付ける（特に「迷ったら青」）。
3. heuristic.py の冒頭docstringを現在の結論に合わせて書き直す。

### 3.4 §7.4 覗き見テストの弱さ → 監査で置き換えた。ヒューリスティックは合格、貪欲に漏洩を発見

単一局面のテストの代わりに、実対局のリプレイ中の**全実決定ノード**（合法手
2以上）で隠蔽情報を差し替え、選択の不変性を検査する監査を実装した
（`review_nopeek_audit.py`。エージェントの乱数状態を試行ごとに復元して
比較条件を揃える）。

| エージェント | 差し替え対象 | 決定ノード | 違反 |
|---|---|---|---|
| ヒューリスティック（40局） | 相手手札＋両デッキ順序 | 2054 | **0** |
| 貪欲（6局） | 相手手札＋両デッキ順序 | 334 | **7** |
| 貪欲 | 相手手札のみ | 334 | 0 |
| 貪欲 | **自分のデッキ順序のみ** | 334 | **7** |
| 貪欲 | 相手のデッキ順序のみ | 334 | 1 |

**ヒューリスティックは公開情報のみで動いていることが高い網羅性で確認できた。**
一方、貪欲の違反の原因は自分のデッキ順序である。機構は明確で、先読みの
`apply`／`_settle` がドロー効果を**実際のデッキ順序**で解決するため、
「次に引く札を知った上で」手を比較している。評価関数が相手の手札を読まない
という既存テストの主張は正しいが、**先読みの過程**が隠蔽情報を使っていた。
既存テストが単一の初期局面（先読み中にドローが発生しない）だったため
すり抜けていた。相手デッキ順序の違反1件も同機構である（先読み中の相手の
ドローが実順序で解決される）。

影響の測定: 先読み時に両デッキ順序も決定化する公正版（`review_fair_greedy.py`）
は 0.637 ±0.054、元の版は 0.680 ±0.053（同一シード n=300）。差は信頼区間内で
あり、**貪欲の優位が覗き見によるものではない**ことも同時に確認できた。

処置の提案: (1) 公正版の変更（デッキ順序の決定化を `_sample_opponent` と
単独決定フェイズの先読みに追加）を greedy.py 本体に取り込む。
(2) 本監査を縮小版（数局・数百ノード）でテストスイートに常設し、
今後のエージェントすべてに適用する。フェーズ4のIS-MCTSは同じ `_settle` 系の
部品を深く使うため、放置すると漏洩が探索の深さに比例して拡大する。

### 3.5 §7.5 アブレーションの解釈 → 指摘は正しい

同型対戦のアブレーションは相対寄与であり、「協奏エリアの整備 0.927」の絶対値
は同型ゆえに強調されている可能性が高い、という自己評価に同意する。安価な補強
として、主要規則2つ（協奏整備・レベルアップ）だけでも SD001 vs SD02 の異型
対戦で再測定しておくと、デッキ非依存の知見かどうかが切り分けられる。

### 3.6 §7.6 重みの相互作用 → 妥当。結合探索を提案

「一つずつの掃引が誤導する」という観測は本質的で、対処は §6 A-3 の
結合最適化（CEM/TPE）に集約する。現状の既定値のまま結論を急がない判断は正しい。

### 3.7 §7.7 D-022 の先送り → 妥当

B-4（誘発列挙の一括先行）は現行カードプールで挙動差がないことが
SIMPLIFICATIONS.md に記録済みであり、先送りは妥当である。推奨する追加の防御は
1行で済む: `_queue_fire` に「解決中に相手の盤面が変わったら列挙をやり直す必要
がある」旨のアサーションまたはコメントを置き、将来のカード入力時に気づける
ようにする（カード入力は別セッションが行うため、コード内の防御が効く）。

## 4. §7 以外で見つかった記載の問題

### 4.1 §8-4 の「58%」が再現しない

「レベルアップの手札コスト選択が全選択の58%を占めている」は測定条件が
書かれておらず、追試では再現しなかった。実決定ノード（合法手2以上）の内訳は
次のとおり（`review_profile.py` 相当の測定）。

| 方策 | 最多カテゴリ | levelupコスト選択を含む choice:discard |
|---|---|---|
| ヒューリスティック自己対戦 200局 | action 38.8% | 11.1% |
| ランダム自己対戦 100局 | action 49.8% | 9.9% |

「決定ノードの削減が速度に効く」という方向性自体は正しい（choice系を合計
すると約25%）。ただし58%という数字は、計数方法（分岐数の合計か、choice内の
比率か）を明記して測り直すまで引用しないことを推奨する。

## 5. 良い点（維持すべき実践）

信頼区間と対戦数の常時併記、先攻後攻の両方向測定、シードの決定的使用、
テストへの条項番号の明記、そして「変奏コンボは判定不能」のような負の結果・
判定不能の記録は、いずれもこの規模の個人プロジェクトとして例外的に規律が
高い。CFRの逆転を「実験の誤り」ではなく「解いた部分ゲームの定義の問題」と
切り分けた分析も正確である。この文化は維持すべきである。

## 6. CPU強化の提案（優先順）

現状の構図: ランダム ≪ ヒューリスティック < 貪欲（+0.18）。伸びしろの所在は
実測から明確で、(a) アクションフェイズ（貪欲 0.338 と最弱）、(b) 対抗の
駆け引き（現状は「自色を出す」のみ）、(c) 評価関数（線形・手調整）の3つである。

### A. 即効（フェーズ3内・ローカルPCで可能）

**A-1. 貪欲の公正化（正しさの修正・最優先）**
§3.4 の deck 順序決定化を本体に取り込む。実装は `review_fair_greedy.py` に
動作するものがある。取り込み後、GREEDY_NOTES.md の数値を再測定して更新する
（0.64前後になる見込み）。

**A-2. ターン計画探索 — アクションフェイズの構造を利用する（強さへの本命）**
貪欲がアクションフェイズで負ける原因は「1手先では手札が減った損失しか
見えない」ことだった。ここで効くのは先読みの深さ一般ではなく、
**アクションフェイズが相手の関与しない単独逐次決定である**という構造である。
チャージ・切り替え・レベルアップは各1回/ターン（§6.3）なので、ターン内の
行動列の空間は小さい。「1手」ではなく**「ターン内の行動列全体」を単位として
列挙し、対抗ステップ直前（または対抗の決定化評価後）の局面を採点する**。
これなら「チャージしてから対抗に入る」の合計価値が正しく見える。

- 分岐の抑制: 同一の結果局面に至る行動列の重複除去（チャージとレベルアップの
  順序交換など）、チャージ対象の card_utility 上位数枚への限定。
- 期待値: アクションのみ貪欲 0.338 → 0.5 超、既定構成との併用で
  対ヒューリスティック 0.7 超を目標ラインとする。
- ここで作る「ターン計画の列挙＋採点」は、そのままフェーズ4のMCTSの
  行動抽象（アクションフェイズを1ノードに潰す）として再利用できる。

**A-3. 評価関数と Params の結合最適化**
§7.6 の相互作用問題への恒久対策として、単軸掃引をやめ、CEM または
Optuna(TPE) で Weights×主要Params を同時に探索する。目的関数は
**固定シード・固定相手プール**（既定H＋摂動H群＋貪欲変種）に対する平均勝率
とし、in-sample 化（§7.1）を仕組みで防ぐ。ヒューリスティックは242局/秒
出るので、1評価300局×数百試行はローカルで一晩の規模である。

**A-4. ヒューリスティックの整理**
寄与ゼロと実証された規則（use_lethal、use_skip_clash 等の差なし群）を
削除または既定オフにし、調整空間を絞る。リーサル判定は「対抗に勝つ見込み」
を要するため規則では書けず、貪欲側（決定化評価）に任せるのが正しい分担である。

**A-5. 被搾取性の安価な測定（§7.2への中間回答）**
H(own_color=1000) を凍結し、それに対する最適応答をパラメータ探索
（counter系の掃引＋貪欲の重み探索）で近似する。到達勝率がそのまま
「確定方策がどこまで搾取されうるか」の実測下界になる。

### B. 中期（フェーズ4の入口）

**B-1. IS-MCTS（決定化UCT）**
部品は既に揃っている: `_sample_opponent`（決定化）、`_settle`（進行）、
ヒューリスティック（ロールアウト方策）、evaluate（葉の評価）。
対抗ステップの同時手番は DUCT（各プレイヤーが独立にUCBを回す）で扱うのが
実装最小。A-1 の公正化が前提条件になる（漏洩が探索深さで拡大するため）。

**B-2. 速度（B-1の前提）**
Python の 25局/秒では1決定あたり数百シミュレーションが限界である。順序は
(1) プロファイルでホットスポット確認（clone と legal_actions が候補）、
(2) 対局単位のプロセス並列（実験のスループットはコア数倍になる。決定性は
シード分割で維持）、(3) D-001 のRust移植。(3) の判断は (1) の結果を見てから
でよいが、IS-MCTS を本格運用するなら最終的に必要になる見込みである。
移植時は同シード同結果の一致テスト（D-001）を先に書く。

**B-3. 相手モデルの脱固定化と履歴**
貪欲・MCTSの相手モデルが「既定ヒューリスティック」固定である限り、
異質な相手への見積もりは歪む。C-2（observe が履歴を持たない）の解消と
合わせて、「相手がこれまで対抗に出した色の経験分布」を最初の履歴特徴として
導入する。人間対戦（§8-3）を見据えると、ここが実利の大きい一歩になる。

### C. 学習（フェーズ4本体・Kaggle/Colab）

**C-1. 価値関数の学習**
自己対戦ログ（局面特徴, 最終勝敗）からロジスティック回帰で evaluate の
後継を学習し、貪欲・MCTSの葉評価を置換する。特徴は現行 evaluate の項＋
live_reds＋協奏目標乖離＋履歴特徴から始める。線形で頭打ちを確認してから
小型MLPに進む。CPUで足りる規模であり、Hugging Face に重みを置く運用
（プロジェクト方針）に乗る。

**C-2. PSRO / NFSP による混合方策**
§7.2 への正面回答。エージェント集団（H変種・貪欲変種・MCTS）で
利得行列を作り、メタゲームのナッシュ混合を維持しながら最適応答を追加して
いく。CFR実験の教訓（部分ゲームの切り出しが結論を歪める）を踏まえ、
**常にフルゲームの勝率で評価する**ことを不変条件とする。

**C-3. IS-MCTS＋学習価値関数**
B-1 と C-1 の合流点。「マスターより強い」の到達目標はここで狙う。

**C-4. 恒久評価インフラ**
固定シード・固定相手プールのガントレットと簡易Eloを整備し、以後のすべての
エージェントを同一の物差しで測る。§7.1 型の in-sample 評価を構造的に
再発させないための投資である。

### 優先順の提案

**A-1 → A-2 → A-3 →（A-4, A-5 は隙間で）→ B-2(1)(2) → B-1 → C-1 → C-2/C-3。**
A-1 は半日、A-2 と A-3 が今週の本体、Bは A の頭打ちを確認してから。
発売（2026-09-12）後はカードDB整備が割り込むため、A群を発売前に
片付けておくとフェーズ3→4の移行が滑らかになる。
